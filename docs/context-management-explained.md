# Wovra 上下文管理机制详解（通俗版）

> 本文是 `context-runtime-v2.md`（设计定稿）的通俗讲解版。
> 每个机制都按同一个套路讲：**是什么 → 常规做法 → Wovra 的做法 → 举例 → 优化在哪**。
> 读完你就能向别人解释清楚 Wovra 到底在干什么。

---

## 开读前的五个基础概念

**① token（词元）**：模型计费和计算的基本单位，大约等于半个到一个汉字，或一个英文单词。你发一段话，模型按 token 收费、按 token "阅读"。

**② 上下文（Context）**：每次请示模型时发给它的**全部材料**——系统设定 + 对话历史 + 工具结果 + 当前问题。模型没有记忆，每次回答都是"带着全部档案重新看一遍"。所以档案越厚，每次越贵。

**③ 前缀缓存（Prefix Cache）**：服务商给的折扣机制。这次发的材料，如果**开头部分**和上次一模一样，相同部分只收 **1/30 的钱**。但只要开头改了任何一个字，折扣全部作废，后面全部按原价。

**④ Agent 循环**：AI 干活不是一口气答完，而是"想一想 → 调一个工具 → 看结果 → 再想"循环很多步（叫"步"）。**每一步都要把全部材料重新发一遍**——这是成本会滚起来的根本原因。

**⑤ 基座（B）**：每一轮对话中，每一步都要重复发送的那部分材料（历史 + 状态 + 系统设定）。它是成本公式里的乘数：

> 一轮的总输入 ≈ 步数 × 基座。基座 770K 走 17 步 = 1316 万 token；基座 50K 走 17 步 = 92 万 token。

记住这个公式，全文所有的机制都在做同一件事：**把基座压小，同时不弄丢"需要时能找回细节"的能力，还不破坏前缀缓存。**

---

## 机制一：Round（轮）——以"最终回答"为边界记账

**是什么**：用户发一条消息，到 AI 给出最终回答，中间不管调了多少次工具，整个过程记为一个 **Round（轮）**。轮内的一步步动作（用户输入、工具调用、工具结果、回答）叫 **Event（事件）**。

**常规做法**：所有消息摊平成一条无限长的列表，没有结构。哪些消息属于"同一件事"，没人说得清。

**Wovra 的做法**：按 Round 切片记账。而且**轮的闭合规则很讲究：只有 AI 产出最终回答，一轮才算结束**。

**举例**：网络断了，你连发三条"继续"（AI 一次都没回上），网络恢复后 AI 完成回答。在 Wovra 里这不是三轮废轮 + 一轮正常轮，而是**一个完整的 Round**：三条"继续"作为独立事件保留在轮内，整理时合并理解。

**优化在哪**：

- 断断续续的尝试、失败的尝试都被当成"同一件事的过程"来整理，而不是三个孤立碎片
- 没有闭合的轮（AI 没回上）**不产生任何整理成本**——空转不花钱
- 跨会话也成立：中途退出程序，下次打开接着积累，直到 AI 回答

## 机制二：Event 双份存储——Full 与 Truncated

**是什么**：Round 里的每个事件，同时存两份：

- **Full（全文）**：原始内容，一字不改，永久保存，是"事实来源"
- **Truncated（截断概览）**：由**程序**自动生成的一行概览（约 120 字），**不花一分钱模型调用**

**常规做法**：二选一。要么全存全发（每个工具结果原文都塞给模型，基座爆炸）；要么截断后丢弃原文（细节永远找不回来）。

**Wovra 的做法**：Full 永存，Truncated 用于"日常展示和装配上下文"，需要细节时从 Full 找回（见机制十）。

**举例**：模型调用 `read_file` 读了 3000 字的源码。

```text
Full：      （那 3000 字源码，原样存着）
Truncated： [R5-E02] 调用 read_file({"path":"src/icp.cpp"}) → 成功（共 2400 行）
```

**优化在哪**：日常上下文里放的是一行概览（约 50 token），不是 3000 字（约 2000 token）。信息没丢——想看原文随时能取回。**用 40 分之一的日常成本，保留了 100% 的可追溯性。**

## 机制三：安全阈值——超大输出的保险丝

**是什么**：单条工具结果超过 **2000 字符**时，进入当前上下文的是"前 2000 字 + 一条指路条"，原文完整存在 Full 里。

**举例**：某个命令输出 10 万字日志。

```text
上下文里：   [输出过大（100,000 字符）已截断。完整结果：R5-E07，可用 expand_history 查看]
Full 里：    （完整的 10 万字日志）
```

**常规做法**：要么全塞（一次就把基座撑大 10 万），要么硬砍且不告诉模型"还有更多"。

**优化在哪**：模型明确知道"有一条我没看全的信息、它的编号是 R5-E07、想看可以取回"。保险丝熔断是显式的、可恢复的，不是静默丢失。

## 机制四：Organization——异步的幕后整理员

**是什么**：一轮闭合后，系统把它丢进**后台队列**，由一个专门的整理流程（Organization）处理。主对话**完全不用等**——这就是你不会再感觉"回答完了卡两分钟"的原因。

**常规做法**：要么不整理（历史自由生长），要么同步整理——回答完了用户干等着系统跑 1-3 分钟的总结（V1 的实测教训：耗时变成 2.25 倍）。

**Wovra 的做法**：整理在后台跑，产出三样东西（下一节起逐个讲）：

1. **Normalized 用户输入**（整理后的意图）
2. **精修事件索引**（RefinedIndex）
3. **State Patch**（任务状态增量补丁）

**举例**：一轮 17 步的 ICP 调试（读了源码、跑了测试、失败、改代码、重跑通过），你收到回答后立刻发下一条消息——与此同时后台整理员正在写这一轮的"归档卡片"。等你第 4 轮之后需要用到这轮的浓缩视图时，归档卡片早就写好了。

**优化在哪**：整理是**必须有人做的事**（不整理历史就没法检索），问题只在于"谁等待"。常规让用户等；Wovra 让后台等——而后台有的是时间，因为整理结果最早也要三四轮之后才被用到。

---

## 机制五：Normalized 用户输入——天然的话题索引

**是什么**：整理员把你这一轮（可能是合并的多条）输入，重写成一句**清晰、完整的意图描述**。

**举例**：你断网期间发了"继续"、"(这条没发出去)接着调"、网络恢复后又说"把 ICP 调试完"。整理员合并输出：

```text
Normalized：用户要求继续调试 ICP 配准误差问题（衔接上一轮），
            重点是让失败的测试通过
```

**常规做法**：历史里的用户输入就是你的原话——口语化、碎片化，三轮之后连你自己都要翻半天才知道那轮在干嘛。

**优化在哪**：几十轮之后，判断"哪几轮在聊同一件事"靠的就是这些 Normalized 意图——它们是**天然的话题索引**。原话也全保留着，想要更细就展开看。

---

## 机制六：精修事件索引 RefinedIndex

**是什么**：整理员把本轮**每个事件**重写成一行更短更准的摘要，替换程序机械截断的版本。

**举例**：

```text
Runtime 机械截断（程序生成）：
  [R5-E03] 调用 run_command("pytest tests/test_icp.py") → 失败
  [R5-E04] 调用 edit_file(...) → 成功

AI 精修后：
  [R5-E03] 运行 ICP 测试，3 个用例失败（变换矩阵初值问题）
  [R5-E04] 修改初值估计逻辑
```

**优化在哪**：机械截断只知道"失败了"，不知道"为什么失败"；精修版一行就携带了结论。同样的信息，token 更少、密度更高——这就是为什么它"大多不会触发 120 字截断上限"。

---

## 机制七：Task State 增量补丁——"现在"与"过去"分账

**是什么**：Task State 是一张**任务现状表**：目标、已完成、已决策、已知问题、待解决问题、当前状态。每轮整理时，AI 输出的是**增量补丁**（只说"新增了什么、改了什么"），系统把补丁合并进现状表。

**常规做法**：要么没有任务状态（模型靠翻全量历史猜现状），要么每轮重新总结一份完整状态（每轮重写，容易越写越漂移）。

**举例**：

```text
R5 补丁：known_issues += ["变换矩阵初值估计不准"]
R7 补丁：completed += ["ICP 测试修复"]，known_issues 里那条消失（已解决）

最终 Task State：
  目标：完成 ICP 配准模块
  已完成：ICP 测试修复
  已决策：采用初值估计修正方案
  当前状态：ICP 功能正常，等待联调
```

**优化在哪**：**History 回答"过去发生了什么"，Task State 回答"现在是什么状态"**——两本账分开，各自增长互不干扰。状态表每类上限 200 条，超了淘汰最旧的（被淘汰的内容在历史里永远可查），防止状态表自己变成新的"无限上下文"。

---

## 机制八：分层加载 Assembly——不同年龄的历史不同分辨率

**是什么**：新一轮开始时，系统组装上下文，规则是：

```text
最近 3 轮  → 全部消息原文（正在干的事，一个字都不省）
更早的轮次 → 按预算自动降档：
   档 1：用户原文 + 意图 + 精修索引   （信息最全的浓缩视图）
   档 2：用户原文 + 意图              （预算不够时，去掉索引）
   档 3：一行话题行                   （"R12 ICP误差调试（已完成）"）
```

**预算** = 模型窗口的 30%（1M 窗口 → 30 万 token）。预算装得下就全给档 1；装不下，**最老的轮次先降档**。任何轮次任何时刻都可以用 `expand_history` 升级回高分辨率。

**举例**：68 轮的会话（R1-R3 调 ICP、R4-R6 改 UI、R7 闲聊、R8 起写视觉算法）：

```text
发给模型的上下文：
  系统设定
  R1-R65 的浓缩视图（各几百 token：意图 + 索引行）
  任务状态表（"已完成 ICP 修复、当前在写视觉算法"…）
  R66-R68 的全部原文（最近 3 轮）
  你本轮的新消息
```

**优化在哪**：你最初的需求"前面讨论 UI、闲聊，不应该干扰现在写视觉算法"——在 V2 里 R4-R6 的 UI 讨论只剩三四行"改按钮颜色｜改好了"，闲聊几乎为空。**不是被删除（永远可找回），而是被降到了不干扰的分辨率**。基座稳定在 50K 左右，而全量回放此时已经 770K——这就是 12 倍差距的来源。

## 机制九：上下文布局——变化频率决定位置

**是什么**：前缀缓存按"开头相同部分"打折，所以上下文里各部分的**摆放位置**按变化频率排序：

```text
[1] 系统设定              永远不变  → 放最前（缓存最优）
[2] 历史浓缩视图           闭合后不变 → 放中间
[3] Task State + 降档索引  每轮都变  → 放靠后（它变了只作废它之后的少量缓存）
[4] 当前轮事件             追加式    → 再往后
[5] 新的用户输入           最后
```

**举例（反例）**：如果把 Task State 放在最前面，它每轮都变——50K 的基座**每一步都按全价重算**，成本直接翻 20 倍以上。放到尾部后，它每次变化只作废自己之后的 8-10K。

**优化在哪**：这不是"压缩 token"，是**布局优化**——同样的内容，换个位置，真金白银差 20 倍。

---

## 机制十：expand_history——细节的后悔药

**是什么**：模型发现浓缩视图里的信息不够用时，可以自主调用：

```text
expand_history(ids=["R5-E04"], level="full")   ← 取回某条事件的原文
expand_history(ids=["R1-R3"], level="summary") ← 取回某几轮的意图+索引
```

取回的内容**追加在上下文末尾**（追加不破坏前缀缓存），本轮内一直可用。

**举例**：第 30 轮你问"当初 ICP 的初值是怎么定的？"——第 5 轮的细节早就是一行索引了，模型调用 `expand_history(["R5-E04"], level="full")` 取回当时的完整修改记录，然后回答你。

**常规做法**：截断了就是截断了；或者把所有细节一直留在上下文里（贵）。

**优化在哪**：**历史不进上下文，但仍然可找回**——这是整个架构对用户的承诺。且"取回 = 末尾追加"，缓存零破坏。

## 机制十一：对照组 baseline——80% 阈值压缩

**是什么**：对照组完全按市面惯例工作：所有消息原文追加，当累计输入达到模型窗口的 **80%**（1M 窗口 = 80 万 token）时，触发一次压缩（旧内容压成摘要 + 保留最近两三轮原文），然后继续追加。

**为什么要有它**：没有对照组，你说"我省了 12 倍"没人信——得证明你的对照是"市面上正常工具的真实做法"，而不是故意做得很蠢的稻草人。实测中 baseline 第 4 轮输入就冲到 58 万（逼近窗口），第 69 轮单轮输入 1316 万 token——它就是"不管理会怎样"的活标本。

**优化在哪**：两组用同一套工具、同一个模型，唯一变量是上下文策略——所有差异都归因于机制本身。

## 机制十二：成本三分账——管理机制自己也要被审计

**是什么**：所有 LLM 调用按用途分三个账户记账：

```text
working       干活的钱（回答你、调工具）
organization  整理的钱（后台归档）
compaction    压缩的钱（对照组的阈值压缩）
```

每轮结束的账单一行里全部可见：

```text
耗时 49.0s ┃ 轮次 第1轮 ┃ 输入 6,627 tok（81.8%）┃ 缓存命中 2,816 tok（42.5%）
┃ 等效输入 3,905 tok ┃ 整理 1,794 tok
```

**优化在哪**：V1 实测发现"输入省 32.7%，总成本只省 7.2%"——省下的钱被整理调用悄悄吃掉了。有了三分账，**管理机制自己也在被审计**，这类问题当场暴露而不是积累几个月后才发现。

## 两个完整场景对比

### 场景 A：多话题会话（UI → 闲聊 → 视觉算法）

**baseline**：第 4 轮时上下文里仍是"UI 讨论 + 闲聊 + 算法"的**全部原文**，每一步都带着它们；模型每步都要从无关内容里"穿过"去找相关部分；第 69 轮基座 770K。

**Wovra**：UI 轮次是三四行索引、闲聊几乎为空；模型面对的是"算法相关的浓缩视图 + 最近 3 轮全量"；基座稳定 50K。需要旧细节时 `expand_history` 追加取回。

### 场景 B：第 69 轮的账单（17 步）

| | baseline | Wovra |
|---|---|---|
| 每步发送 | 770-778K | 50-58K |
| 本轮原始输入 | 13,161K | 918K |
| 缓存折算后 | ≈ 446K | ≈ 38K |
| 基座构成 | 全部历史原文 | 全部历史浓缩视图 + 近 3 轮原文 + 状态表 |

## 参数速查表

| 参数 | 默认 | 调它影响什么 |
|---|---|---|
| `WOVRA_MAX_RECENT_ROUNDS` | 3 | 全量原文的最近轮数（Recent Full-Resolution Window） |
| `WOVRA_HISTORY_BUDGET_RATIO` | 0.3 | 历史加载预算 = 窗口 × 比例（决定几轮后开始降档） |
| `WOVRA_CONTEXT_LIMIT` | 1,000,000 | 模型窗口（决定预算绝对值与 baseline 阈值） |
| `WOVRA_COMPRESS_THRESHOLD` | 0.8 | baseline 压缩触发点（× 窗口） |
| `WOVRA_OPEN_ROUND_EVENT_LIMIT` | 50 | 开放轮事件软限制（超出部分折叠为索引） |
| `TRUNCATED_LIMIT` | 120 字符 | 每条索引行的长度 |
| `SAFE_RESULT_LIMIT` | 2000 字符 | 安全阈值 |
| `STATE_LIST_CAP` | 200 条 | 任务状态每类容量 |

## 一段话总结

> **常规工具**：把对话当成一条越写越长的文档，每次全文重发，靠窗口大硬扛，扛不住就一次性粗暴压缩（破坏缓存 + 丢细节）。
>
> **Wovra**：把对话当成一个**带归档系统的工作现场**——现场（近 3 轮）保持高保真；归档（更早轮次）压缩成高密度索引卡；档案室（Full）永不销毁；需要任何细节，报编号即可取回。所有归档工作在后台进行，用户永远不等；所有记账公开透明，机制自身也在被审计。
