# 整理与分裂：现在的流程到底是怎么跑的

> 面向读者：想搞清机制、但不打算逐行读代码的人。写法是"讲人话 + 举例子"，
> 每个结论都能在代码里找到出处（关键处标了 `文件:行号`）。
> 成文 2026-09-14。**同日口径变更**：分裂产物 = 结构树（文件 + 保底块归宿）、
> 只读文件不算活性文件、覆盖缺口行不再注入、是否分裂改由代码按树决定（未实现）。
> §5 已按新口径更新；§2/§3（整理）与 §7（视图）不受影响。

## 0. 一张全景图

```
用户一轮一轮地聊
      │  （每轮 = 一次输入 → 干完 → 回答；轮内按文件切成"块"）
      ▼
   攒着，不急着压                   ← 触发有两道闸门（水位 / 宽限+冷却）
      │
      │ 上下文占用 ≥ 水位（默认 10 万 tok）
      ▼
┌───────────────── 一次维护（一个后台线程，串行两步）─────────────────┐
│  ① 整理（organization）：把全过程"降分辨率"成索引 + 任务账本       │
│  ② 分裂（split）：接着同一段对话问"这摊活能不能分成两条线"          │
└──────────────────────────────────────────────────────────────────┘
      │  产物先**暂存**（pending_org），不立刻替换
      ▼
   下一次"开新轮"的那一刻，产物**生效（promote）**：
   ├─ 轮上的索引/账本换新（此后读的是降过分辨率的历史）
   └─ 注册表登记/更新域 → 生成子 agent → 各 agent 各看各的视图
      │
      ▼
   之后每一轮：主 agent 起手 → 自己答 或 route_to 转交 → 接手方按自己的视图干
```

三个词先记住：

| 词 | 一句话 |
|---|---|
| **整理** | 把一堆轮的全过程，压成"每轮干了什么 + 用户要什么 + 红线 + 任务账本"，**不删事实**（原文按 ID 随时取回） |
| **分裂** | 在同一次维护里问模型："这些活能不能分成互不重叠的几条线？" 能分就建子 agent，各管一摊 |
| **视图** | 每个 agent 实际发给模型的那串消息：系统提示词 + **只属于自己**的历史 + 身份卡 + 运行时信封（待办/传话/账本） |

一个必须先说的口径（用户 2026-09-13 纠正过）：**多 agent 是整理+分裂的自然产物，
不需要"单 agent 溺死"才出现；本质是单 agent 分流（一个主 agent 把活分出去），
不是多个 agent 同步并行。**

## 1. 地基：轮 → 块 → 标签

**轮（round）**：一次用户输入到回答完成。**块（block）**：轮内按**文件**聚合的片段，
纯函数切出来，零 LLM（`blocks/segment.py:202-341`）。块的种类只有四种：

| 块 | 是什么 | 例子 |
|---|---|---|
| `file` | 一个文件在该轮的全部交互（读/写/改/删 + 相关命令） | `R13-B1`（一整轮对某文档的读写） |
| `environment` | 环境准备类命令（装依赖、起服务） | 跑 `pip install` 的那几步 |
| `user` | 轮头**之后**用户的补充/修正发言 | "等等，先别提交" |
| `fallback` | 纯聊天/结论块（这轮没碰任何文件） | "哪个优先？" |

块 ID 形如 `R13-B1`（第 13 轮第 1 块）；事件 ID 形如 `R13-E02`。
**这两个 ID 是"降分辨率不删事实"的钥匙**——整理后历史里只留一行描述，
但想回原文随时能按块 ID / 事件 ID 用 `expand_history` 取回。
首条用户输入不进块，由**轮头**承载：`👤 用户原文 / 🎯 意图 / 📌 关键约束`（`segment.py:241-244`）。

文件状态两档：**LIVE**（写过、现在还在）与 **DEAD**（删了/被取代/测试已清理——不是失败）。
另有"幽灵块"（文件不存在）、"越界块"（被安全层拦了）两类标注（`blocks/labels.py:8-41`）。

**真实例子**（会话 `20260909-181052-orgtest` 的 R13，35 轮里的第 13 轮）：这轮用户问
"对没问题的工具给个评价"，助手读写了一份报告文件 + 最后给了个结论，于是切成 2 块：
`R13-B1`（file 块，29 个事件）、`R13-B2`（fallback 块，结论）。

## 2. 什么时候触发整理

三道判据，全在 `maintenance._maybe_organize_batch()`（`maintenance.py:175-256`）：

1. **水位**：`最近一次装配的 token 估算 ≥ 10 万`（`WOVRA_ORG_WATERMARK`，`support.py:34`）。
   口径是"**下一步请求的窗口占用**"——不是"没整理的东西攒了多少"，也不是累计计费。
2. **宽限 3 轮**：会话最开始 3 轮内不整理（`support.py:30`）。
3. **冷却 3 轮**：距上次"真正整理过"不足 3 轮不整理（`support.py:32`）。
   例子：R35 整理完 → R36/R37/R38 都挡着，**R39 才放行**。

批次 = 所有"已完结但没整理过"的轮，**最老的先整理**，没有批量上限（`maintenance.py:161-173`）。
网页通道（`wovra serve`）每轮结束也会兜底调一次 `organize_backlog()`——其实 `close_round()`
早已把整理排进后台队列（异步、排队即返回，不阻塞对话），那次调用只是兜住"上一批被推迟"
的情形；它**同样过这三道闸门**（`serve.py:565-568`）——这里修过一个真缺陷：早期网页通道
无视水位、每轮都整理，上下文才 1.7 万就被压缩，还每轮打断前缀缓存（实测 org 提示词 22,776
+ split 26,310 tok，`maintenance.py:269-274`）。`force=True`（只在会话收尾/退出时用）才无视闸门。

## 3. 整理：把"全过程"降成"索引"

### 3.1 喂给模型什么

整理调用（`_organize_rounds`，`maintenance.py:515-661`）**不改**已有的对话消息，
只在尾部**追加**一条 `[整理指令]`——这样能骑着前缀缓存问（这是全项目的省钱的根）：

- `[压缩元信息]`：整理范围、LIVE/DEAD 定义、"本视图只降分辨率不删事实"（`prompts.py:187-195`）
- `[分块地图]`：逐轮逐块的标签行（如 `R13-B1【agent-test/tool-layer-audit….md(LIVE,修改)】`），
  连续纯聊天轮会被合并成组（组 ID 如 `R1-2-B1`）（`_block_map_lines`，`maintenance.py:394-513`）
- `[轮↔阶段映射]`：哪几轮属于同一个大步（todo）阶段
- `[格式纪律]`：别用英文双引号、别尾随逗号——实测一次 30,740 字符的产物就因为一个未转义
  引号整批作废（`prompts.py:261-267`）

工具数组与工作对话**完全相同**（不是临时收窄成只有提交工具）——收窄过一版，实测命中率
从 91% 掉到 0.4%，一分钱没省反而更贵，于是改回恒定数组（`support.py:63-90`、`maintenance.py:1225-1247`）。

### 3.2 要模型产出什么

唯一出口是工具 `submit_organization`（`prompts.py:10-185`）：

```
rounds: [
  { seq: 13,
    normalized_user_input: "把用户想要什么说得更清楚"（不是压缩）,
    key_constraints: "红线/硬约束，没有就空",
    block_summaries: [ {id: "R13-B1", summary: "…逐块描述，详略随信息量…"} ],   ← 每块一条、一个不落
    refined_index:   [ {id: "R3-E02", line: "…"} ]                              ← 只在没有块结构的轮用
  }, …
]
state_patch: { completed, decisions, known_issues, open_questions,
               escalations, experiments, closed:[{field, match}],
               current_status, goal, is_done }        ← 合并成一份"任务账本增量"
```

`block_summaries` 的篇幅规则很关键：**标签定分辨率基线，块内实际信息量只做微调**
（`prompts.py:269-338`）——"创建/重构"的块写充实，"读/只读"的块写结论，
寒暄两三行甚至一句。这样"降分辨率"不是均匀砍，而是**把过程压掉、把结论留住**。

**真实例子**（还是 orgtest R13，落库后的形状）：
`block_summaries` 变成一个 {块ID: 描述} 的字典，两条描述是模型真实产出的原文：

> `R13-B1`：用户问对"没问题"工具的评价。我以执行者视角给三档真实体感：真正好用（read_file
> 分页提示"后续还有N行"、delete→restore→move 可逆链、todo 大步=验收单元模型……）；能用
> 但不顺手（run_command 输出超限截断丢中段是最大痛点……）；未能真正测到（notify/consult
> 无第二 agent 只能验证报错、ask_user 需真人）。
>
> `R13-B2`：新增功能建议按价值排序6项：高价值（diff 查看工具、项目结构树、git 封装）……

同一个 round 里的 `user_input.normalized` 是"对没有问题的工具给出评价，判断是否顺手，
并建议还需要给 agent 添加什么功能"——**用户原话（458 字）保留在 `original` 里，
normalized 只是澄清，不是替换**。

### 3.3 出错怎么办（容错链）

整理产物是长中文 JSON，翻车方式很实在，所以有一条四段链（`maintenance.py:82-160`、
`1674-1791`）：

1. **宽松解析**：原样 → 给内容里的引号补转义 → 删非法转义 → 修尾随逗号，逐个候选试；
2. **带诊断重发一次**：把"错在 JSON 第 5,069 字符处"这种现场作为一条消息**追加**回去再问一次
   （追加不重排 → 这次调用照样骑缓存）；
3. 仍失败：**整批判 `failed`，撤掉暂存**——这些轮回到"未整理"队列，下批重做（不是丢弃）；
4. 成功：只给**真拿到产物**的轮打 `done`，代次（`org_generation`）+1。

## 4. 为什么产物不立刻生效：暂存 → 开轮时 promote

一轮跑到一半就换掉它的历史字节，会有两个后果：对话连贯性断了、前缀缓存被打碎。
所以产物先写进轮上的 `pending_org` **暂存**（`maintenance.py:663-763`），
等**下一次开新轮的那一刻**才真正替换（`_promote_org_results`，`maintenance.py:1331-1466`）。

- 谁是"开轮那一刻"：`close_round → _settle_after_maintenance`（主流）、异步维护线程
  收尾（若用户已在轮里则让路）、以及进程重启后第一次开新轮（**崩溃安全**：
  暂存跟着 rounds 一起落盘，重启补生效）。
- 这就是全项目**唯一允许主动破坏前缀缓存的时刻**，代价是实测的一笔：
  一次前缀断裂 ≈ 18,830 tok ≈ **0.0075 元/次**（`economics.py:31-33`）。
- **整理期间用户照常聊天，新输入不压缩**——产物在"没有开放轮"的时刻才落地
  （`maintenance.py::_settle_after_maintenance`，用户 2026-09-11 确认过这个手感）。

**2026-09-14 收口（用户口径：「判定先做、边界才生效」）**：产物就绪时若用户正在轮里，
维护线程**不是白等**——它当场把已闭合轮的归属判定做完（`_prepare_settle_views`，
判据用 `project_merge` 的影子注册表投影：产物还没进注册表，也能按落地后的形状判），
结果先记进轮上的 `pending_view` 预备区。预备区不参与装配，故"一轮内上下文不变"
不受影响；轮边界由 `_apply_staged_views` 一次性生效，带**产物指纹**核对
（`registry.domains_digest`：产物被拒收/换批就丢弃预备值，交给补判重算——预备是
省时间的加速器，不是新的真相来源）。

"有没有开放轮"按 **`current_round` + 盘上最后一轮**两处判（`_open_round_on_disk`）：
serve 是每轮新建 agent，维护线程看不见"下一轮"（它的 `current_round` 恒为 None），
只查自己那份会让产物在**别人的轮**进行中泄漏落地——那一轮下一次落盘（工具卡）会
rebase 合并产物，`latest_domains` 从空变非空，装配在轮中间从全量切到视图路径
（前缀断裂、前后步上下文不一致）。唯一的例外是 `/pending-views` 预览：它是只读
派生（把 `_persist_rounds` 换成 no-op，连盘都不碰），不受轮边界纪律约束。

## 5. 分裂：和整理同一次维护、连着做

### 5.1 为什么连着做

整理刚跑完，那一段对话的 KV 缓存是热的。分裂**纯追加**在整理的对话后面
（整理产物 → split 指令），于是只付自己那 ~1.5K 指令的钱：实测整理命中率 91.1%、
分裂 92.7%（`maintenance.py:658-660、777-778、1225-1247`）。两步串行、各自 try/except，
整理失败就不做分裂（分裂依赖整理质量）；**分裂失败不影响整理产物**（`_parallel_maintenance`，
`maintenance.py:1215-1329`）。

### 5.2 喂给模型什么（硬数据，零 LLM 现算）

- **LIVE 文件清单**：非 DEAD 且**被写过**的文件，带写/读次数与块引用（`_split_hard_data`）
- **分块地图**（同上）+ **纯对话块占比**：按块内事件字符数算，"约 X%"直接写进指令
- **逐层视图体量与自身水位比**：对每个候选域**真装配一遍**、量 token，和 10 万水位比，
  输出"已到自身水位 → 可以在它内部再裂一层 / 未到水位"（装配口径，`maintenance.py:1498-1580`）
- **覆盖缺口**：哪些文件没有任何域认领、哪些轮被多个域共命（分域过细的信号）

### 5.3 要模型产出什么（2026-09-14 起：一棵**结构树**）

工具 `submit_domains`（`prompts.py`）——模型只负责"把活性文件理成树、把附属物
挂上去"，**不判断分不分**：

```
domains: [{ name, description, parent,
            file,                     ← 叶子：一个活性文件的**编号**（L00、L01…）
            chat_block_ids,            ← 挂本节点的保底块
            user_block_ids,            ← 挂本节点的用户块
            history_files,             ← 非 LIVE 文件的**编号**（H00、H01…）
            file_notes?, constraints, goal,
            block_ids }                ← 例外声明用；文件块按叶子自动归属
unassigned: { block_ids, reason }      ← 与任何工作线无关的块（归主 agent）
```

**文件用编号、不写路径**（2026-09-14 用户思路）：硬数据每行形如
`L03 = system-prompt-content-review-20260909.md`（活性）/
`H07 = testlab/renamed.txt`（非 LIVE）。编号只是**模型侧的引用符**——
Runtime 在提取产物后**立刻翻译回真路径**，下游（注册表/视图/前端）看到的
仍是路径，零兼容负担。好处：路径拼写差异在源头消失、输出更短、还能机械
校验（编号未知 / 把 H 填进叶子 → 带诊断重发一次，仍错则整批回入水位）。
**块 ID 同样受校验**（2026-09-14）：`block_ids` / `chat_block_ids` /
`user_block_ids` / `unassigned` 里出现[分块地图]中不存在的 ID（含合并组编号
如 `R19-24-B1` 是合法的）→ 判错 → 带诊断重发一次 → 仍错整批回入水位——
此前这类抄错是静默的（那块没被认领、兜底归主 agent，只能靠人对数）。

树形照项目实际组织结构分层，**叶子 = 单个活性文件**（示例：
`项目架构 → 核心业务层 → 接口与控制器 → 路由文件 → 用户路由.ts`）；
非 LIVE 文件、保底块、用户块挂在对应节点（通常叶子）下面。`file` 路径**逐字抄
硬数据里的活性文件清单**（Runtime 按字符串核对归属；抄成 `agent-test/xxx.md`
而块里是 `xxx.md` 会被判成漏项）。没有 `split_assessment`——"可分性判定"不再
由模型给（改由代码按这棵树决定，落地判定**尚未实现**，先把结构交出来）。

### 5.4 模型侧规则（`_SPLIT_INSTRUCTIONS`）

1. **文件成树**：活性文件按**功能语义**聚合成树（parent 表达层级）。**不是按路径**——
   同目录可属不同节点、不同目录可属同一节点；路径只是线索。
2. **保底块定归宿**：纯聊天/结论块逐个判——真在讨论某节点事务的 → 该节点
   `chat_block_ids`；寒暄/身份确认这类没落到文件工作上的 → `unassigned`（归主 agent）。
   一个不落、不许重叠。
3. **结构稳定 + 粒度**：同一批数据两次分析应给出同构的树；节点 = 可独立推进/交付的
   工作单元，不是"每类文件一个节点"；节点描述必须写满三件（干什么+产出什么／
   边界（什么不归我）／什么信号该找我）——它是跨 agent **唯一的公共信息**。

**非 LIVE 文件（只读/被删/被取代）不占分裂单元，但必须挂满**（2026-09-14 用户口径）：
* 硬数据里它们**单独一段列出、逐条不落**（不看磁盘是否存在——"磁盘上没了不等于没用：
  临时测试脚本验过什么、结果如何，是后面装配上下文要用的结论"）；
* 每个非 LIVE 文件必须出现在某个节点的 `history_files` 里（挂到相关叶子下）；
  **漏一个 → Runtime 拒收整批**（与活性文件漏认领同级的硬闸门，回入水位下批重做）；
* 只读文件仍然**不算活性**：不进活性文件清单、不计入数量（"压缩后真正干活还需要重新读"）。

**输出精简**：文件块按 `files` 自动归属，不必逐块列 `block_ids`——只列例外
（跨节点块、与文件归属不符的）。

### 5.5 Runtime 侧的硬闸门

- **归属完整性**：每个**活性文件**（被写过且现在还在）必须**恰好**落在一棵树的
  一个节点里（不许重叠、不许遗漏）——落地前 `registry.split_defects` 会拒收违规
  产物（`maintenance.py`）；只读文件不在校验范围内（2026-09-14 口径）。
- **覆盖缺口硬数据**（"N 个文件未落在任何域"那句）：2026-09-14 用户判定"多余且
  错误"，**已不再注入模型输入**；漏项改由 Runtime 机械校验并报错。
- **主 agent 不许有文件**（用户 2026-09-13 口径）：分裂完若还有文件块"没域认领、
  连它所在轮也没归域"，直接抛 `SplitCoverageError` **中止**，整批**回入水位**下批重做
  （`maintenance.py:950-985、1304-1312`）。为什么要回滚而不是记一笔：整理那一路此刻
  已经把这些轮标成 `done` 了，只记一笔的话它们**永远不会再被分析**。
- **归属结算 + 互斥体检**：promote 时先做落点预演，一个文件只能属于一个域；
  重叠即拒收（F2 闸门）；再把产物认领的文件从旧条目（**含主 agent**）手里减掉
  （`registry.settle_ownership`，`registry.py:449-498`）。

**真实例子 A：一次"不可分"判定**（orgtest 的 R13 产物，模型原话）：

> `splittable: false`，理由——"现状仅 1 个互不重叠的活性文件域：所有产物（4 份文档 +
> 压缩快照）都落在 agent-test/ 目录，性质同为文档产出，文件域重叠。话题虽多
> （工具测试/提示词评判/机制深读/成本讨论）但按判据'话题不同永远不构成分裂理由'，
> 不构成独立文件域……预测不分裂已兑现：集中会话不分，分裂判定逻辑工作正常。"

这就是"**按文件域分，不按话题分**"的现场：聊了很多主题，但文件就一摊，所以不分。

**真实例子 B：一次成功分裂的前后**（worklog §101 记录的实测会话 `20260913-175945-533c5d`）：

| 指标 | 修前 | 修中 | 修后 |
|---|---|---|---|
| 未覆盖文件 | 28 | 7 | **0** |
| 主 agent 桶里的块 | 32 | 7 | **空** |
| 主 agent 材料（装配口径） | 6,674 tok | 2,085 | **1,130**（只剩路由+兜底） |
| 那个域自己的视图 | 7,283 | — | **12,235** |

"没膨胀"的原因：主 agent 让出去的是**别人的文件史**（历史文件并入了所属域），
不是凭空多出来的。

## 6. 生效那一刻：注册表与"分家"

promote 时（`maintenance.py:1331-1466`）：校验 → 落注册表 → 归属结算 → 记录生命周期。
注册表条目长这样（本地真实数据）：

```json
{"id": "Main", "name": "主agent", "description": "全局协调与未归属事务",
 "files": [], "status": "active", "inbox": []}
{"id": "A", "name": "agent-test 文档产出域（Wovra 工具层测试与评价）",
 "goal": "系统性测试 Wovra 工具层……", "constraints": ["只读/只在 agent-test 工作区内操作", …],
 "files": ["agent-test/tool-layer-audit-20260909.md", …], "status": "active", "inbox": []}
```

- **ID 体系**：主 agent 恒定 `Main`；顶层域 A、B、C…（第 27 个起 AA、AB…）；子域 `A-1`、`A-2`。
- **status**：`active` = 名下已有命中轮；`dormant` = 登记了但还没轮到它干活
  （`split_lifecycle.py:49-117`）。主 agent 恒 active。
- 子 agent 再分裂 → **两级替换**：产物里的 `split_parent`（这批轮里出现最多的非主
  `active_view`）在落地时作为 `parent_id` / `retire_id`——新子域进来、老域退休，
  `land` 按 id 复用对象，避免"僵尸引用"（`registry.py:530-601`）。

## 7. 分家之后：每个 agent 看到什么

### 7.1 视图的四段结构

装配时现场派生（**视图字节不落盘**——同一份 rounds+registry 重放必得同一串字节，
持久化的只有一个 `active_view` 标记；`agent/assembly.py:276-411`）：

1. **system**：公共人设 + `[全局职责表]`（所有域的"职责说明书"摘编——跨 agent 唯一的公共信息）
2. **本视图历史**：只遍历**命中本域**的轮。每轮两条消息：
   `user` = 轮头（👤用户原文 / 🎯意图 / 📌关键约束）+ 该轮用户块；
   `assistant` = 本域的块描述。**一块都没命中的轮，整轮不出现**——只在一条都没有时给一行
   `[本视图历史]（无——本域尚无命中轮）`
3. **身份卡**（user 角色一条）：`[当前身份] A（域名）：职责/目标/约束/文件域…`
   并写明"你只看到属于自己这摊活的历史与账目……文件系统是共享的"
4. **运行时信封**（绝对尾部，`<runtime-reminder>`）：主 agent 才有 `[路由建议]`；
   外加 待办阶段行、`[传话]`收件箱（最多 8 条，送达即清）、`[本域账本]`（按文件域切片的
   任务账本，全局节永不切）

**真实骨架**（orgtest 的 A 视图，共 4 条消息、6,452 字符）：

```
[0] system : 你是 Wovra 的执行助手……（公共人设）
[1] user   : [本视图历史]（无——本域尚无命中轮）        ← 产物已登记、但那些轮还没标成"命中 A"
[2] user   : [当前身份] A（agent-test 文档产出域…）：目标：系统性测试 Wovra 工具层……
[3] user   : <runtime-reminder>[本域账本]（按文件域切片；全局节永不切）目标：…… 现状：……
```

### 7.2 归属：一个块算谁的

**分工（2026-09-14 用户口径）**：模型只负责**关系**（不相关的隔开、相关的归成
一条线），**归宿由代码算**——是否分裂、在哪一层分裂、每个节点/块最终归哪个
agent，都由 Runtime 按树机械决定。

`views.ownership()` 按序：

0. **树里显式挂载的块 → 树说的那个节点**（模型给关系、代码翻译成归宿；
   `main_agent` 桶节点 → 主 agent）。树没覆盖的**新块**才继续往下判
   （渐近归属：等下一次分裂再入树）；

1. 环境块 → 主 agent；
2. 文件块 → `file` 落在某域文件集合里就归它（文件集合 = 活文件 + 老目录前缀 + **历史文件**，
   最长匹配优先）；
3. 文件块没被任何域认领 → **跟这一轮的归属走**（轮的 `active_view` 早就定了，
   文件块不该另起一套规则——2026-09-13 用户口径）；
4. 其余（用户块、连轮也没归域的文件块）→ 主 agent。判据 4 的文件块 = 分裂漏认领，
   落地时会直接报错（§5.5）。

**用户块**归属记在主 agent 名下，但渲染时**随命中轮进域视图**——所以子 agent 也看得到
"用户当时是怎么说的"。

### 7.3 折叠：老历史变一行

每个视图按**自己的代次水位**折叠（`views.py:82-116`）：保留最近 3 代（`FOLD_KEEP_GENERATIONS=3`），
更老的块描述折成：

```
涉及文件：src/a.py、src/b.py（已删）
（N 块细节已折叠：R3-B1、R3-B2…——块 ID 保留，按轮号或块 ID expand_history 可展开本轮）
```

两条纪律：**折叠只改渲染文本、不改归属**；**块 ID 一律保留**——没有 ID，原文就取不回来了。
用户块永不折叠。

### 7.4 路由与协作（分流，不是同步）

- 现行流程**恒由主 agent 起手**：规则层（文件命中/粘滞/兜底）只写一个 `[路由建议]`，
  主 agent 看完可以自己答，也可以 `route_to` **转交**（`routing.py:142-200`、`core.py:387-434`）。
- `route_to` 会拒绝：转给自己、转回当前视图、跳数 >3。成功后在**工具批次跑完**才真正换手
  （避免一批工具上下文错乱），接手方看到的当前轮会剥掉路由步骤、补一条 `[回合内转交]` 尾注
  （`ledger.py:370-431`、`core.py:808-845`）。
- 子 agent 之间默认**互相看不见**（别人的块描述/ID 在本视图字节里一次都不出现）；
  要沟通走三个工具：`notify`（单向留言）、`consult`（双向问一次，答案直接流进用户窗口）、
  `join_with`（会合，机械排队交棒）。用户插话默认广播给本轮参与者，`@X` 只投给 X。
- **异步窗口里到达的轮**（产物还没生效、只能先判给主 agent 的那些）：产物一生效就按
  同一套规则**补判归位**（`_settle_views`：零 LLM，只写落点、不改消息字节、不重做活；
  已归域的轮不被反复推翻）。补判可以提前做（§4 的预备归属），但**生效一律在轮边界**。

## 9. 诚实的边界（现在没做的）

写文档不能只说好话，以下是当前代码的真实边界：

1. **15% 聊天门槛没有代码级闸门**：`_SPLIT_CHAT_MERGE_RATIO` 只以 docstring 存在，
   真实执行是"把占比当硬数据喂给模型 + 指令里说'残留不算节点'"——判在模型侧。
2. **`splittable:false` 不阻断注册表落地**：`split_assessment` 会落到轮上供人看，
   但 promote 不因它拒收（域树该落还是落）；就是说它目前是"分析结论"，还不是"闸门"。
3. **经济算式只算不拆**：`economics`（`(B−B′)×N−C`）与 `split_lifecycle` 只把
   "值不值得"记进历史，不自动触发拆分（`economics.py:10-12`）。
4. **一个 LIVE 文件可以自成一域，但不能拆到块**——最细粒度到此为止。
5. **视图字节不落盘**：靠确定性重放。好处是不会出现"盘上的视图和代码算的不一致"，
   代价是每次装配要重算（毫秒级）。
6. 折叠保留 3 代是"经验值"，不是算出来的最优。

### 一页话总结

**攒轮 → 到水位 → 一次维护（整理降分辨率 + 分裂分家）→ 暂存到下一轮开轮才生效 →
主 agent 起手、按职责表分流给子 agent，每个 agent 只看自己那摊。**
整理不删事实（ID 保留、原文可取回），分裂按**文件域**不按话题，产物**先暂存后生效**
（保护连贯性与缓存前缀），Runtime 用机械校验守住"文件不许重叠、主 agent 不许有文件"两条底线。
