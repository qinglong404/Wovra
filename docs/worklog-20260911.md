## 3 备份与回滚手段（已就位）

1. **git（主手段）**
   * 备份点：`baseline-v3-20260911` tag = 本轮改写前的锚点；
   * 普通回滚：`git revert <commit>`（保留历史，安全）；
   * 强回滚：`git reset --hard baseline-v3-20260911`（丢未提交改动，慎用）；
   * 远端异地备份：`git push origin main --tags`（需用户确认，本轮未做）。
   * 注意：`git tag/commit/push/reset/clean/checkout/restore` 均命中
     **敏感操作确认门**（shell.py `_confirm_reason`）——交互环境 y/N
     授权一次，非交互环境自动放行但写审计记录。
2. **文件级 checkpoint（无 git 也能后悔）**
   * 每次覆盖/编辑/按行替换/删除前，旧内容自动归档到
     `.wovra/history/<相对路径（/ → __）>/<时间戳>.bak`；
   * 每文件保留最近 10 份，`restore_file` 列出并回滚；
   * 回滚本身也归档（回滚可再回滚）；界外授权文件不纳入归档。
   * 实测记录见 §4。
3. **会话级持久化**：`tasks/<id>/task.json` 每轮落盘，
   `.lock` 保证单写者；中断/异常轮保持开放（`\c` 可续跑）。

## 5 运行期发现（本轮未修，待决）

**P2（可用性/安全）确认门在子进程里会静默挂死，且可能"盲授权"。**
机理：交互/非交互判定看的是**调用方进程的 stdin**——
* Wovra 主进程内（工具函数就地执行）`sys.stdin` 非 TTY → 确认门
  **自动放行**、越界授权门**自动安全拒绝**；
* 我经 `run_command` 起的**子进程**继承真实终端 stdin → `isatty()=True`
  → 子进程内部再弹 y/N 会真的阻塞等输入，而**提示写在被重定向的输出里、
  用户屏幕上看不到** → 表现为"命令卡死到超时强杀"。
风险面：用户此时在终端敲的任何字符会被那个 `input()` 吃掉——若恰好
是 `y` 就等于**在看不见提示的情况下授权了界外访问**。

**P3（仪器保真）探针在 Windows 上对 `known_leak` 项给出假"已拦住"。**
`shell:python拼路径` / `shell:python拼文件名` 两条在 Windows 上因
`python3` 不存在 → 命令直接失败 → 无金丝雀 → 判定"已被拦住"，探针
还提示"加固生效，请摘掉这些标记"——**照办会让 Linux 侧变红**。
blocked 组普遍存在同类假通过（命令不存在 ≠ 拦截生效）。

验证：`uv run --no-sync python -m pytest -q` → **324 passed**；
探针第一层（`< nul`）→ **73/73**。

**三条实测事实（都是本轮量出来的，不是推断）**

1. **Wovra 主进程内** `sys.stdin.isatty()` = **False**（chat 下）→ 会话内
   工具的确认门自动放行、越界授权自动安全拒绝。反证：`git tag` 命中
   确认门却 0.0s 通过（`_confirm_reason` 实测确实命中）。
2. **子进程继承终端时** `isatty()` = True → 子进程内部的 `input()` 真的
   阻塞（探针挂死 240s 的直接证据）。
3. **Windows 下 NUL 设备（`< nul` 或 `DEVNULL`）的 `isatty()` 仍是 True**
   （实测 `isatty_nul= True`）→ 修复后 Windows 上子进程内的门走
   "打印提示 → input() 立即 EOF → 拒绝"；而 Linux（/dev/null → isatty
   False）走"静默自动放行"。**跨平台行为不一致**，见待决 C'。
