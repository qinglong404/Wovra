## 5 运行期发现（本轮未修，待决）

**P2（可用性/安全）确认门在子进程里会静默挂死，且可能"盲授权"。**
机理：交互/非交互判定看的是**调用方进程的 stdin**——
* Wovra 主进程内（工具函数就地执行）`sys.stdin` 非 TTY → 确认门
  **自动放行**、越界授权门**自动安全拒绝**；
* 我经 `run_command` 起的**子进程**继承真实终端 stdin → `isatty()=True`
  → 子进程内部再弹 y/N 会真的阻塞等输入，而**提示写在被重定向的输出里、
  用户屏幕上看不到** → 表现为"命令卡死到超时强杀"。
风险面：用户此时在终端敲的任何字符会被那个 `input()` 吃掉——若恰好
是 `y` 就等于**在看不见提示的情况下授权了界外访问**。

**P3（仪器保真）探针在 Windows 上对 `known_leak` 项给出假"已拦住"。**
`shell:python拼路径` / `shell:python拼文件名` 两条在 Windows 上因
`python3` 不存在 → 命令直接失败 → 无金丝雀 → 判定"已被拦住"，探针
还提示"加固生效，请摘掉这些标记"——**照办会让 Linux 侧变红**。
blocked 组普遍存在同类假通过（命令不存在 ≠ 拦截生效）。

## 9 越界守卫缺陷（2026-09-11 20:0x–20:4x）：开关被当路径 → 盘根进授权清单

### 9.1 触发：用户在真实终端裸跑探针，得到 5 条失败

用户报告：`uv run --no-sync python experiments/security_probe.py`
（真实 TTY，**对每个授权询问答 Y**）→ 第一层 68/73，5 条失败：
`read:界外链接`、`search:起点链接`、`write:链接穿透`、`replace:链接穿透`、
`shell:覆盖重定向`。

**判定：不是新洞，是"用户授权"的后果**——这 5 条的越界目标（界外链接的
真实目标 / 界外目录）被用户当场授权（清单落盘、重启仍在），授权门放行
之后探针自然报 LEAK。**仪器把"人愿不愿意授权"与"边界拦不拦得住"混在
一起了**，这一点是探针的判别力缺陷（已修，见 9.3-E）。

### 9.2 顺藤查出的三个**真缺陷**（都在守卫自身）

实测（`output/_detector_probe.py` 一次性诊断，跑完即删）：

| 命令 | 修复前判定 | 问题 |
|---|---|---|
| `dir /s /b .wovra` | 越界（目标 `/s`、`/b`） | **cmd 开关被当成绝对路径** |
| `timeout /t 25 /nobreak` | 越界（`/t`、`/nobreak`） | 同上 |
| `cd /d D:\BC\Wovra` | cd 越界（目标 `D:\d`） | 同上（`/d` 被当 cd 目标） |
| `find / -name x` | 越界（`/`） | 正确，但**弹授权询问** |

**后果（实锤）**：本工作区 `.wovra/authorized-paths.json` 被写进
`["D:\\d", "/t", "/nobreak", "/s", "/b", "D:\\"]`——**最后一条是盘根**。
实测：

```
is_authorized('D:/Windows/win.ini')             -> True   ← 整块 D 盘放行
is_authorized('D:/some-other-project/secrets.txt') -> True
```

即：一条垃圾条目让**工作区边界实质失效**（此后 `dir /s /b` 这类命令
再也不会被拦——`/s` 落在 `D:\` 之下，授权检查直接通过）。

三个缺陷：
* **D1 误报**：cmd 开关（`/s /b /t /nobreak /r /d`）被判成界外绝对路径
  → 合法命令反复弹授权询问；
* **D2 超授权**：根目录/盘根可被授权（`Path("/").resolve()` 在 Windows
  = 当前盘根），一条 Y 即放行整块盘；
* **D3 持久污染**：授权清单落盘且无人清理，垃圾条目长期有效。

### 9.3 修复

| 项 | 改动 |
|---|---|
| **D1** | `safety._is_cmd_option()`：单字母 `/X` 或已知多字母开关（`nobreak`/`recurse`/`pid`/`im`/`ad`…）不当路径；真实路径（`/etc`、`/tmp`、`/usr/bin`）照旧受检 |
| **D2** | 新增 `_is_fs_root()` + `_normalize_auth_targets()`：授权目标一律解析为绝对路径，**根目录/盘根直接驳回且不询问**（问了也只能答不）；`add_authorization` 同样拒绝写入；`shell.run_command` 用 `auth_rejection_note()` 把驳回理由说给模型/人听 |
| **D2'** | `is_authorized()` 防御性过滤：清单里**已存在的**根目录条目一律不作数——边界不能被一条脏条目作废（旧文件、手工编辑、降级都挡住） |
| **D3** | 本工作区清单已清空为 `[]`（实测 `is_authorized('D:/Windows/win.ini')` → False） |
| **E 仪器** | 探针 `main()` 调 `_declare_noninteractive()`（`os.environ.setdefault(WOVRA_NONINTERACTIVE, "1")`）：**自动仪器永不问人**，授权门一律安全拒绝 → blocked 组测的才是真边界 |

### 9.4 测试自足性（本轮踩到的第三个坑）

## 10 P3 + P4：未测到判定与原生输出解码（20:5x–21:1x）

### 10.1 P3：命令没跑起来 ≠ 被拦住

**症状**（用户裸跑输出）：两条依赖 `python3` 的 `known_leak` 用例在
Windows 上被判"已被拦住 → 标记可摘"，探针还汇总提示"加固生效，请摘掉
这些标记"——**照办会让 Linux 侧变红**（假信号）。

**根因**：判定只看"有没有金丝雀/界外素材有没有变"。命令因解释器不存在
而直接失败 → 没有金丝雀 → 被判"拦住了"。命令没跑起来时，"没泄漏"根本
不是拦截生效的证据。

**修法**：`Finding` 增 `inconclusive` 字段 + `_not_executable()` 判定；
命中即标"未测到（命令在当前平台不存在）"，**不进**"可摘标记"清单，
报告单列一行"未测到"，结论里分开计数。

**实测补充**：本机 cmd.exe 对不存在的命令返回 **exit_code=1**（不是
9009，探针早前那条 9009 来自不同调用路径）——**不能靠退出码判定**，
只能靠输出文本。这条直接引出 P4。

### 10.2 P4（新发现）：原生程序输出被按 UTF-8 解码 → 乱码

查 P3 时发现：`definitely-not-a-command` 的报错回传是**乱码**
（`'x' ���������...`）。原因是 `run_command` 按 `utf-8, errors="replace"`
解码，而 cmd.exe 内建报错按 **OEM 代码页**（本机 cp936）输出——原有的
`PYTHONUTF8=1` 只约束 Python 自己，管不住 cmd.exe 与大量原生工具。
影响：**模型看不到命令失败的真实原因**（只能看到乱码），本项目的
"失败要可诊断"直接受损；探针的文本判定也失效。

**修法**：`shell._decode_output()` 先按 UTF-8 严格试，失败再用
`_oem_encoding()`（Windows 走 `GetOEMCP()`）解码；`background.check_background`
的日志读取复用同一函数。

**实测**：

```
uv run --no-sync python -c "from wovra.tools import run_command; print(run_command('definitely-not-a-command-wovra-xyz'))"
→ stderr: 'definitely-not-a-command-wovra-xyz' 不是内部或外部命令，也不是可运行的程序或批处理文件。   ← 可读了
```

### 10.3 验证证据

```

uv run --no-sync python experiments/security_probe.py          → 0.6s

  ❔ 5 条未测到（命令在当前平台不存在，既非通过也非失败）：
```

### 11.8 未转义引号 → 改为**代码自动修复**（20:5x，用户提问触发）

用户提问：*"这种转义，我不能用代码直接给替换了再解析吗？这样不简单的多？"*
——此前 §11.4 的判断"有歧义、不猜"过于保守：**局部上下文足以判定，且解析
本身就是校验**，猜错不会被采纳。

判据（`_requote_json()`，纯结构、零 LLM）：串内的一个英文双引号，右侧第一个
非空白字符若属于 `: , } ]` 则是**结构引号**（键/值收尾），否则是**内容引号** →
补 `\`。`\` 开头的既有转义序列整体跳过。

策略化解析（`_json_candidates()`，**最小干预优先**）：原样 → 结构引号修复 →
非法转义修复 → 两者叠加 → 各自再加"尾随逗号修复"；每档再试严格/宽松。**先试
干预最少的**，避免"本来能解析却被改坏"；**解析通过才采纳**，修不好就退回
§11.5 的带诊断重发。

诚实边界（写进 docstring 与测试）：正文里"引号紧跟逗号"（`他说"好",然后`）在
文本层面是真歧义 → 修不了 → 该候选被弃用 → 走重发。所以本修复只提高命中率，
不承担正确性；两个原用例因此改写为歧义样本（自动修复救得活的样本另立正向用例
`test_org_auto_repairs_unescaped_quotes`）。

留痕：自动修复成功也写 history（`org：模型产物畸形，已自动修复（结构引号修复）`），
用于判断"要不要把提示词护栏（§11.6 (a)）前移"。

验证：`uv run --no-sync python -m pytest -q → 338 passed`（新增 1 条正向用例，
改写 2 条原用例为歧义样本，仍锁住"重发有界"与"失败留痕"）。

### 11.10 整理产物"部分覆盖"被当成整批成功（21:1x，机制评审中发现并修复）

**症状**：`_organize_rounds` 只判 `staged == 0` 为失败，之后**无条件对全批**
打 `org_state = "done"`。当模型少输出一轮（`seq` 匹配不上剩余的轮，而位置兜底
又要求 `len(items) == len(rounds)`），那一轮既没有块描述、又被标 done。

**后果**（比"失败"更隐蔽）：该轮视图降级成事件索引（块描述全空），且因
`org_state="done"` **永不再整理**——判断它"还需要整理"的 `_unorganized_rounds`
只收 `org_state != "done"` 的轮。`\maint` 上显示 100% 已整理，账面完美，
内容却缺了一半。

**实测复现**（零 LLM 脚本，自包含 stub）：


**修复**：逐轮判定——只有**真拿到产物**（`pending_org` 非空）的轮才 `done`，

history（`org：产物只覆盖 2/3 轮，R[3] 未收到产物…`）。

修复后同一复现：`R3 org_state='failed' pending_org=无`，done 的轮与有描述的轮

## 14 口径更正：「不做 todo_write」写宽了（2026-09-11 用户拍板）

且原文档 §3 的四条理由**恰恰都被大步/小步制规避掉了**：

| §3 否决传统 todo 的理由 | 大步/小步制如何规避 |
|---|---|
| 清单写下就积累权威，现实偏离后仍倾向 tick | **深度恒 1**：只存当前大步，验收通过才允许写下一个 → 方法层没有长期权威可积 |
| 写时固化判断（用最少信息赌全过程） | 大步 = **一次可验收的增量**；验收即轮边界，粒度由 acceptance 倒逼收窄（硬上限 3 条） |
| 退化成"一个任务拆几步"的平铺清单 | **结构闸门**：未拆过小步 / 带未完成小步 → verify 拒绝（E/F 组实测 8 阶段 0 小步，不加门会被跳过） |
| 事后账本（TaskState.completed）与事前处方混淆 | 二者分家：`verify_milestone` 把**事实+证据**写进 `TaskState.completed`，todo 本身关掉即清 |

结论：**唯一的差异在"许不许累积"，不在"有没有清单"。** 深度恒 1 就是
防累积的结构；平铺清单的病灶是无限累积的权威。

## §15 P0：状态渲染预算截错了对象（2026-09-11，R9 自埋回归的修复）

> **对 §14.3 的更正**：该节最后一项实测写的是
> `render(8000) = 8,012 字符，含"(任务状态过长已截断)" → 超长截断保护不再是死代码`。
> 结论**只对了一半**：保护确实激活了，但它**截错了对象**，且方向反了。
> 以本节为准。

### 15.1 症状（人机协同回路正在实时受损）

用户问"后面该干嘛"时取证查出：装配处传给 `render` 的 `budget=8000`，
旧实现是 `text[:budget]` 整块尾部切片——**保头部**。而节的输出顺序是
`目标 → 现状 → 已完成 → 已决策 → 已知问题 → 待解决问题 → 决策升级 →
待办实验 → 约束`。活会话实测（2026-09-11，c34bc5）：

```

决策升级 7 条 → 可见 0 条     ← 人机协同一等公民，且无第二注入点
待办实验 13 条 → 可见 0 条    ← 同上
```

后果三重：

1. **截错对象**：决策升级与待办实验是文档（organization-runtime-v1.md）
   写明的一等公民、**没有第二个注入点**，被整节吃掉即彻底不可见——
   需要人拍板的事（如"轮换 .env 的 API key"、"裁定 next-stage-intent
   与 todo 账本的关系"）模型永远读不到，协同回路单侧断掉；
2. **方向相反**：截断保最旧，而 `apply_patch` 的容量淘汰是 `del merged[:len-CAP]`
   ——丢最旧留最新。两头口径打架：越陈旧的越容易被模型看见；
3. **花钱喂最不重要的节**：`completed` 实测单节 9,356 字符已超 8,000 预算，
   而它恰恰是档案价值最低的一节（原文在 history 与 report.md 里），
   关键三节合计仅 1,833 字符却全被挤掉。

根因定性：R9 的初衷（让 `render` 里形同虚设的截断保护真正生效）没错，
**错在把全局字符切片用在结构化账本上**——节的语义价值不同，不能用
同一把尺子从头量到底。

### 15.2 修法（task.py，纯函数级改动）

`TaskState.render(budget)` 从"整块切片"改为**按节分配**：

* 新增 `_STATE_SECTION_ORDER`（输出顺序）与 `_STATE_SECTION_PRIORITY`

* 新增 `_section_need()`（一节完整渲染的字符数）与 `_fit_section()`
  （在配额内保留**最新**条目、至少保一条、返回 `(文本, 省略条数)`）；
* 被裁条数写进标签：`已完成（前 27 条已省略，见 report）：…`——

  字节起就不匹配**——工作调用辛苦建立的整段前缀对维护调用全部作废，与
  "输入是不是整理产物"无关。这正是当初 0.4%/0.3% 的成因，也是 R11 复议
  结论"收窄这笔交易不划算"的物理基础。
* **纯追加继承确实按设计工作**（实测证据）：split 的 `cached=98,944` ≈
  org 的 `prompt=98,954`——org 那一整段几乎 **100% 被 split 继承**，split 只付
  自己新增的 **7,770 tok**（分块地图 + 分裂指令）。用户说的"纯追加应该高"成立。
* **残余 ~9% 是固有成本，压不掉**：维护调用是"冷启动插入"，一次付掉整个
  尾部信封（TaskState + 文件地图 + todo，实测 8K 级）+ 整理指令与分块地图，
  这些 token 对本进程而言必然是新 token。working 能到 97.3% 是因为它每步
  只付"一步增量"，而维护调用一次付整段新增。

## §17 修 400：维护快照的协议闸门（2026-09-11，§16.4 的落地）

§16.4 只做了取证与定性，两件事留待拍板：机理已复现、修法候选 (a)/(b)/(c)。

### 17.1 根因（一句话）

`close_round()` 末尾就做水位检查并取装配快照，而 **close_round 会被工具
方法体内部调用**——`todo(action="verify_milestone")` 的流程是
"标记轮 completed → close_round() → 开新轮写运行时说明"。此刻**这条 todo
调用的 tool 结果事件尚未落盘**（结果要等工具返回后才写进轮次），于是快照
尾部是"未被回复的 `assistant(tool_calls=['todo'])`"；整理指令再以 user
消息追加到尾部 → 严格端点立刻 400。

## §19 缓存断裂定价与前缀布局实测（2026-09-11，用户拍板"先把1做了吧"）

到底花多少？② 分裂后三类视图各自能共享多少前缀？③ 用户提的两种排法

### 19.2 方法（零 LLM，全部本地）

* 数据源：`tasks/*/task.json` 的 `history` 里 `kind="llm_call"` 记录（形如
  `[working] prompt=… cached=… miss=…`）。可用会话只有三个有记录：
  `20260909-181052-643355`（144 次 working）、`20260911-190158-c34bc5`

  调用**。
* 断裂检测：`prompt[i] < prompt[i-1] × 0.8` 即判断裂。依据是**只有 promote
  （整理生效、历史被压缩）能让装配体量骤降**；不依赖对 promote 时间点的
  猜测，用数据自己说话。
* 视图测算：把活跃会话 `c34bc5` 的 `task.json` 复制到 `tasks/` 下临时目录

### 19.3 实测一：每批一次断裂的定价

**结论（三条）**：

1. **断裂很稀**：9 次 / 840 次工作调用 = **每 93 次一步**（每批整理 3 轮、
   每轮十几步，与"每批一次"吻合）。
2. **断裂很便宜**：断裂步平均 miss 23,269 tok，扣掉非断裂步 miss 中位数

   计：**全部 9 次断裂合计 ≈ 0.068 元，平均每次 ≈ 0.0075 元**。
3. **断裂后会真恢复**（不是百分比幻觉）：看绝对 miss——距断裂 0/1/2/3/4/5+
   步分别为 19,938 / 12,807 / 8,488 / 6,308 / 6,956 / 4,729 tok。绝对量
   3–4 步内收敛回常态（早期几步偏高的原因是新前缀还短、尾部信封占比大，
   属"分母效应 + 逐步重建"，不是机制没恢复）。

**对布局决策的含义**：要复用旧前缀就得保留旧字节（放弃压缩），要压缩就得
改字节（付一次断裂）。实测这次交易的定价是 **0.0075 元/批**，而压缩换来的
是**每步**从 ~250K 降到 ~40K 的体量——**压缩赢得压倒性，一次断裂微不足道**。
"每批一次断裂"不是设计缺陷，是压缩的定价，且价格很低。

### 19.5 诚实边界

* **样本小**：只有 2 个独立会话、9 次断裂。定价（0.0075 元/次）量级可信，
  分布不值得当统计结论。
* **断裂判据是启发式**（prompt 跌破前一步 80%）：理论上"整理后反而变大"的
  批次会漏检（实测未遇到），"工具结果超长被截断"理论上也会触发误检（9 次
  逐条核对时间与 promote 记录吻合，无误检）。
* **公共前缀是字符级近似**：`tokens.estimate`（tiktoken cl100k_base）按字符

## 20. 账本适配分裂：结案机制、`completed` 退出模型侧、遗产盘点（2026-09-11，用户拍板）

### 20.1 起因

   —— 逼出「这份账本在分裂后还适应吗」的重新审视，结论是**粒度错 + 注入点
   重复 + 结构缺一环**。前两项并入"装配按域分化"（Level 1 第二步，须一并
   改装配以免对同一段代码改两次、破两次前缀），第三项（**只增不减**）本轮做。
2. **"是否还有很多产物是之前遗留下来的，后面可能需要更改去适配，例如开始
   对话的目标……"** —— 用户点名的正是真缺陷：`Task.goal` 与 `TaskState.goal`
   **已经分裂了**（实测 5/77 个会话）。

### 20.2 结案机制（`TaskState.close_items`）

**症状（实测）**：状态账本全链只有追加去重，**没有任何删除/结案路径**。活会话
11 条 `escalations` 里 **8 条已结案仍挂着**——400 缺陷已修并推送、幽灵误判已
按 A 修完、v1/v3 双轨已废、分裂去留已拍板、旧定律清理已拍板、org 收窄已复议
两次……模型每轮都在读它们，**随时可能把已经做完的事重新拿来问一遍**。

**定性**：这是缺机制，不是口味问题。**"现状账本"在缺结案机制时会退化成
"没清理的收件箱"**，而化石会直接污染行动判断。

**分工纪律**（对齐 `next-stage-intent.md` §2「排除性判断不做，累积性整理可以
做」）：**语义判断归模型、机械匹配归机制**。模型在整理时（读取时刻）给出
"哪条已结案 + 用于识别的片段"，机制只做子串**唯一匹配**与移除。

关键取舍：**命中 0 条或多条一律不猜**（原样保留并把片段回报出去）——
**错删比滞留危险：滞留只是噪，误删会丢约束**（升级队列丢一条，模型就永久
少一条边界）。

**落地**：
| 文件 | 改动 |
|---|---|
| `task.py` | 新增 `TaskState.close_items(field, snippets)`（唯一匹配才移除，返回存活/已结案/未匹配）；`apply_patch` 消费 `patch["closed"]`（`[{field, match}]`）并返回结案报告；**先追加再结案**（同批"新增即结案"也能结掉，否则化石要等下一批）；`apply_state_patch` 回传报告 |
| `maintenance.py` | 新增 `_record_close_report(report)`：结案与未匹配**都写 maintenance history**（结案是删除操作，必须可见——条目删掉后 history 是唯一能回答"谁在哪次整理结掉的"的地方） |
| `prompts.py` | `state_patch` 加 `closed` 字段与判据：escalations 被人拍板、experiments 已验证、已知问题已解决即结案；**decisions 只在被推翻时结案**（正常决策是历史，留着）；片段要抄 20–40 字且账本内唯一、"要抄得够准" |

```
含已删键的会话数: 77

  …（77/77 全中）
```

即 **77/77 个历史 task.json 都躺着这个键**（值为空列表，非空计数看不见它）。

的遗留键（…）` 并落盘。选通用写法而非硬编码 `acceptance_criteria`：往后删/改
字段都不必再回来改加载口。幂等（第二次加载无键可丢、不再留痕、不落盘）。

> 这条同时是对 §17.6 实测纪律的正向印证：**同一事实换口径重测救了一次全线事故**。

## 22. Level 1 第二步：域视图的机械派生（2026-09-11，用户拍板「做装配按域分化」）

### 22.1 触发与范围裁定：先做**材料层**，不接管主链装配

用户指令「做装配按域分化吧」。动手前的定位取证发现一个硬约束，据此把范围
切成"材料层先落地、接管留到路由一起做"：

* **缓存前缀纪律**（`cache-layout-intent.md` §1/§2，09-07 用户拍板）：
  *"只有整理生效（promotion）才破坏前缀"*。而"装配按域分化"若直接接管主链
  装配，等于**每轮**（或每次切换）在中部改写历史字节——正是被否决的 V2 三档
  滑窗的同一错误（实测把命中率从 83.7% 砸到 49.9%）。
* **没有路由就没有切换点**：域视图要进主链，前提是"这一轮由哪个 agent 接活"
  存在。而路由（机制三漏斗：活跃粘滞 → 关键词/文件域命中 → LLM 兜底）在本步
  之前**不存在**。若先让装配按域分化但不路由，主链看不到任何行为变化，只是
  白付一次前缀断裂。
* 且 `context-differentiation-runtime.md` §4 明写 Level 1 三项是
  ①域树落实为注册表条目 ②**装配按域分化** ③规则优先路由；②③必须同一批落地
  才有可观测行为。

**结论**：本步交付第②步的**材料层**——把每个域的上下文完整派生出来（纯函数、
零 LLM），带完整性对账、可见面与体量实测；**不接管主链装配、不动 tools 数组、
不改任何现行行为**。这样等路由落地时，"视图怎么拼"已经是既有事实，"什么时候
用哪个视图"才是新代码。

### 22.2 视图分段与归属规则（写进 `src/wovra/views.py` 模块 docstring）

分段沿用 `cache-layout-intent.md` §3 的三段排法 + 现行信封纪律：

```
[1] 共享 system 人设        ← 公共部分在头部，分叉点尽量往后
[2] 重组上下文（本域块全分辨率 + 外域块指针 + 域卡 + 本域账本）
[3] 子 agent 身份与约束      ← 稳定尾
[4] 运行时信封              ← 绝对尾部（现行纪律，不放中部）
```

归属规则（机械、确定性、可对账）——每个块**恰好一个**归宿，三级优先：

1. **域显式声明**：块 ID 在某域 `block_ids` 里（模型的跨域/例外判断）；
2. **文件域命中**：块的文件落在某域 `file_domains` 下（精确文件或目录前缀），
   **最长前缀优先**（`src/a/b.py` 同时命中 `src/` 与 `src/a/` 时归后者）；
3. **兜底归主 agent**：无归宿块归主 agent——对齐"排除性判断不做 / 不丢块"。

账本分片（对齐 `task._MODEL_SIDE_SECTIONS`）：全局节
（goal / current_status / escalations / experiments）**永不分片**——目标与现状是
"我在干什么"的最小上下文，决策升级与待办实验是**人机协同回路本身且没有第二个
注入点**；分片节（decisions / known_issues / open_questions）按文件域机械匹配
（条目文本含该域路径或文件名即命中）。**主 agent 视图拿全量账本**——它是路由器
与默认执行者，体量削减靠"外域块指针"，不靠账本切分。

## §23 装配地板修复：二级折叠 + 最小间隔口径更正

> **本节的由来（用户两条反馈）**：①「宽限 3 轮、冷却 3 轮，谁说冷却 3 轮了，
> 我说的是最少 3 轮内不触发」；②「咋刚压缩完，现在又 10.2%，又触发了。是不是
> 有问题」。两条都成立，且是同一件事的两面：**折叠档单调膨胀把装配地板顶到了
> 水位线之上**，于是"压缩完立刻又该压"；而"冷却"这个门比用户口径少安静一轮。

### 23.1 症状与根因（实测，零 LLM）

**根因一：折叠档带着块摘要，而块摘要只在文件被删时才会掉**。`_render_collapsed`
的旧实现是「👤 原文 + 🎯 意图 + **当前仍 LIVE 的文件的块摘要**」——真实会话里
多数文件长期 live，于是折叠档**只增不减**。实测本会话：

```
折叠档 24 轮 = 46,782 tok，其中：
  👤原文+🎯意图+标题行  =  8,383 tok（20%）
  仍 LIVE 文件的块摘要  = 33,938 tok（80%，125 行）
紧凑档 11 轮 = 26,114 tok     （最近 3 代，设计如此）
```

**根因二：折叠档增长而水位线固定**。触发线 `WOVRA_ORG_WATERMARK` 是常量
100,000，每新增一批整理，折叠档就多收一轮进来——地板单调上爬：

```
每批维护结束后的第一条装配读数：
  20:10:15 →  52,980        21:40:09 →  75,851      23:16:10 →  96,847
  00:10:49 → 101,826  ← 已在水位线之上
```

00:10 这批压缩完，装配读数 101,826 tok，**比触发线 100,000 还高**——用户看到的
"刚压缩完又 10.2%"就是这个：冷一到期立刻再压，压了等于没压（下一批收编的轮
腾出的空间抵不过折叠档涨上来的）。

**顺带发现的第三方问题**：`keep_min = 最新代次 − 2` 保的是"最近 3 批**整理**"，
但折叠档原本仍给老轮留了完整块摘要，"只保留最近三次整理的内容"这个设计意图
在实现上只兑现了一半。

### 23.2 修法

| # | 改动 | 文件 |
|---|---|---|
| 1 | `_render_collapsed` 改为**二级折叠**：只留 👤 原文 + 🎯 意图 + 📌 关键约束 + **涉及文件名清单**（已删文件标「已删」）；块摘要不再进折叠档，加了「N 块细节已折叠，expand_history 可展开本轮」的指针行 | `agent/assembly.py` |
| 2 | 维护最小间隔由 `<` 改 `<=`：R35 整理完 → R36/R37/R38 都挡、R39 才放行 | `agent/maintenance.py` |

**口径更正细节**：原实现 `current_seq - last_maintained < self._org_cooldown`
是"距上次维护满 N 轮就放行"，只安静 N−1 轮；同一份代码里宽限用的是 `<=`
（R1-R3 豁免、R4 才放行），两个门不等式方向不一致本属笔误。改用 `<=` 后
才与用户口径「最少 N 轮内不触发」一致。常量名与环境变量
（`WOVRA_ORG_COOLDOWN_ROUNDS`）保留不变，仅注释改为「两次维护之间至少安静
N 轮」。

**诚实边界**：块摘要退出折叠档后，老轮的块细节要 `expand_history` 取——多
一跳。这是拿"一跳"换"地板"。另：`keep_min` 仍是"最近 3 批"而不是"最近 3 轮"，
本批未动（批的轮数由水位自然决定）。

### 23.3 实测（零 LLM，临时副本装配，不动活跃会话）

```
折叠档：46,782 → 15,465 tok   （省 31,317，降 67%）
装配地板：85,123 → 53,641 tok  （水位线 100,000，余量 +46,359）
判定：地板已低于水位线（改前 00:10 那批读数 101,826 在线之上）
紧凑档 26,114 tok 不变（设计如此）
```

  → `test_render_collapsed_keeps_file_list_only`：断言折叠档含 📌 关键约束与

* 条数上限（搜索/glob）与字符上限共用同一开关，`list_limit()` 只允许调大。
* **真超限时不丢数据**：完整内容落盘 `output/spill/<时间戳>-<用途>.txt`，
  返回文本给出路径（`limits.spill`），可用 `read_file` 分段取回。
* 落盘失败也不影响主流程（仍返回首尾，只是无路径提示）。

六处接线：`shell.run_command`、`files.read_file`（行数上限 400 → 20,000，
另加字符爆阀）、`files.search_files`（50 → 200 条 + 爆阀）、
`files.glob_files`（200 → 1,000 条 + 爆阀）、`background.check_background`（全量）、
`web.web_fetch`（默认全量，`max_chars>0` 才截断）。

**新增常驻仪器 `scripts/maint_health.py`**（零 LLM、只读，一条命令出结论）：
触发判定（到线/宽限/最小间隔三态 + 还差多少）、地板构成（system / 用户原文 /
紧凑 / 折叠 / 未整理原文 / 信封三块 + 分项自洽校验）、缓存命中（按用途分组的

## 26. 工具输出改为「指针模式」：不丢文本、量大不进上下文、告知体量（2026-09-11）

### 26.1 触发与用户口径

用户原话（并附 Zcode 工具层的同类做法作参考）：

> "不要截断丢失文本，量大可以不进上下文，返回截断内容，但可以让你取回。
> 告诉你有多大就可以。"

§25 只解决了「上限太小」（1500 → 200,000 字符），但**超限时的行为本身仍是错的**：
`limits.clip` 原实现在超限时内联 `limit` 那么长的首尾——默认 200,000 字符 ≈ 60K tok
照样灌进上下文，**一点没省**，而中段仍然凭空消失。这是把一个「省 token」的动作
做成了「既没省、又丢」的双输。

### 26.2 修法

| 位置 | 改动 |
|---|---|
| `tools/limits.py` | `clip()` 超限时只内联 `preview_chars()` 字符的**开头预览**（`WOVRA_PREVIEW_CHARS`，默认 2,000），附 `_overflow_note()`：原文体量（字符 / 行数）+ 取回方式 + 省事替代做法；新增 `source=` 参数（原文本就在盘上时不落副本） |
| `tools/files.py::read_file` | 传 `source=path`——原文就在磁盘，直接给继续读取位置，不落副本 |
| `tools/files.py::search_files` | 超限不再静默丢弃：完整清单落盘 + 报出**总条数**（「共 800 条，显示前 200 条」vs 旧的「已达 200 条上限」） |
| `tools/files.py::glob_files` | 同上：完整清单落盘 + 报出总条数 |
| `tools/web.py` / `tools/shell.py` / `tools/background.py` | 走同一 `clip`，docstring 同步为预览口径 |

关键区别一句话：旧版**内联 limit 那么长**（省不下），新版**只内联预览量级**（真省），
两者都保证完整内容可取回——区别只在「上下文里塞多少」。

### 26.3 实测证据

* `tests/test_tools` → 130 passed（含改写与新用例）。
* `test_run_command_spills_instead_of_losing_output`：3,000 字输出在 limit=500 下，
  返回体 `< 2,000` 字符、原文 3,000 字不全塞进上下文，**盘上文件一字不差含全文**。
* `test_clip_over_limit_is_preview_plus_pointer`：只留预览量级（`< 3,000`），
  报出「原文共 N 字符」与 `output/spill/` 路径，盘上内容 `== text`。
* `test_clip_source_skips_spill`：`source=` 路径不产生副本（read_file 无需复制整个文件）。
* 全套 `uv run --no-sync python -m pytest -q → 400 passed`（398 → 400，改写 2 条、新增 3 条）。

### 26.4 与 Zcode 的对照（用户提供的参考）

Zcode 侧承认四处截断（Read 默认 2000 行带 offset/limit 翻页、Bash 输出被 harness
截断、脚本里自己 `[:200]` 切片、`| tail -3` 只看结尾），并明确两条「不截断」兜底
（分析计算在完整数据上做、原文存档可随时取回）。本轮把第二条落到工具层：
**量大不进上下文，但一个字不丢，且模型知道它有多大、去哪取。**

### 26.5 回滚

* `git revert` 本批提交即回到 §25 状态（首尾内联 + 落盘）。
* 环境变量可即时回退行为：`WOVRA_OUTPUT_LIMIT`（超限线）、`WOVRA_PREVIEW_CHARS`（预览量）。
* 生效条件：进程不热重载——当前 chat 进程内仍是旧行为，**下次启动生效**。

  [运行时信封]`。身份放历史之后而非 system 里，否则每视图从第 0 字节分叉。

  判不了留主 agent（不调 LLM 兜底）。
