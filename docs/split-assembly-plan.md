## 0. 一页结论

1. **隔离第一（v3 核心，v4 收紧粒度）。** 视图之间**不共享内容**：一个视图里只有
   **属于自己的活**——自己名下的块（全分辨率）+ 这些块所在轮的用户原文（任务陈述是输入，
   机制四）。主 agent 对子域的认知**只有职责表**（分裂时写下的
   `name / description / goal / file_domains`，注册表机械派生、量极小、零 LLM）；子 agent
   看兄弟域同样如此。**路由只读职责表，不读内容。**
   *为什么不需要全局背景（用户口径）*：「工作历史就有背景」——子视图服务的是**新的需要**，
   它靠自己的历史知道「之前走的弯路、干到哪里」就够了；多余背景只会污染它的判断。
   故**非本视图的轮整轮不出现**（不做轮头占位、不留涉及文件清单）——缺口不是洞，正是隔离本身。
   （推翻 v2 的「主 agent 拿全量 + 外域块一行指针」；`views.py` 现行实现里主 agent 的
   全量账本与指针清单属 AI 埋下的遗留，步 1/2 一并改。）
2. **视图物化 + 冻结。** 每个视图持有自己的一份上下文快照 + 自己的整理代次；字节只在
   **自己**的水位整理生效时重写，其余时间纯追加（§5.1 不变量）。材料层（rounds / blocks）
   仍是唯一真相源，快照是派生物、损坏可重建。
   （术语：「视图物化」= 本轮不再只认一份上下文，而是按该轮所属视图取它**自己那份**；
   弃用「接管」这个含糊词。）
3. **视图同构，四段布局**：`[共享 system 人设] → [本视图历史] → [职责表 / 域卡] →
   [运行时信封]`。本视图的块全分辨率（按自身水位分档）；**非本视图的轮整轮不出现**。
4. **切换点只有一个：轮开启时刻。** 轮内绝不换视图（轮内赦免 + 前缀稳定），路由结果
   落在轮上、随轮持久化。
5. **粘滞是钱的问题，不是体验问题。** 默认沿用上一轮视图；只有规则命中（用户消息出现
   某域的文件域路径/文件名）才切。切换 = 一次前缀断裂 = 0.0075 元（已知定价）。
6. **视图必须按自身水位分档，否则比现在更贵。** 实测 A-1 域视图 62,152 tok > 现行装配
   地板 56,433 tok——因为它一行一块地保留了**整个历史**，而现行装配早就把更早的轮降成
   折叠档。见 §2。
7. **开关默认关。** `WOVRA_ACTIVE_VIEW` 缺省 off，行为逐字节等于今天；出问题一条环境变量
   回退，不必 revert 代码。
8. **隔离生效必须与路由同批（v3 升级）。** 步 1 的「零行为变化」只属于只有一份视图的过渡期；
   分裂产物一旦生效，主 agent 视图首次真正瘦身（历史里非本视图的块离开它）。这要求路由
   同时上线——否则用户问子域的事，主 agent 已无那份料而无人接手。原「同批」结论的理由
   从缓存纪律升级为正确性（§5）。

## 2. 关键发现：域视图比现行装配更厚

A-1 单域 62,152 tok > 现行装配地板 56,433 tok。原因不是域视图写胖了，而是**它缺分档**：
`view_for_domain` 对 222 个块一律给一行全分辨率描述，而装配对更早的轮早就只留文件名清单
（§27 的二级折叠：本会话折叠档 38 轮 16,333 tok，折叠前曾是 46,782 tok / 80% 是块摘要）。

**结论（本稿的硬要求）**：域视图做成实物时，必须按**该视图自己的整理代次**分档——基准是
该视图的代次水位，**不是全局最新代次**（否则别的域一整理，这个视图的字节就跟着漂，
冻结性立刻失效）：

```
本域块  → 最近 keep_min 代：一行式块描述（全分辨率）
        更早代：只留文件名清单 + 一句「N 块已折叠」（与现行二级折叠同口径）
外域块  → **不出现**（隔离）：**非本视图的轮整轮不进本视图**——不做轮头占位、不留块描述/
          摘要/块 ID、也不留涉及文件清单。用户口径：子视图只需要「属于自己的活」（自己走过
          的弯路、干到哪里），工作历史自带背景，多了反而污染判断。跨域取事实走 `consult`
          问属主域，接错活则转交（§4.1）
```

不分档 = 按域物化反而更贵（A-1 62K > 现状 56.8K），这是必须先解决的量。隔离（非本视图块
不出现）会在此基础上再削一层，但不能替代分档——本视图自己的旧轮也得分档。
另：`views.py` 现行实现里主 agent 拿全量账本、外域块给块 ID 指针清单，两条都是 v2 口径的
遗留，步 1/2 按 v3 改掉（主 agent 只拿自己名下的块 + 职责表）。
**另一处实现偏离**：`view_for_domain` 的 `_terse_block` 对每块输出「完整描述 / digest」，
不含分档信息；分档需要该视图的 `keep_min`，故物化时得把「整理代次」一起传进来
（`views.py` 现在接不到代次，只有 `rounds`）——这是步 1 的第一个实现缺口。

## 3. 装配布局

### 3.1 顺序

```
[1] system 人设 + 全局职责表（注册表机械派生的 name/description/goal/file_domains；
                               所有视图逐字节相同——路由的唯一输入，公共部分放最前）
[2] 本视图历史（按轮序；只含本视图块所在的轮；本视图的块按自身水位分档）
[3] 本视图身份与域卡（稳定尾：同一视图内每轮不变——我是谁、我的边界）
[4] 运行时信封（绝对尾部：todo / TaskState / 文件地图）
```

### 3.2 三条理由

* **公共在前、域相关在中、身份在后**：命中 = 从第 0 token 对齐的连续前缀，分叉点越靠后
  能共享的越多。**路由表（全员职责）是公共的**，放最前可与 system 一起被所有视图共享；
  **本视图身份是独有的**，放第 3 段——身份若放最前，每个视图从第 0 字节分叉，跨视图共享
  立刻归零。
* **身份在信封之前**：信封每轮变、身份不变——不变的必须在变的之前，否则每次状态变化都会
  作废身份段。
* **不指望跨视图共享**：各视图互享仅 system 头。分裂的真收益是**每轮体量**（降 82–84%），
  不是"大家吃同一段缓存"。

### 3.3 视图怎么物化（实现要点）

每个视图持有**自己的一份上下文**（`view_snapshots[view_id]`），内容是它的 messages 序列
（system + 历史 + 身份域卡 + 信封）加**自己的整理代次水位**。新轮到达时，只往「该轮归属的
视图」尾部追加，其余视图字节不动（§5.1 不变量）。

* 物化是零 LLM 纯函数（`views.py` 已有派生逻辑），毫秒级；可随时从材料层重建——
  **材料层（rounds / blocks）仍是唯一真相源**，快照是派生物、损坏可重建，不构成数据丢失。
* 分档按**该视图自己的水位**（见 §2）。**非本视图的一切一律不出现**（隔离，§0 第 1 条）：
  块描述、摘要、块 ID 不进；**非本视图的轮整轮不进**——不做轮头占位、不留涉及文件清单。
  本视图块所在轮保留该轮用户原文（任务陈述是输入，机制四）。跨域取事实走 `consult`
  问属主域（§4.1 接错活则转交）。
* **过渡期**（开关 off 或尚无分裂产物）主 agent 视图的物化结果与今天的装配**逐字节相同**
  （验收第 1 条）；**隔离生效后**同一视图已瘦身，等价性不再适用（§5）。
* `view_snapshots` 由装配读取；开关 `WOVRA_ACTIVE_VIEW=off` 时装配走现行路径，快照不参与
  请求（可照常物化，纯零成本）。

排序**保持时间序**（不改成域分组）：用户视角就是时间序；隔离之后本视图只看得到自己那几轮，
数量本来就不多，域分组要额外判断且不省字节。两方案待实现后实测（列为待验项，不预设结论）。

## 4. 路由（机制三漏斗，第一版只做前两级）

```
① 粘滞：默认沿用上一轮的视图（零成本、零判断）
② 规则命中：用户消息里出现某域的 file_domains 路径或其文件名 → 切到该域
③ 判不了 → 留主 agent（不调用 LLM）
```

* **路由的唯一输入是职责表**（第 1 段的全员 name/description/goal/file_domains，机械派生、
  零 LLM）——主 agent 不知道子域内容，判归属只能靠它。故职责表必须写清 file_domains，
  这是隔离架构的硬依赖（§12-7）。
* **不做 LLM 兜底**：判不了就留主 agent（它对自己名下的块是全分辨率的）。
* **误路由的代价在 v3 上升了**：v2 是「只是体量没降」，v3 是**真的会缺料**——命中域看不到
  外域块细节。这正是路由规则必须准、且第一版只做「路径/文件名」这种高置信命中的原因
  （列为 §10-6 的验收项）。
* 路由结果**落在轮上**（`round["active_view"] = "A-1"`），随轮持久化；轮内不重算。
* 用户原文**原封不动**（机制三：主 agent 是路由器不是翻译层）。

### 4.1 接错活可以转交（v4 恢复，用户口径）

原畅想的地基之一：**路由不是一次性分类，而是可以逐步纠错的过程。**

```
User → 主 agent → A（规则命中，但判错）
                    ↓ A 打开上下文发现「这不是我的活」
                  A → B（单程 notify 转交 + 在本轮留一行「已转交 B」）
                    ↓
                  B 接活（下次轮开启时成为 B 的视图）
```

* 依据：接到活的视图**手上有自己那份上下文**（走过的弯路、干到哪里），它比只读职责表的主
  agent 更有资格判断「这活该谁干」。
* 因此路由准确率**不必**做到 99%——错误成本被「转交」兜住（v3 把误路由升级为「真的缺料」
  是对的，但结论应是「用转交兜住」，不是「把隔离放开」）。
* 实现上**复用既有 `notify`**（它已在 tools 里常驻，不新增工具、不动 tools 数组）：
  转交 = 一条 notify 消息 + 本轮落一行「已转交 X」；对方 next 激活时收到（inbox）。
* **转交不算切换**：它不改本轮视图（轮内不换视图、前缀稳定），改变只发生在**下一轮开启**。
* 一次误路由 = 一轮白做 + 一条消息；故规则仍要精（§10-6），只是不再要求 100%。

## 5. 步 1 过渡期：唯一视图 = 今天的装配（逐字节等价）

**口径注意**：本节只是**过渡期**（尚无分裂产物、或开关关着）的等价性要求，**不是终态**。
终态是隔离（§0 第 1 条）——主 agent 视图瘦身，历史里非本视图的块离开它。

* 开关 `off` 或尚无分裂产物 → 只有一份视图（主 agent），其物化结果 = 今天的装配，逐字节
  相同（验收第 1 条）；
* 分裂产物生效 + 开关打开 → 即使落回主 agent，视图也已是瘦身后的（非本视图块不出现）。
  这一次字节变化**与 promote 同点**，不额外付费；此后该视图的字节只在它自己的水位整理时
  变化。

推论：**隔离生效必须与路由同批。** 否则用户问子域的事，主 agent 手上已无那份料，而没人
接手。这把原有的「同批」结论从缓存理由升级为**正确性理由**。

### 5.1 不变量：视图只在自身整理生效时改变

> **一个视图的上下文，只在它自己的水位整理生效（promotion）时重写；其余时间纯追加。**

* 别的域整理**不动它**——否则「冻结的记忆」变成「每轮现场渲染」，就是 v1 被否掉的原因；
* 分档基准是该视图自己的代次水位，不是全局最新代次；
* 与既有硬线一致：缓存前缀只在整理生效时被破坏（`cache-layout-intent.md`，09-07 拍板）；
* 代价（知情）：视图数 × 物化次数；整理要按视图各写一次。收益：切回去不因别人的整理而
  前缀失效；子 agent 有自己的记忆（Level 2 真派发的前置）。
* 推论：**跨视图共享缓存不指望**（各视图互享仅 system 头，约 1%）；分裂的真收益是每轮
  体量（降 82–84%）与视图的稳定性，不是「大家吃同一段缓存」。

## 6. 切换点与缓存定价

* 切换只发生在轮开启时刻，一次切换 = 一次前缀断裂 = **0.0075 元/批**（已知定价：净
  18,830 tok @ 未命中 0.4 元/M，见 worklog §19）。
* 粘滞轮**零额外成本**：同一视图连续多轮 = 追加式增长，与今天同命中率（90%+）。
* 因此核心工程指标是**粘滞率**：目标 >80%（用户话题本身不常跳）。若实测粘滞率低，说明
  规则太敏感（关键词误命中），应先收紧规则而不是怀疑架构。
* **不做**"切换时顺手整理"：整理有自己的触发线（体量 + 宽限 + 最小间隔），两条线不合并，
  免得把一个可观测机制变成隐式二合一。

## 7. tools 数组

* 所有视图共用**同一份** tools 数组（core.py 纪律：tools 恒定，一差分叉即整段前缀作废）。
* 第一版**不加** `view_context` 之类的模型侧工具（已拍板）。跨域取事实**走既有通信工具**
  （`consult` 问属主域 / `notify` 转交）——隔离后模型手上连对方块 ID 都没有，v2 的
  「按块 ID 走 expand_history 取回」写法随隔离作废（替代方案见 §12-6）。
* **`notify` / `consult` 已在 tools 里常驻**（core.py 注册，v3 前就如此），故 v4 的「接错活
  转交」（§4.1）**不产生任何 tools 数组变化**——它只是第一次真正被用起来（此前 inbox 有
  投递口、没有激活者）。
* 将来若要加转交/查看工具，**必须与路由同一次改完**（只付一次分叉价）。

## 8. 观测与记账

* 每轮 usage 行加 `view=A-1`（切换频率、粘滞率从账本即可算）。
* `rounds[i]["active_view"]` 落盘 → 可离线对账"这一轮由谁接活"。
* 仪器：`scripts/maint_health.py` 增一节「视图」——当前视图、各视图体量、切换序列与粘滞率。
  （仪器已存在，加一节即可，不新写脚本。）

## 9. 落地顺序（三步，每步可独立验收）

| 步 | 内容 | 可观测行为变化 | 风险 |
|---|---|---|---|
| **1** | 视图物化：每视图一份上下文快照（本视图块按自身水位分档 + 非本视图块不出现 + 职责表 + 身份域卡段），默认只物化主 agent 视图；开关 `WOVRA_ACTIVE_VIEW` 默认 off | **无**（off 且无分裂产物时逐字节等于今天） | 低：纯新增路径 |
| **2** | 路由（粘滞 + 规则命中，只读职责表）+ 落盘 `active_view` + 增量追加（新轮只写归属视图）+ 观测节 + 跨域取事实接口（§12-6）；打开开关（**隔离在此生效**） | 有（隔离 + 命中时体量降） | 中：隔离必须与路由同批，否则缺料；需实测粘滞率 |
| **3** | 逐层分裂（§13）：子视图到达自己水位时按同样的机制再裂，直到「只操作单个文件」；同时落地生命周期动作（split / no split / merge / dissolve）与经济判据 | 有（域树长出新层） | 中：需先有步 2 的真实粘滞数据 |

步 1 与步 2 可合并为一次发布（若坚持"同批"的字面口径）；分成两次的好处是步 1 出问题时
连开关都不用碰。

## 10. 验收标准（可检验，不是自述）

1. **等价性**：`WOVRA_ACTIVE_VIEW=off` 与改动前，对同一会话同一轮装配的 messages 序列
   **逐字节相同**（哈希比对）。
2. **降量 + 隔离**：路由到 A-1 时装配体量 ≤ 今天的 70%（目标值，实测后校准）；本视图块
   全分辨率；**且非本视图的块 ID、描述、整轮内容在本视图字节中一次都不出现**（用全历史
   块 ID 清单 + 全历史用户原文做否定断言）。
3. **不丢块**：`verify_completeness` 仍 True；折叠档口径与现行 `keep_min` 一致。
4. **缓存**：粘滞轮命中 ≥90%；切换轮只付一次断裂；切换次数与用户话题切换次数一致，
   不存在"每轮都切换"。
5. **冻结性（v2 新增，对应 §5.1 不变量）**：① 同一视图连续两轮之间，除尾部追加外字节不变
   （哈希比对，扣掉当前轮事件与信封）；② 制造一次别的域的整理生效，本视图的 messages
   字节**不变**（哈希比对）——这条是 v1 被否掉的那个行为，必须能测出「没发生」。
6. **路由准确性（v3 新增）**：① 对历史轮离线回放规则，记命中率与误命中率各一条；
   ② 判不了的轮留主 agent（它对自己名下的块是全分辨率的）；③ **命中率不必 99%**——
   错误成本由「接错活转交」（§4.1）兜住；④ 命中率明显低时，方案是**扩路由输入**（职责表
   写得更好/规则更细），**不是**放开隔离。
7. **转交通路（v4 新增，对应 §4.1）**：构造一次误路由（把 A-1 的活路由给 A-2），断言：
   ① A-2 本轮能调 `notify` 转交且工具返回成功；② 下一轮开启时 `active_view` 变成 A-1；
   ③ 本轮 A-2 的 messages 未被改写（轮内不换视图）；④ `active_view` 序列里出现
   `A-2 → A-1` 且只付一次断裂。

## 11. 回滚

* 步 1：删代码路径或 `git revert`（默认关闭，无行为影响）。
* 步 2：`WOVRA_ACTIVE_VIEW=off` 一行环境变量即回到今天；再不行 revert 提交。
* 无数据迁移：`active_view` 是新增字段，旧轮缺该字段视为 `A`。

## 12. 待拍板项

1. **步 1 与步 2 一次发还是两次发**（§9）。
2. **规则命中的具体形态**：路径全匹配 / 文件名匹配 / 关键词表？（第一版建议：路径或文件名，
   最小实现、可对账；关键词表易误命中，留到有数据后。）
3. **是否需要 LLM 兜底**（§4）。
4. **视图内两种排法的对照实测**（时间序 vs 域分组）——实现后量可共享前缀长度与体量，
   用同一单位（token）比较，不预设结论。
5. **视图快照的存储形态**（v2 新增）：仅内存（进程内重建、每次启动重建）还是落盘
   （跨进程稳定、可离线检查、可 git-ignore 归档）？「实物」语义倾向前者也不排斥后者，
   但要定清失效与重建规则（材料层是唯一真相源，快照随时可由它重建）。
6. **跨域取事实的接口（v3 新增，隔离的必配件）**：主 agent 拿不到子域块 ID，`expand_history`
   用不上 → 第一版是否够（`consult` 问属主域 + §4.1 转交）/ 是否要「按文件域或轮号取对方
   整理视图」的只读工具？（加工具 = 改 tools 数组 = 一次分叉价，必须与路由同批）。
7. **路由表的质量护栏（v3 新增）**：职责表是路由唯一输入，`description`/`file_domains` 由
   分裂时的 LLM 写。若某域 file_domains 为空或含糊，规则命中必失效 → 是否在分裂提示词里
   强制填 file_domains（改提示词、不改机制）。
8. **转交的落盘形态（v4 新增，对应 §4.1）**：转交只留一轮的「已转交 X」一行，还是要写
   `round["handoff_to"]` 字段（便于离线统计误路由率）？前者零成本，后者多一个字段。
   （原第 8 项「非本视图的轮轮头一行粒度」已由 v4 定案：整轮不出现，无需再拍。）
9. **分裂判据的参数（v4 新增，对应 §13.3）**：`N_future`（预计未来调用次数）怎么估、
   `C_split`（拆分成本）含哪些项、阈值定多少？第一版建议先只**记录**「发现职责」不自动拆
   （§13.3 的两动作分离），参数等有真实数据再定。
10. **一句话涉及多个域时路由给谁（v4 新增，原始畅想未落地项）**：用户原话——
    「如果一句话涉及多个agent的职责，就传递给关联最大的子agent，然后子agent再和其他
    子agent聊天对齐」。这与 §4 第一版「路径/文件名最高置信命中」不同：可能同时命中两个
    域，需要「关联最大」的判据（命中数量？命中位置？）以及随后由它 `consult` 兄弟域
    （机制五既有能力）。第一版建议：多域命中时**留主 agent**（零判断、零缺料风险），
    等有了误路由/多域轮的真实样本再定「关联最大」的算法。

## 13. 逐层分裂、生命周期、经济判据（v4 补齐原始畅想未落地项）

### 13.1 逐层分裂是正式机制，不是可选项

子视图**到达自己的水位时，按同一套机制再裂**（`A-1` → `A-1-1`），直到「只操作单个文件为止」。
用户口径：「一个任务属于 A-1 类，但现在已经分到 A-1-1 不存在那个类，就传给最相关的人，
让其后面再次分裂出来这个新功能需求」。

* 裂出的子视图同样遵守 §0 第 1 条（隔离）与 §5.1（不变量），不因层数深而破例。
* **管理关系永远一层**：主 agent 直管所有 agent；`A-1` 是**职责路径 ID**（A 内的子域），不是管理树。
  2026-09-12 改版：主 agent = `Main`，顶层域 `A`、`B`、`C`…，`A` 满了才裂 `A-1`（见 worklog §46）。
  的第三层（`registry.py` 现有实现即如此：路径 ID 管职责，管理关系两层）——避免重演 V1 的
  复杂组织结构。
* 落地位置：§9 步 3。前置是步 2 的真实粘滞数据（不然不知道自己裂得对不对）。

### 13.2 生命周期：四个动作，极简版

`split` / `no split` / `merge` / `dissolve` 都是**运行时行为**，不是架构铁律。

* 「允许不分」与「允许拆」同等重要：工作虽多但始终高度相关，且现行上下文管理已够用 →
  **不拆**（用户口径：「拆分本身也有成本，只有 Context 隔离的收益超过拆分成本时才值得拆」）。
* 注册表条目现只有 `status: dormant` 一种取值，四动作**尚未实现**；第一版只做 split/no split，
  merge/dissolve 留到出现「Agent 垃圾堆」的实证再说（不给未发生的问题写代码）。
* 无需新增 create/destroy API：agent 不是进程，是「注册表条目 + 视图」（机制二）。

### 13.3 经济判据：「发现职责」与「创建 Agent」是两个动作

```
Benefit_split ≈ (B − B′) × N_future − C_split
  B / B′   拆分前 / 后每次调用的上下文基础（base）
  N_future 预计未来调用次数
  C_split  建视图 + 缓存重建 + 沟通等一次性成本
Benefit_split ≤ 0 → 不拆
```

* 所以第一版可以**先记录类别、不立刻拆**：发现职责 → 记进职责表；真出现「base 很大 + 该类
  占比高 + 未来还会继续干」时才 split。
* 这与 §6 的「粘滞率」不冲突：粘滞率是**已拆之后**的工程指标，本判据是**要不要拆**的经济判据。
* 参数待定（§12-9）。

### 13.4 三级台阶：先验证「Context 分化本身是否就够」

```
Level 0  一个 Agent + 一个 Context           ← 今天
Level 1  一个 Agent + 多个 Context 视图      ← 本稿步 1/2 交付的形态
Level 2  多个 Agent + 各自 Context（真派发） ← 步 3 之后才谈
```

* 只有 Level 1 不够，才升 Level 2。若 Level 1 已拿到约 90% 的收益，就不必付 Level 2 的剩余成本
  ——这正是把 §9 拆成三步、而不是一步跳到多 Agent 的理由。
* 主 agent 仍保留**环境配置**与**不属于任何域的讨论**（原始畅想：「只有环境配置与不涉及文件
  且不属于那一类的讨论一直放在主 agent 里面」）——它是默认执行者，不只是路由器。
