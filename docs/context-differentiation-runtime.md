## 0. 一页结论

V1（模型驱动编排）被首战数据与四条反驳收缩为三项长周期资产并冻结后，
用户对"多 agent 是否该存在"做了一整晚深度反思，产出的不是放弃，而是
**因果反转**：

> **不是先有 Agent 再分配上下文，而是先有真实工作，从上下文的自然分化中
> 产生 Agent。**

```text
真实工作 → Event → Round → Block（运行时结构化，零 LLM）
        → 语义标注（低频批量 LLM，随水位整理做）
        → 稳定工作边界 → 水位拆分 → Context View
        → 必要时才是独立 Agent → 继续真实工作 → 新结构继续产生
```

六条定调：

1. **Agent 不是进程**（对齐确认）——是注册表条目 + 上下文视图 + 路由规则，
   单线程运行时内切换。V1.2 的进程基建（锁/进程组/唤醒线程/taskkill）
   对本方案完全多余；"agent 间通信"就是同一进程内读对方的账本。
2. **主 agent = 路由器 + 默认执行者**——原文转发、错误路由可纠、不收汇报。
   不再是 Planner / 架构师 / 总秘书。
3. **拆分发生在水位整理点**（对齐确认）——那次缓存破坏本来就要发生，拆分
   只是把"整理成一锅"变成"整理成 N 锅"，不引入新的上下文破坏。
4. **休眠 agent 零成本**（对齐确认）——不对话就没有那一轮的基座付费；
   拆多了的代价不在 token，只在注册表卫生（见 §3.3）。
5. **Level 1（单 agent 多 Context 视图）是主战场**——押注它拿走大部分
   收益；真 Agent 化（Level 2）只在 View 不够时才值得（§5）。
6. **实验 A 可零成本起步**——块划分是事件流的纯函数，可对历史 task.json
   离线补算，不用写运行时就能验证最上游假设（§5）。

## 1. 与 V1 首战死因的逐条对账

V1 实测四大成本（`org-experiment-minecraft.md` §5），新方案各有一个
结构性消解，不是修补：

| V1 实测死因（事实） | 新方案的消解 | 性质 |
|---|---|---|
| 冷启动税 ×3（最大单项，命中率 73.8-94.5% vs 98.3%） | 拆分与水位整理同点发生：那次缓存破坏本来就注定；输入单流，非活跃分支不产生持续成本 | 假设→待实验 B/C |
| 翻译与调度（主 agent 等效 223K 只产出调度） | 主 agent 降级为路由器，原文转发；子 agent 直报用户，翻译层整个消失 | 假设→待实验 |
| 强制汇报链（Child→Report→Main→理解→下发） | pull 替代 push：信息默认存在（账本），需要时才读——与 V3 "不装进上下文、保持可取用"同一条原则 | 事实级设计决策 |
| 预先职责设计（动结构的门槛从未满足） | 职责从块结构事后涌现；拆分决策权从模型移交给运行时——"机制只做体量与时机，语义归模型"应用到组织层 | 假设→待实验 A |

最后一条是本方案与 V1 的本质区别：**V1 里 spawn 是模型的语义决策，
新方案里拆分是水位触发的机制行为，依据是客观事实**（哪些文件被改过
多少次、命令标签的分布）。

## 2. 机制基线（意图封版 · 形态待现场）

### 机制一：Block 与命令标签（运行时结构化，零 LLM）

* 轮内以**写/改文件**为截止划分 Block：读、分析、修改 icp.py → 一个块；
  切到 UI 文件 → 边界。**一轮内没有修改文件 → 不分块，整轮总结成一段话**。
* 命令执行工具加分类标签，第一版六类：
  `environment / file / test / build / run / other`——环境配置天然单独
  组块，隔离出工作上下文（Runtime Governance 的前哨）。
* Block 第一版最小结构：`{id, round_id, start_event, end_event,
  touched_files, command_types}`。不设计更复杂的块。
* 成本：确定性规则，CPU/代码复杂度略增，token 成本 ≈ 0。
* 收益：整理输入结构化（LLM 不再从几百个原始事件里自己找结构）、
  文件地图增强、expand 导航、回放分析——**即使组织层永不建成，
  这些也是纯 V3 收益**。
* （2026-09-07 落地：`src/wovra/blocks.py`——`tag_command` 六类标签 +
  `segment_round` 纯函数切块，轮闭合时随轮次落盘；`scripts/render_blocks.py`
  对历史 task.json 离线补算检查，不迁移不修改。）

### 机制二：低频语义标注（LLM，随水位整理批量做）

* "文件名不是职责"（algorithm.py 可能同时含 ICP/标定/可视化），纯规则
  不足以产生稳定职责；但也不逐事件调 LLM——**N 个块一次调用**，在
  水位整理时批量完成：块属于哪个大类（如 ICP / UI）、大类叫什么、
  哪几个块本质同域。
* 分类**只分大类**（对齐确认）。语义归模型、体量归机制的原则继续成立：
  运行时先切出明显结构，LLM 只做低频轻语义。
* **判据修订（2026-09-08，实测反例驱动，样本见
  first-split-analysis-sample.md）**：分类按**现状归属**，不按"话题×
  时间"——实测反例：按话题把"单文件页 v1"与"模块化 v2"分成两类，
  恰是要防止的"旧版一类、新版一类"。三条判据：
  ① **独立运行性**：类 = 能独立接活的单元（活性现状 + 解释现状的最小
  历史）——把该类单独丢给新会话，能不问"这是什么项目"就接活；
  ② **生死归属**：块跟着它触达工件的现世走，被重写/取代的前史归取代
  者并标注 superseded（机械信号：同路径重写链、拆分转世链——机制一
  的 wrote_files 已铺好，LLM 只答"这条链还活着吗、被谁接班"）；
  ③ **粗分裂优先**：首分裂只分零状态 vs 工作（规则可做），细分要
  体量压力 × 现状可分性双信号，话题不同永远不是理由。
* 分类器输出形态（同日修订）：不再输出话题目录，改为三段——**现状
  清单**（文件域 × 约束 × 目标，即注册表"类别描述 + 所有权文件域"的
  直接原料）→ **块 → 域归属**（带 superseded 标注）→ 类内历史线
  （时间序叙事，生死标注内嵌；"逻辑阶段归组"是类内叙事的段落，不是
  分裂边界）。分类与注册表推导是同一次调用的两个产物。

### 机制三：注册表与路由

* Agent = 注册表条目：`{路径 ID（A / A-1 / A-1-1）, 类别描述, 所有权
  文件域（可多文件）, 状态}`。
* **路径 ID 是职责路径，不是管理树**（对齐确认）：管理关系永远最多两层
  （主 agent 直管所有子 agent），`A-1-1` 表示"算法大类 / 某功能 / 某
  具体文件"的职责粒度。子 agent 到达自己的压缩水位时可再次分裂
  （满足分裂条件则分裂，不满足只压缩），最细到只操作单个文件。
* 主 agent 通过工具获取所有 agent 的职责描述与文件域；用户消息**原封
  不动**转发给关联最大的子 agent。一句话涉及多个 agent → 传给关联
  最大的，由它再和其他 agent 对齐。
* **错误路由可纠**（对齐确认）：子 agent 上下文更丰富，发现不符合自己
  就转给更合适的 agent。配套纪律：**接活先验 ownership**（自己的文件域
  /类别），不匹配就转走，不许先干一半再退回——半途退货是最贵的纠错。
* 路由不每次调 LLM：规则优先（Active Agent 粘滞 / 关键词命中文件域），
  判断不了才走 LLM 兜底，且兜底只回答 `{"target": "..."}`，不解释、
  不理解任务。
* 任务属于某大类但已分裂到更细粒度（A-1 类已不存在）→ 传给最相关的
  现存节点（如 A-1-1），由它后续再分裂出新功能。不属于任何子 agent
  → 主 agent 自己处理，等下次分裂时长出来。环境配置与不涉及文件且
  不属于任何大类的讨论，一直留在主 agent。
* **生命周期 = 现世生命周期（2026-09-08 拍板：不造生命管理机制）**。
  agent 不是进程，是"注册表条目 + 视图"，因此生命周期退化为注册表
  状态字段的五个值，全部由既有机制触发，无 create/destroy API：
  - **休眠**（默认态）：条目 + 磁盘上的视图，零窗口成本；
  - **活跃**：路由漏斗命中，单线程切换——同一时刻至多一个活跃 agent，
    切换 = 换视图（分流），传递的上下文不同而已；
  - **诞生**：分裂生效（机制四）或现状清单长出新文件域（"等下次
    分裂时长出来"）——没有 spawn，只有注册表多一行；
  - **并行**：契约协商后的临时 fan-out（见机制五补充），join 后回到
    单线；
  - **分裂**（唯一结构变化，2026-09-08 修正：无"合并/归档"态）——
    子 agent **不会死**：其现世被取代/删除不是死亡，是它自己的工作
    历史翻篇（同一 agent 继续拥有新版本）。父 agent 分裂后也不消失，
    退化为协调者/或保留为其中一域的执行者。判据二（生死归属）在
    agent 层的体现因此只有一种：**前史跟 agent 走，不换主**——块级
    的"归取代者"规则只发生在同一 agent 的历史线内部标注上。
    生命周期管理与注册表状态字段是同一件事，无 create/destroy API。

### 机制四：拆分 = 水位整理的一次特殊产物

* 拆分时机：当前 agent 到达水位 → 批量整理 → 发现多个稳定工作大类
  且当前上下文正在多类混装 → 按已形成的边界把整理结果分成 N 份视图。
  **不引入额外缓存破坏**（补充答辩确认）。
* 子 agent 继承与自己类别相关的整理视图；**逐层分裂、不复制全局历史**
  （对齐确认）——分裂时子上下文先天带有它形成之前所需的工作历史，
  之后增长自己的。全局历史不可变的不变量继续成立。
* 拆分收益的账本口径：**B 取整理后残余基座**，不是原始基座——
  Benefit = (B−B′)×N_future − C_split，其中 B−B′ = 混装残余 − 单话题
  残余。收益是二阶的：随稳定话题数 × 会话长度增长；小规模（峰值 90K、
  1-2 话题）可能测不出，真实目标尺度是多话题长会话（几十轮、累计
  亿级 token）。
* **归属与生效协议（2026-09-08 补充，异步双路实测定型）**：
  - **原子生效**：整理与分裂同批暂存、同一轮开启时刻 promote——
    不允许分裂先生效造成视图与产物错位；
  - **决定只认已生效状态**：分析中的提案不参与路由。路由 = 粘滞 →
    关键词/文件域命中 → LLM 兜底 → 接活验 ownership 不匹配转走
    （机制三漏斗，向维护期的推广）；
  - **期间到达轮次**：维护窗口内用户新聊的轮次粘滞原地、原始追加
    （缓存照骑），**渐近归属**——不在分析快照里的轮不强行塞进提案，
    等它进入下次水位批次才做语义归属，该搬的那时搬（成本 = 搬家者
    自己的一次视图替换）；
  - **提案新鲜度检查**：生效前机械核对提案文件域 vs 最近 wrote_files，
    现状已变则作废提案、等下次水位重析（提案半衰期 = 到下一次现状
    变化）；
  - **上下文分配**：**块级所有权**——每块恰有一个属主域（多域轮按块
    拆，轮不是分配单位）；**轮首用户原文随块共享**（任务陈述是输入
    不是结论，多份无害）；**外域块留一行指针**（跨域取事实走对方
    整理视图 / expand_history，不复制块细节——同一事实两份真相必然
    漂移）；**共享事实允许双向冗余**（接口契约、联调结论等高价值
    小体积的协商产物，双方状态账本各留一份，生死各自维护）。
    "允许一定臃肿"的边界 = 共享事实与用户原文可以冗余，块细节不冗余。
  - **保护机制（2026-09-09 用户拍板：3 轮全豁免，无事件数上限）**：
    `WOVRA_ORG_GRACE_ROUNDS`（默认 3，会话前 N 轮豁免维护，**巨型轮
    同样豁免**——用户提出 3 轮时已考虑 229 步巨轮；代价知情：超水位
    推迟的整理由冷却后的批次补上。昨夜 D 组驱动的"轻轮才豁免"双条件
    经用户否决，已回滚）+ `WOVRA_ORG_COOLDOWN_ROUNDS`（默认 3，两次
    维护之间最小轮距，适配大小不同的起点、防高频）；窗口保底紧急折叠
    **不在豁免范围**（独立生存线）。配套：`verify_milestone` 即轮闭合
    （里程碑驱动轮，检查点 = 轮边界）。分裂后水位按 agent 各自计量——
    **有效容量随分裂增长**（Σ 子 agent 窗口 > 单体窗口），阈值无需
    上调，保护旋钮主要服务分裂前的单体阶段，分裂后系统自调节。

### 机制五：通信是例外，不是主流程

* 两类：**单向**（转交/通知/交接，只发不等）与**双向**（对方确认/
  对齐观点，发并等回）。场景少——大多发生在不同职责要统一接口的
  思想对齐，通常一两次对话。
* **已实现为常驻工具（2026-09-08，Level 0.5 骨架）**：`notify(agent,
  message)`（单向：落目标收件箱，激活时送达）+ `consult(agent,
  question)`（双向：切目标职责视角回答一次，回复打 `[子agent]` 标签
  直接流式进用户窗口、同时返回调用方——**子 agent 结果直达用户，
  不回路由主 agent 转述**）。配套展示纪律：思考全局单行（\\r 原地
  刷新，防污染窗口、防视角来回切换）；consult 不带工具（协商是对话
  不是干活）；收件箱随激活送达并清空。
* **并行 fan-out 协议（2026-09-08 补充，Level 2 形态）**：用户一个大
  任务横跨多域时——
  1. **前置协商**（一次双向对齐）：重心 agent 分解任务 → 各域 agent
     确认接口契约/文件边界/验收口径。契约属共享事实，双向冗余（各方
     账本各留一份）；
  2. **并行执行**：各 agent 在自己的视图里跑自己的块——ownership 无
     交集保证零文件冲突，各自前缀、各自水位、各自缓存；
  3. **汇合 join**：重心域（或集成域）pull 各家产物做集成验收，逻辑
     轮在 join 后闭合，最终答复由主对话 agent 呈给用户。
  硬边界：**依赖即串行**——块间有依赖（B 的对接依赖 A 的接口细节）
  就不能并行，回到分流串行（A 完成 → 转交 B）；并行只冻结"接口已
  协商"的部分。一路失败不阻塞其他路，join 时标注缺口。并行是例外
  （同本机制第一条），默认仍是单线程分流。
* 默认不发生。正常流永远：用户 → 某个 agent → 完成 → 直接呈现给用户。
  **子 agent 完成情况不向主 agent 汇报**（对齐确认：单向，所有子 agent
  直报用户），主 agent 需要时按需读取（pull）。
* 跨 agent 取事实（对齐确认）：直接对话或直接读。默认读到的应是对方的
  **整理视图 / 状态账本 / 事件索引**，全文细节走 expand——别让"直接读"
  变成跨 agent 的全量历史搬运。
* 每个 agent 可通过工具获取所有 agent 的职责描述、工作范围与整体文件
  架构——这份文本由注册表与文件地图**机械派生**，很小且零维护成本。

### 机制六：全局状态——待定，不造

* 全局 TaskState 是否独立存在：**待定**（对齐确认）。原文转发保证主
  agent 亲见过每一条用户输入，它自己的 V3 水位管线组织自己的历史，
  产出即是事实上的全局账本——不需要新机制。出现真实需求前不造，
  这是项目自己的纪律。

## 3. 经济模型（口径已定 · 数值待校准）

### 3.1 拆分的账

* 不变式：拆分与水位整理同点 → C_split 里没有"额外一次缓存破坏"；
  拆分的真实成本 = 一次组织结果从一锅变 N 锅的结构处理 + 未来各分支
  的缓存爬坡（按实际访问概率加权：C ≈ Σ Pᵢ·Cᵢ，不是 2×C）。
* 休眠分支零持续成本：没有对话就没有基座付费。**推论（对齐确认）**：
  "用户提一嘴就分裂"在 token 经济学上无害——拆多了的代价不在 token。
* 残余约束因此只有注册表卫生：类别标签**永远免费记**，agent 节点在
  **体量过阈值**时才立——低于阈值的类别只是索引行上的一个标签，
  不进注册表。阈值数值待定（第一现场）。

### 3.2 交替税的真实形状（执行侧分析，2026-09-07）

前缀缓存命中的判据是**位置**不是内容：新请求与缓存中仍存活的条目
**从第 0 个 token 起逐位对齐**，对齐多长命中多长。由此：

* 切回旧 agent **天然对齐**（追加式装配保证新请求以它上次的请求为前缀）
  ——间隔 < TTL 则免费；间隔 > TTL 则条目已被服务端丢弃，整基座按
  全价冷算 + TTFT 拉长。
* 单上下文没有这个问题：追加式历史永远在同一棵前缀树上延长，话题怎么
  跳都不换树。分裂后的交替是在多棵前缀树之间跳，每跳回一次赌一次 TTL。
* 应对三件套（待验证，不是架构规定）：账本记录"距本 agent 上次请求的
  间隔 + 命中/未命中"（交替税从数据现形）；`WOVRA_CACHE_TTL` 可配置
  （各服务商差异大：OpenAI/Anthropic 5-10 分钟，DeepSeek 宣称数小时，
  火山/GLM 待实测）；**粘滞路由**——把切回间隔顶过 TTL。
* **冷切回 = 免费整理时机**：TTL 已杀死的缓存，破坏免费。检测到超时
  切回时顺手做该 agent 的水位整理，重组基座的缓存代价为零——与
  "拆分发生在水位点"是同一逻辑的镜像。

### 3.3 一次重要的判据修正（存档）

执行侧曾提出"拆分判据要区分交错复现与时序阶段"，其经济理由被用户
驳倒：休眠零成本意味着"给已结束的阶段立 agent"也不产生 token 代价。
判据收缩为注册表卫生问题（§3.1 的体量阈值），不再是成本问题。

## 4. Level 0 / 1 / 2：三级形态

```text
Level 0   一个 agent，一个 context            （现状：V3）
Level 1   一个 agent，多个 Context 视图        （装配规则切换）
Level 2   多个 agent，各自 context             （必要时才做）
```

* Level 1 本质是**话题感知的装配规则**：路由到 A-1 时，装配里 A-1 类别的
  整理残余全分辨率，其他类别降为索引行——这要求块/类别标签落在整理
  输出的每一行上（装配顺序决策，实现前定死）。基座随话题数增长的问题
  由它解。
* 押注：Level 1 拿走 ~90% 收益。只有 View 不够时才 Level 2。
  实验 C 的判据：C < B 才说明 Agent 本身有额外价值；C ≈ B 就停在 B；
  C > B 则 Agent 是多余的。

## 5. 实验路径

| 实验 | 问题 | 方法 | 成本 |
|---|---|---|---|
| **A：结构有没有意义** | 块划分稳定吗？分类纯度？同类工作聚在一起吗？ | **离线**：对真实历史（29 轮生产轨迹等）跑块划分 + 批量标注，看纯度/稳定性 | ≈0（块是纯函数；标注一次性） |
| **B：Context 分化的经济价值** | 单 context vs Context Views | 受控对照，记 Base/Input/Cache/TTFT/成本 | 中 |
| **C：Agent 化是否值得** | View 之外 Agent 还有收益吗 | 单 agent vs Views vs Agents 三组 | 高，最后做 |

* 实验 A 是最上游假设（**稳定类别存在且可从块结构恢复**）的检验——
  下游一切（拆分收益、路由、继承）都以它为条件。若失败，失败的是
  "分类可恢复"这个假设，不是分化思想本身。
* 账本新指标：分类纯度/稳定性、路由准确率与纠正跳数、切换频率与
  间隔-vs-TTL、各 agent 基座 vs 单 agent 整理基座、每单位验收产出的
  等效成本。
* 时间（墙钟）不作为指标，沿用既定口径。

## 6. 边界与纪律（全部继承，无一新增）

1. **不做排除性判断**——分类只做大类、描述性不裁剪视野、expand 展开
   权保留、人机界面不卡死细节。
2. **语义归模型、体量归机制**——块/标签/路由表是机制的，类别语义是
   模型的。
3. **原始历史不可变**——拆分是视图分化，不是历史切分。
4. **通信是例外**——不为协同而协同。
5. **不为"架构完整"加机制**——强制汇报、强制规划、强制拆分、强制通信、
   强制层级，V1 已证全是要把系统搞复杂的东西。
6. 生命周期第一版极简：`active / dormant / dissolved`，不做自动合并
   （dissolved = 账本合并回父级、历史归档——"解散 ≠ 删除"继续成立）。

**待定清单（后面再定，不是遗忘）**：拆分时组织调用的输出契约（JSON
三段式：categories / views / registry，观察一次分 2-3 个 vs 5-6 个的
质量差异）· 体量阈值数值 · WOVRA_CACHE_TTL 实测值 · 路由兜底的具体
形态 · ownership 先验协议细节 · 装配顺序的最终落位 · 升级/待办实验
等 V1 遗产在新架构里的去留。

## 一段话总结

V1 问"多 agent 怎么设计"，答错了；本方案换了一个问题："一个长期工作
的 agent，随着领域自然增多，如何不让所有工作共享同一个不断膨胀的
上下文"。答案是先让机制把工作历史结构化（Block + 标签），让语义在
水位时批量归堆（大类），让职责从稳定的边界里涌现（注册表），让拆分
与整理同点发生（不引入新破坏），让路由犯错变得便宜（原文转发 + 可纠
+ ownership 先验），让休眠免费、让冷切回变成免费整理时机。多 agent
从此不是要设计的架构，而是上下文分化之后**可选的执行实体**——
Long-running Work → Context Accumulation → Context Differentiation →
Responsibility Emergence → Agent。
