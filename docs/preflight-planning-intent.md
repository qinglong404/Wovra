## 0. 一页结论

这是一条**开工前的升级**：当任务开放、意图模糊或体量巨大时，先做一轮
**只读的规划**，把方案交给用户审批；**范围确认后**才落实细节并动手。

它与 `next-stage-intent.md` 否掉**传统 todo**（平铺清单）不矛盾——被否的是
"把步骤清单写下来当权威、逐条 tick"（Wovra 自己的 `todo` 大步/小步账本是
另一形态：深度恒 1、验收即清，见 `todo-milestone-tool.md`），这里要的是
**开工前的签批闸门**：闸门在**动工之前**
拦一次，计划本身**不落盘为权威工件**。

一句话：

> **借"停一下、要签批"，不借"先写步骤清单"。**

## 1. 需求（用户原话展开）

触发情形（用户列举，非穷尽）：

| 情形 | 含义（待第一现场细化） |
|---|---|
| **开放话题** | 目标没有明确终点（"越还原越好"），边界需要人参与划定 |
| **模糊意图** | 用户自己还没想清楚要什么，需要机器把决策空间整理成"人尺寸"的选项 |
| **巨大体量** | 一次动作波及面大、代价高、难回退（如全库重构、批量改名、对外发布） |
| 等等 | 留口子：由第一现场补，不从纸上穷举 |

流程（用户拍板）：

```text
识别情形 → 规划（只读） → 用户审批 → 确定范围 → 落实细节 → 开始
```

三条要点：

1. **规划发生在动手之前**，且是只读的——不产生副作用，审批前不写文件、
   不改状态；
2. **审批是闸门**：未经确认不进入执行；确认的内容是**范围**（做什么、
   不做什么、验收长什么样），不是逐条步骤；
3. **细节在范围确认之后落实**——先定边界，再谈怎么做。

## 2. 为什么现在提（第一现场）

**事实级动机**（已有真实数据，不是纸上推演）：

* F 组实测：**范围自长 ∝ 模型速度**——"越还原越好"类无边界任务书在快模型上
  膨胀更快（15 功能域 / 325K 上下文 / 整理 6 次全 pending）；
* 用户在成熟 agent 上的亲历：**改一个小功能烧掉 23M token**，事后看"没干
  多少活"；
* 2026-09-11 的重构会话本身就是一次样本：任务开放（不是一句明确指令）、
  体量巨大（8000+ 行、跨 20 个文件）、影响面不可逆（大 diff），
  机器先只读探查 → 出一份方案 → 用户审批（兼容口径 / 拆分粒度 / 执行顺序
  三个选择）→ 才动手。**用户事后主动提出把这件事机制化。**

**假设**：上面这类失败有一部分本可在**开工前**用一次低成本的确认避免，而不必
等干到一半才靠升级队列补救。

**待验证**：闸门对"该动手时过度确认"的副作用——低 stake 任务若也被拦，
决策成本会吃掉收益（见 §4 边界）。

## 3. 与现有机制的关系（不新建管线）

**事实**：Wovra 已有四块现成的地基，规划闸门应当长在它们上面：

| 已有机制 | 本闸门如何使用它 |
|---|---|
| `TaskState.escalations`（决策升级，人机协同一等公民） | 规划产出**就是一条升级**——不是新工件类型 |
| `report` / `\report`（零 LLM 机械渲染） | 审批界面：人视图里读方案、拍板，无需新 UI |
| 异步友好（人不在线时跑别的分支，升级在队列里等） | 人不在时挂起等待，而不是机器替人拍板 |
| `todo` 大步/小步（`todo-milestone-tool.md`） | 审批通过后的**执行侧**计划账本；闸门只负责"开工前"，二者不重叠 |

**关键**：整理/报告/升级的管线都不新增——闸门只是给 `escalations` 增加
一种**开工前触发**的类型（现有升级是"干到一半发现不对"才触发）。

## 4. 边界

### 4.1 触发：看"不可逆性与体量"，不看"任务大不大"（假设）

* 可逆的、低 stake 的分叉**不拦**——"不为低 stake 的分叉花决策成本"
  （`next-stage-intent.md` §7.5 已有纪律）；
* 判定应尽量用**零 LLM 的事实**（会触及多少文件、是否含不可逆操作如删除/
  对外发布/大范围改写），语义判断（这题开不开放）由模型在读取时刻做——
  与"机制只做体量与时机、语义归模型"一致；
* 阈值形态（绝对值 / 相对会话体量 / 分档）待第一现场，纸上不定。

### 4.2 产出的工件：只写目标展开层，不写方法处方（假设）

沿用计划两层论（`next-stage-intent.md` §4）：

```text
目标展开层（写，且耐久）：要解决的问题、边界约束、验收长什么样、粗路标
方法路径层（不落盘为权威）：步骤、顺序、实现选型——每轮从当前状态重算
```

粗路标可以写，但必须**显式声明非承诺**（"路标只作排序参考，不做承诺"），
否则就是传统 todo（平铺清单）的原罪：方法死时目标陪葬，或方法靠沉没成本赖着不走。

### 4.3 审批后：范围进约束，细节进执行（对齐确认）

* 用户拍板的"做什么 / 不做什么"应进入 `TaskState.constraints`（最慢层，
  装配最前）——它是后续每轮的边界，不是一次性消息；
* 具体步骤仍不落盘，由执行侧（todo 大步/小步 + 每轮重算）承担；
* 人的修改走既有修订留痕（谁改、哪轮改、为什么）。

### 4.4 不做成"模式"（待验证）

* 模式是**全局状态**，需要人记得切换、也容易被遗忘；
* 升级是**内容**，由水位/报告机制免费携带；
* 假设：做成内容比做成模式更贴合"机制只做时机、语义归模型"。
  （ZCode 的 plan mode 是模式开关，本闸门不照搬其形态。）

## 5. 明确不做

1. **不做传统 todo 式的持久步骤清单**——与 `next-stage-intent.md` §3 一致；
   （执行侧仍由 `todo` 大步/小步账本承担，那是深度恒 1 的另一形态）
2. **不为低 stake 分叉加确认**——决策成本也是成本；
3. **不阻塞在人不在场时**——升级排队，机器按最小不可逆路径继续；
4. **不新增整理/报告/UI 管线**——只给 `escalations` 加一种开工前触发；
5. **不在纸上定阈值与模板字段**——从第一现场长。

## 6. 检验清单（进入实现前逐条过）

1. 它需要语义判断吗？需要的话，判断权能否推给读取时刻的模型？
   （"这题开不开放"是语义 → 归模型；"触及多大面"是事实 → 归机制）
2. 触发条件能否只用零 LLM 事实估？不能的话，宁可让模型在规划轮里自报。
3. 审批通过的范围是否进了最慢层（constraints），而不是随对话漂走？
4. 人不在场时是否有明确且安全的默认路径（最小不可逆）？
5. 低 stake 任务是否会被误拦？误拦率如何观测？

## 7. 第一现场与待办

* **首战样本已有**：2026-09-11 重构会话（只读探查 → 方案 → 三选一审批 →
  执行）。可作为"闸门本可以是什么样"的对照，但**尚未机制化**。
* **待第一现场**：触发的具体口径（哪些情形算开放/模糊/巨大）、审批产物的
  字段（复用 `escalations` 的哪些栏目）、与 `todo` 大步的衔接点。
* **开放问题**：规划轮是否要独立的"只读"工具集（像 org/split 那样收窄），
  还是在工作对话里直接声明只读？前者更硬、后者更省一次调用——待现场。
* **优先级**：用户已定"先写意图存档，不急实现"；按生长纪律，等真实使用
  再打脸一次后落地。
