# Wovra 上下文管理 V2 —— 最终设计与成本模型

> 状态：定稿待实现（本文取代 `context-runtime-experiment.md` 成为正式设计）
> 本文的所有机制均由讨论与实测数据推导而来，关键数字可在"成本模型"一章复算。

---

## 0. 一页结论

```text
目标：在缓存定价（命中 = 1/30 价）的现实下，让长会话（几十到几百轮、
     亿级累计 token）的等效输入成本比"全量回放"低 5-10 倍，
     同时保证模型始终知道"历史里有什么、需要时如何找回细节"。

手段：分层加载（不是压缩历史）——
     近 3 轮全量 → 更早轮次按预算给三档浓缩视图 → 永远可 expand 找回原文；
     整理（Organization）异步后台跑，不阻塞对话；
     缓存友好排序：越易变的信息越靠后放。

一句话：历史是磁盘上的事实，上下文是按需组装的临时视图，
       视图永远可以丢弃重建，事实永不修改。
```

## 1. 设计目标与经济学

### 1.1 缓存记账规则

模型 API 对输入按"前缀缓存"计费：本次请求与上次请求**完全相同的
前缀**按缓存价（实测 **1/30**）计，不同的尾部按全价计。由此三条定律：

1. **追加免费**——末尾加内容，前缀全部命中缓存
2. **从尾部裁剪免费**——去掉末尾内容，剩余前缀缓存原样有效
3. **改写中前部 = 从改写点起全部作废**——后面所有内容按全价重算

### 1.2 乘数公式

Agent 循环里每步都要发送"当时的全部上下文"，所以：

> **一轮的输入总量 ≈ 步数 × 加载基座体积 B**（新增内容在 B 大时可忽略）

### 1.3 真实案例：第 69 轮（17 步，每步新增 0.5K）

| 每步加载基座 B | 本轮原始输入 | 缓存折算后（1/30） | 说明 |
|---|---|---|---|
| 6K | 170K | ≈ 13K | 理论下限（需极强筛选） |
| **50K** | **918K** | **≈ 38K** | **V2 机制的现实规模（68 轮浓缩视图 + 当前轮）** |
| 100K | 1,768K | ≈ 65K | 分层失效、基座膨胀时 |
| 770K（baseline 全量回放） | 13,161K | ≈ 446K | 对照组在第 69 轮的真实成本 |

**结论：基座 B 是唯一的乘数。** 50K 基座下比全量回放省约 12 倍；
且 50K 下缓存破坏一次只损失 50K（≈ 一轮成本），架构对"重组"的容忍度高，
实现可以保持简单。真实 67 轮会话推算：baseline 约 1,000 万+ 等效输入，
V2 约 200-300 万等效——**节约 5-10 倍**。

### 1.4 首轮 4 轮实测数据（V1 机制，待 V2 修正）

| 轮次 | V1 managed：输入/合计/耗时 | baseline：输入/合计/耗时 |
|---|---|---|
| R1-R4 合计 | 59,012 / 104,086 / 1138s | 87,659 / 112,210 / 505s |

V1 的问题（V2 逐条修正）：输入省 32.7% 但被整理调用的思考输出抵消
（总省仅 7.2%）；整理同步阻塞导致耗时 2.25 倍；摘要机制是多余的
（浓缩视图靠"整理后用户输入 + 事件索引"即可完成检索）。

## 2. 核心概念

### 2.1 Round（轮）与闭合规则

**一轮 = 用户的一条（或合并的多条）输入，到 AI 产出最终回答为止的完整过程。**

闭合规则（V2 修订核心）：

> **只有 AI 产出最终回答，Round 才闭合。** 中断、异常、无回复的尝试
> 都不闭合——期间的所有用户输入**并入同一个开放 Round**（原文各自
> 保留为事件），跨会话持久化。闭合时才做一次整理。

举例：网络中断，用户连发三条"继续"（AI 均无回复），网络恢复后 AI
完成回答——这四条输入 + 期间的所有事件 = **一个 Round**。整理时把
四条输入合并成一条澄清后的意图。空转的轮次不再产生任何整理成本。

### 2.2 Event（事件）与三层信息

Round 内每条协议消息登记为一个 Event，同时保存三层信息：

```text
Event
├── id / type / timestamp / status      ← 元数据
├── Truncated：Runtime 程序生成的概览（零 LLM 成本）
│     例：[R3-E05] 调用 read_file({"path":"src/icp.cpp"}) → 成功
│     例：[R3-E06] 失败，测试执行失败，3 个测试未通过
└── Full：原始协议消息（事实来源，永不修改）
```

截断规则：折叠空白取前 120 字符；优先保留动作、对象、结果、状态、
关键错误；`run_command` 等常用工具有专用规则（提取 exit_code 与错误行）。

### 2.3 整理产物（Organization 的输出）

每个闭合的 Round 额外拥有：

```text
Round
├── UserInput.Original   用户原文（可多条）
├── UserInput.Normalized 合并澄清后的意图（AI 生成，全量显示）
├── Events               Truncated + Full（如上）
├── RefinedIndex         精修事件索引（AI 重写的事件一行摘要，
│                        比 Runtime 截断更短更准，多数不触发 120 字上限）
└── （Round Summary 已取消——检索靠 Normalized 输入 + 索引即可）
```

## 3. 轮末整理 Organization（异步、轻量）

### 3.1 触发与执行

Round 闭合后，整理任务进入**后台单线程 FIFO 队列**，主对话立即继续——
**整理不占用任何等待时间**（它解决的是"下一轮之后"的事）。

- `chat` 模式：退出时若队列未清空，等待最多 10 秒（带状态行），
  未完成的 Round 标记 pending，**下次加载该会话时惰性补跑**
- `run` 模式（一次性进程）：退出前必须等队列清空，否则整理结果丢失

### 3.2 输入与输出（轻量化）

```text
输入：本 Round 的用户输入们（原文）+ 事件 Truncated 索引
     （不给原文——Truncated 已经够整理意图和补丁用）
输出 JSON：
{
  "normalized_user_input": "合并澄清后的用户意图（可扩写）",
  "refined_index": ["R3-E01 重写的事件一行摘要", "..."],
  "state_patch": { "completed": [...], "decisions": [...],
                   "known_issues": [...], "open_questions": [...],
                   "current_status": "...", "goal": "...", "is_done": bool }
}
```

因为不再产出过程长摘要、不再读原文（Truncated 够用）、可以关闭思考，
整理调用的成本从 V1 实测的每轮数万 token 降到一个很小的常数。

### 3.3 容错

输出剥代码围栏 → 取最外层花括号 → 解析失败**重试一次** →
仍失败则本 Round 保持 Runtime 视图（Truncated 兜底），状态不更新，
**原始层永远不受影响**。

### 3.4 举例

一轮 17 步的工具调用轮（ICP 调试），事件流截断索引为：

```text
[R5-E01] 用户：继续调试 ICP
[R5-E02] 调用 read_file({"path":"src/icp.cpp"}) → 成功
[R5-E03] 调用 run_command("pytest tests/test_icp.py") → 失败
[R5-E04] 调用 edit_file(...) → 成功
[R5-E05] 调用 run_command("pytest tests/test_icp.py") → 成功
[R5-E06] 最终回答：...
```

整理输出：

```json
{
  "normalized_user_input": "用户要求继续调试 ICP 配准误差问题（衔接上一轮），
     重点是让失败的测试通过",
  "refined_index": [
    "读取 ICP 源码定位误差来源",
    "运行 ICP 测试，3 个用例失败（变换矩阵初值问题）",
    "修改初值估计逻辑",
    "重跑测试全部通过"
  ],
  "state_patch": {
    "completed": ["ICP 测试修复：初值估计修正后全部通过"],
    "known_issues": []
  }
}
```

注意精修索引：**比 Runtime 截断行信息密度更高、长度更短**——
"运行测试，3 个用例失败（变换矩阵初值问题）"一行就浓缩了两条原始事件，
且天然不触发 120 字截断上限。

## 4. 加载模型（Context Assembly）

### 4.1 排序原则：越易变的越靠后

前缀缓存下，排在前面且不变的内容最便宜。因此按**变化频率**排序：

```text
[1] system 人设            （静态，永不改）
[2] 历史轮次浓缩视图        （少变：轮次闭合时成形，之后不可变）
[3] Task State + 话题表     （每轮变——放这里，只作废当前轮的少量缓存）
[4] 当前 Round 的事件       （追加式）
[5] 新的用户输入            （追加）
```

**为什么 Task State 必须放尾部**：它每轮都变。放在 system（头部）会让
每轮请求从第一个 token 起全部全价（50K 基座下每轮多付 ≈ 50K 全价，
成本翻 20 倍以上）；放在 [2] 之后，它每次变化只作废自己与当前轮
（约 8-10K）。

### 4.2 分层加载规则

对每一轮历史，按以下优先级决定加载哪一档：

```text
近 3 轮        → 档 0：全部消息原文（单条超长走安全阈值 2000 字符）
其余轮次       → 档 1：用户原文 + Normalized 意图 + 精修事件索引
预算不够       → 档 2：用户原文 + Normalized 意图（去掉事件索引）
再不够         → 档 3：一行话题行（[R12] ICP误差调试（已完成））
永远          → expand_history(ids, level) 可升级到任意档 / 原文
```

- **预算 = 窗口的 30%**（1M → 30 万 token），环境变量可按绝对值覆盖。
  按几十轮 × ~700 token/轮 的浓缩视图估算，几十轮内档 1 全量加载
  绰绰有余；**降档只在预算真实吃紧时发生**，相关性匹配仅作为
  降档时"保谁降谁"的排序依据，不是默认行为
- **话题表**：档 3 的一行行 `[R12] 话题词（状态）` 是模型了解
  "历史全貌"的窗口——它保证模型永远知道存在过什么，细节靠 expand
- 未闭合的开放轮：按其已有事件参与加载（跨会话同样生效）

### 4.3 举例：混合话题会话的档位分布

68 轮的会话：R1-R3 ICP 调试，R4-R6 UI 修改，R7 闲聊，
R8-R20 视觉算法重构，R21-R68 手眼标定（最近 3 轮 = R66-R68）。

```text
system：人设
档 1（预算内全量）：R1-R65 的浓缩视图
    ├ [R1] 用户：调试 ICP... ｜ 意图：修复配准误差 ｜ 索引：5 行
    ├ [R4] 用户：改按钮颜色 ｜ 意图：UI 微调 ｜ 索引：2 行
    ├ [R7] 用户：闲聊大模型 ｜ 意图：— ｜ （无实质事件，一行即完）
    └ ... 共 65 个浓缩视图
尾部：Task State（目标/已完成/已知问题…）+ 话题表已并入档 1 不重复
当前：R66-R68 全量原文 + 本轮用户输入
```

一次请求 ≈ 65 × 700 + 状态 1-2K + 近 3 轮全量 + 当前轮 ≈ **50K 左右**，
与实测感受吻合。

若用户此刻问"之前 ICP 的误差是怎么解决的"——R1-R3 的浓缩视图已在
上下文里；如果需要当时的**具体代码修改**，模型调用
`expand_history(["R2-E04"], level="full")` 取回原文（追加在尾部，缓存友好）。

### 4.4 举例：话题切换与"污染"问题

"前面讨论 UI、闲聊，现在写视觉算法"——在 V2 里这不是裁剪问题而是
**分辨率问题**：UI 轮次的浓缩视图只有几行（"改按钮颜色｜改好了"），
闲聊轮几乎为空，它们**不会干扰算法工作**；且它们的缓存前缀保持稳定
（降档只在预算吃紧时发生）。若用户希望彻底聚焦，两个现成手段：
开新会话（干净上下文），或未来版本的"聚焦模式"（手动把无关轮次降档）。
V2 不做自动的主题裁剪——预算自动降档已覆盖成本问题，
质量上的干扰被压缩到每轮几行，实测可接受。

## 5. Task State（增量 Patch）

- 字段：`goal / constraints / decisions / completed / known_issues /
  open_questions / current_status / is_done`
- Round Organization 的 `state_patch` 增量合并：列表追加去重、
  每类上限 **200 条**（`STATE_LIST_CAP`，超出淘汰最旧，History 可找回）、
  `current_status`/`goal` 覆盖、`is_done` 仅接受布尔
- 渲染为文本块放在 [3] 位置（每轮变化只作废尾部少量缓存），
  渲染预算 = 历史预算的 1/3

## 6. 对照组（baseline）：常规阈值压缩

- **完全按市面惯例**：全量追加；当累计输入达到 **80% × 1M = 80 万
  token** 时，一次 LLM 调用把较早的轮次压成摘要 + 保留最近 2-3 轮原文
- 阈值比例与绝对值均可配置（`WOVRA_COMPRESS_THRESHOLD` /
  `WOVRA_COMPRESS_AT_TOKENS`），便于大级别实验触发观察
- 无分层、无 expand、无 Task State 注入；时间线照常给人看
- 预期：在百万级窗口下压缩极少触发，成本随轮数二次增长——
  这正是对照组要证明的事情

## 7. 成本模型（复算指南）

```text
一轮输入（原始） ≈ 步数 × B + 新增增量
一轮输入（等效） ≈ 步数 × (B × 1/30) + 新增增量
B（加载基座）    ≈ system + Σ(历史轮浓缩视图) + TaskState/话题表 + 当前轮事件
```

实例（第 69 轮，17 步，每步 +0.5K，B=50K）：
原始 = 17×50K + 68K = **918K**；等效 ≈ **38K**。详见 1.3 的表。

基座 B 的构成是唯一的可控乘数——V2 的一切分层规则都是为了
"在信息完整性（话题表保证全貌）与 B 的体积（乘数）之间自动平衡"。

## 9. 与当前实现的差异（实现路线）

1. **轮闭合规则重做**：失败/中断不闭合，并入开放轮；跨会话持久化开放轮
2. **Organization 异步化**：后台 FIFO 队列；输出改为
   normalized + refined_index + state_patch（删除 round_summary）；
   输入降为用户输入们 + Truncated 索引
3. **装配重写**：近 3 轮全量（档 0）+ 更早轮次三档自动降档
   （预算 = 窗口 30%）+ Task State/话题表移至尾部
4. **baseline 阈值压缩**：80% × 窗口触发，摘要旧轮 + 保留最近 2-3 轮
5. **参数百分比制**：见第 8 节
6. 保留不变：expand_history（容错版）、审计、破坏性防护、
   展示层行纪律、成本核算

## 10. 已知限制与后续方向

* **整理队列的并发写**：单线程 FIFO 规避；多进程同时打开同一会话
  仍是 V2 的单写者假设
* **话题表在数百轮后的膨胀**：档 3 行本身会成为预算压力，
  届时按相关性/时间对档 3 再分层（V3 方向）
* **相关性匹配的召回**：换说法的场景靠 Normalized 意图的全量在档内
  缓解；彻底解决需要语义检索（V3 方向，当前明确不做）
* **步数失控**：轮内步数 × 基座的乘数关系提示需要"单轮步数预算"，
  超限强制收尾并请求人工介入（V3 方向）
