# Wovra 下一阶段：思想对齐与意图存档（活文档）

> 状态：**起草中**——对齐对话尚未说完，本文只负责忠实存档。
> 存档纪律沿用我们自己的结论：**最终做法可能推翻这里的一切表述，
> 但表达出来的、要实现的细节一条不能少。** 因此每一节写的是目标
> 展开（意图层），不是步骤处方（方法层）；方法层等真实任务把它
> 长出来。续写位置见 §7。

## 0. 这份文档是什么

V3（`context-management-v3.md`）封版后、下一阶段开工前的思想对齐
记录。按既定分工：**上层出假设、画边界；底层走路、长机制。**
本文是上层的那部分——假设与边界的存档，不含任何已实现或已承诺
的实现形态。

## 1. 方法论：从底层长出来

起点观察：现行这套方案不是一开始想出来的，甚至最初不会往这个方向
想。起点只是"先做出最初一版，一点点测试着往上加"，方向是被真实
失败一步步**逼**出来的；回头看，长出来的方案比当初想的都妙，而且
是统解——之前设想的很多专项机制（消息分类、内容取舍……）没有被
实现，而是被结构直接取代，连问题本身都消失了。

### 1.1 解决 vs 消解

* 上层想出来的是**方案**：回答"这个问题怎么做"，前提是问题真实
  且稳定。
* 底层长出来的是**结构**：回答"信息应该怎么流动"，不预设谁来问
  什么。
* 结构胜利的签名：打补丁之后问题清单少一条；换结构之后一群问题
  直接不存在。V3 的三次消解：
  1. 零截断 + 轮内赦免，消解了"该截多少"；
  2. 每轮重组 + 三档分辨率，消解了"消息怎么分类"——通用的语义
     分类器难写，不是智力问题，而是"类别"本身任务相对；出路不是
     更好的分类器，是让分类不再是需要回答的问题；
  3. 全量档案 + expand_history，消解了"压缩丢细节"。
* 基座税把散落的问题统一成一句：成本和延迟是同一个量的两张面孔。

### 1.2 底层生长能发生的三个前提

1. **迭代便宜**——CLI 工具，改一轮机制几小时；
2. **反馈诚实**——成本/命中率全落盘，失败藏不住（39 次重读、
   整理比干活贵、水位口径伪影，全是账本自己现形的）；
3. **领域立刻惩罚错误假设**——真实任务不留情面。

推论：**仪器先于实验**不是口号，是生长能发生的前提——没有诚实
的仪表，长出来的东西根本看不见。最初一版的品味也在这里：它决定
你能看见哪些失败。

### 1.3 上层的新角色

* 出**假设**——假设要便宜、可丢弃；
* 画**边界**——封版清单、"暂时不要急着解决"停车场、地图分区，
  都是自上而下的产物，作用是防止自下而上蔓延成野草。
* 一句话：**地图是上层画的，路是底层走的；地图可以改，走出来的
  路不能假装没走过。**

## 2. 设计原则（从三次消解里收敛）

1. **机制只做体量与时机决策（何时整理、何时折叠、基座多低），
   不做语义判断（什么重要、什么该删）——语义判断属于模型，发生
   在读取时刻。**
2. **排除性判断不做，累积性整理可以做。** TaskState 是边界样本：
   它也是"维护的方向"，但它是增量、可审计、可从历史重建的账本，
   不是过滤器。
3. **执行侧与上下文侧对称：不为未来做排除性判断。**
   * 上下文轴：写入时只描述现在，读取时决定分辨率（每轮重组）；
   * 行动轴：t0 只展开意图（计划 = 意图快照，见 §4），每轮从当前
     状态重算下一步。

## 3. 决策：不做 todo_write

传统 agent 的标配技能：先列出怎么做的清单，再按列表逐项执行。
Wovra 决定不做。理由：

1. **与消息分类同构**：todo 是执行侧的"写时固化判断"——用动手前
   最少的信息赌整个执行过程；清单一旦写下就积累权威，现实偏离后
   agent 仍倾向于 tick 它。
2. **它的两个真实功能已被覆盖**：
   * 跨长视野的目标保持 → TaskState.goal 每轮进装配；
   * 进度可见 → rounds/事件流本身。注意区别：TaskState 的
     "已完成"是**事后**写的（记录事实的累积账本），todo 是
     **事前**写的（固化预测的处方清单）。
3. **"复刻 Minecraft"式测试的正确读法**：更先进的模型功能更多
   但细节没做好（材质加载、正常行走），观感为 0；另一个功能少
   但基础处理好（行走、渲染没问题）反而胜。胜负手**不在有没有
   计划**——败者大概率也有 todo——而在两点：
   * **骨架优先**：先让最小闭环真的跑起来，深度优先，广度慢慢长；
   * **每轮可验证**：每轮闭合时留下一个能跑的状态（可运行闸门），
     不在没验证过的地基上叠功能。
   可运行闸门将来才值得长成机制，现在先是执行气质；它的天然土壤
   是 Runtime Governance（实验里 baseline 翻车的 Gradio 旧代码、
   端口孤儿，本质就是"没验证就往上盖"的代价）。
4. **待观察的失败模式**：完全没有计划工件时的**漂移**（干着干着
   忘了范围或质量底线）。若真实使用中出现，长出来的也应为**读时
   工件**（每轮从当前状态重算的下一步建议），不是恢复写死的 todo。
   出现之前不造它。

## 4. 计划的两层：意图快照 vs 方法处方

（用户修正："首先肯定是有计划"——计划有两层目的：
① 保证大方向不歪，一步步走向终点；
② 计划传递更多信息：以展开的形式更详细地描述目标。例：当初写的
分类计划，读了它不止知道分类如何做，还知道分类要解决的目标；即使
后来证明用别的方法更好，原计划传递的目标、要实现的细节基本都一致。
——最终方法可能不按说的做，但表达出来的细节一个不少。）

拆开看，计划里混着两层，寿命完全不同：

* **目标展开层**：要解决的问题、在意的细节、边界约束、验收长什么
  样。这不是对未来的预测，是**对现在的描述**——把模糊意图展开成
  可操作的文字。t0 时刻保真度最高（意图最新鲜、上下文最干净）。
  方法死了它不死。
* **方法路径层**：猜测的路线、步骤顺序。这才是会死的部分——对
  未来的赌博，现实一教就改。

todo_write 的原罪不是"写了计划"，而是**把两层压进同一个工件**：
步骤携带目标，方法死时目标陪葬；或方法靠沉没成本赖着不走，把目标
拖偏。

精确表述：**计划要写，但它是"目标的展开式"，不是"步骤的处方"。
方法层随时可弃，展开层持续传递。**

### 4.1 机制家族的第三个成员

"把模糊的意图展开成清晰的表述"这个操作已存在两次：

* Round 级：Normalized 用户输入（碎片原话 → 清晰意图）；
* 会话级：TaskState（散落历史 → 现状账本）；
* **任务级：计划 = t0 的意图快照**（本节新增）。

### 4.2 变化频率主轴（机制九的延伸）

机制九（变化频率决定位置）原来只管上下文布局，现在把任务结构也
管了——每层信息按自己的变化速度进对应的家：

```text
目标展开 / 验收标准   最慢（会话内近似不变）→ 进 TaskState，装配最前
决策 / 约束           中等 → TaskState 增量
方法 / 步骤           最快（随时被现实推翻）→ 每轮重算，不落盘为权威
事件                  立即 → 追加
```

### 4.3 "复刻用户过程"的完整形态

```text
t0：计划 = 意图快照（目标展开 + 粗路标 + 验收标准）
      → 目标层进 TaskState（goal / constraints / 验收）
      → 粗路标只当排序参考（骨架优先），不当承诺
每轮：从当前状态重算下一步，产物自证可用
方法死亡：organization 天然回收——死方法里仍成立的细节、教训、
      约束，由当轮整理补丁写回状态账本（现有管线承载）
方向漂移：goal 层可修订——它是最慢层，不是永恒层；
      修订走 TaskState 纪律：谁改、哪轮改、为什么，留痕
```

这样"计划保证大方向不歪"由目标层 + 验收标准免费提供；"传递更多
信息"由展开层完成；"一点点完善"由每轮重算承担——全程不需要
todo 列表。

## 5. 边界与检验清单（进入下一阶段前）

1. 任何新机制先过检验：它需要语义判断吗？需要的话，判断权能否
   推给读取时刻的模型？排除性的不行，累积性的可以。
2. 动"结构"（多 Agent）的门槛：只能从一个被证明的真实失败里长
   出来——某任务在单 Agent 栈里溺死，且死因明确是上下文混装了
   不兼容的职责。不是从"多 Agent 是趋势"长出来。

   > **现状更正（2026-09-11 用户拍板）**：这条门槛已被实际路径推翻。
   > 多 Agent 没有等"单 Agent 溺死"，而是作为**整理的副产品自然长出**：
   > 水位整理与分裂一体实现，从真实工作里析出职责域，注册表 + 分流
   > （notify / consult）在同一运行时内按职责切换视角。本质仍是
   > **单 Agent 分流**，不是同步并发的多 Agent。原文保留，作为当时的
   > 顾虑记录。
3. V3 封版重开条件照旧：真实使用打脸。停车场（相邻轮折叠、狠压）
   不动。
4. Wovra 定位问题（挂着）：定位是 runtime，目前唯一消费者是 CLI
   上的用户本人。何时需要第二张嘴（API / 被别的 agent 嵌入）？
   可能本身就是下一个真实痛点。

## 7. 组织架构：主 Agent / 子 Agent / 人（意图层存档）

> **落地状态（2026-09-11）**：组织架构已以"上下文分化"形态实现，
> 见 `context-differentiation-runtime.md`。子 agent = 注册表条目 +
> 上下文视图 + 路由规则（同一运行时内切换，不是并发进程）；主 agent =
> 路由器 + 默认执行者。以下需求层表述继续有效，形态以此为准。
>
> 存档纪律不变：最终形态可能推翻以下表述，但表达出来的需求细节
> 一条不少。以下全部是需求与原则，不是实现规格。

### 7.1 需求层（已逐条核对）

1. **用户通道永不被实现细节污染**：主 agent（总秘书）只对话、定
   方案、汇总子 agent 信息整理成文档；与用户深度绑定，从不主动做
   任务、不去深入细节。
2. **职责隔离取代分辨率调度**：任务拆给多个子 agent，各自只实现
   一块——结构性隔离取代降档模拟。
3. **切职责，不切视野**：子 agent 知道全局（用户需求、主 agent 的
   分析与拆解、任务分了几块、每块要实现什么），只被要求实现其中
   一块。视野裁剪 = 写时的排除性判断，不做。
4. **决策永远在信息最全的时刻做**：拆分重点是目标与需求 + 大概
   任务安排；最终要实现的是目标与需求，不是遵守任务安排——计划
   实施随实践动态修改；报告帮助主 agent 定期修改实施计划，尽量
   确保决策在更多信息知晓下做出，而不是事先信息最少时定死。
5. **目标下传、事实上传、方法不进传递**。
6. **分形缩放**：子 agent 也可以变成主 agent——不去实现具体任务
   细节，只负责汇报、维护任务、把细节再往下分。任何节点对上是子、
   对下是主，循环往复。
7. **人是根节点**：人的视野经常小于 LLM，人的命令本质是需求传递
   （计划安排只是需求本身，不是处方）；机器不可擅自做决定——实测
   不通要上报，帮助人修正决策。主 agent 最开始就可以和人讨论细化
   需求与安排；一线 agent 的真实细节传上来后，决策继续修正。

### 7.2 决策权与人的视野

* 决策权按**可逆性**划界：可逆的机器做、留痕供人否决；不可逆的、
  方向性的升级给人（与敏感命令确认"默认拒绝"同源）。
* 系统职责包含**补偿人的视野**：t0 主 agent 与人细化需求时，机器
  把决策空间整理成"人尺寸"的选项（有什么路、各自意味着什么、第
  一个里程碑能验证什么）；意图快照是**合著**的——人出需求与偏好，
  机器出展开，人批准。
* 失败不是状态报告，是**决策升级**：预期 / 现实 / 选项 / 影响面 /
  不拍板的后果（哪些分支停、哪些继续）。

### 7.3 报告：一次整理，三个视图

报告不设第二条整理管线——它是现有水位整理管线的副产品：

```text
            ┌─ 模型视图：装配进上下文（已有，每轮）
一次整理 ──┼─ 机器视图：子任务的 TaskState = 交给上级的报告（只新增读取）
            └─ 人视图：活文档 = 状态 + 升级队列 + 里程碑线的机械渲染（零 LLM 成本）
```

* 子→主的报告不用写：子任务的 TaskState + 事件索引就是报告；上级
  按事件 ID 跨任务钻取。报告的边际成本 ≈ 0（这笔整理费子任务为
  自己的上下文管理反正要付）。
* 主 agent 的"汇总整理成文档"不是新机制：子报告流入其历史就是
  普通事件，它自己的水位管线消化进自己的 TaskState。**层级之间
  不新增整理调用。**
* 人看的报告是机械渲染的活文档，随时可看、零 LLM 成本；通知只是
  零内容信号（"有决策等你拍板"）。
* 综合文档低频、事件驱动（里程碑 / 水位 / 人索要），走
  organization 账户——**报告水位镜像整理水位**。
* 决策升级是状态账本的一等公民：内容由整理补丁维护（模型写），
  呈现机械渲染（程序做）——语义归模型、体量归机制，原则继续
  成立。升级模板字段从第一现场长。
* 人拍板 = 一轮新输入；改 goal 走修订留痕；异步友好——人不在线
  时树跑别的分支，升级在队列里等。

### 7.4 人视图的分辨率调度

人喜欢看总体大局决策，但保留追求细节的途径：**大局默认，一层层
剥开去展开；默认不含所有细节（例如每次工具调用返回了什么），但
永不卡死**——"小癖好"保留。这是机制八（分层加载）的人类版：分辨
率按视图主人调度，展开权在人。默认不呈现不是排除——细节永远可
剥开，不做排除性判断这条纪律连 UI 也管。

### 7.5 组织架构的动态性

* **组织架构跟着每轮任务变更运行时调整**：解散一个部门、新成一个
  部门、降级升职，都是常态——从不一个决策用到死。组织结构属于
  方法层（快变量），不是目标层。
* 递归终止条件（单一职责 + 单上下文装得下 → 叶子）只是**默认
  启发**，不强求：模糊分不清的任务，先比较"继续拆分收益大还是
  直接做收益大"；若信息不足或差异不明显，两条路都有收益、影响
  不大——**不为低 stake 的分叉花决策成本**（这条本身也是一条
  决策纪律）。
* 解散 ≠ 删除：部门清算 = 状态账本合并回父级，历史不删（原始
  历史不可变，同一条纪律）。
* 重组便宜的原因：意图快照逐字下传、每层只追加——新部门的入职
  = 挂载不可变快照 + 附加父级当前视图，没有转述损耗。

### 7.6 生长式执行与人作为仪器

* 复杂任务**不是一开始就一块块划分去做**：模仿 Wovra 自己的发育
  过程——从最简单开始，一点点长出每个功能，**每个功能都是实验
  逼迫出来的**。开发 Wovra 的方法论成为 Wovra 执行任务的方法论
  （过程自相似）。
* 纪律：**每一阶段都是好的**；不追求高大楼层，追求每一步走得稳
  （"复刻 Minecraft"例子里胜者的策略，成为执行价值观）。
* 机器无法闭环验证时（看不见 UI、要真实手感、要人判断"好不好"），
  **教导用户去实验**：给零基础也能看懂、起了作用的指引——做什么
  （可复制粘贴）、看什么、什么算对、把什么反馈回来。人由此成为
  验证闭环里的传感器。
* 人机协同报告因此有第四个栏目：**待办实验**（当前阶段需要人验证
  什么），由每轮整理补丁维护——第四个"零新增管线"的受益者。
  按水位攒批（人是最稀缺资源，不逐轮打扰）；人不在场时该分支
  暂停、跑别的分支，与升级队列同款处理。
