# 块标签定义 v1（初版）——标签如何辅助整理

> 设计原则（我的猜测，待用户确认）：
> **标签 = 整理分辨率与内容焦点的指令，不是重要性评分。**
> 模型整理时按标签写——标签决定"写多细、写什么"，模型不做
> "哪些重要"的判断。这消除了"应该怎么写"的思考（当前 org 15K
> 思考撞输出上限的病根），把详略完全收敛到 Runtime 定的标签上。

## 分辨率分级

| 级别 | 含义 | 对应块/标签 |
|---|---|---|
| 全量 | 原文级，不降分辨率 | 用户输入（轮头 + 用户块） |
| 高 | 结构/设计/差异，写得充实 | 创建 / 重构 / LIVE |
| 中 | 改了什么、为什么、影响 | 修改 / 读 |
| 低 | 结论与原因，细节从简 | 删除 / 只读 |
| 一句话 | 失败事实，一句带过 | 幽灵 / 越界 |
| 结论 | 只写结论 | 保底块 / DEAD |

## 文件块标签 → 整理指令

| 标签 | 分辨率 | 整理时写什么 |
|---|---|---|
| 创建 | 高 | 文件用途、整体结构、核心设计思想（骨架级） |
| 重构 | 高 | 重写动机、与旧版的关键差异、现在的结构（差异是重点） |
| 修改 | 中 | 改了什么实现、为什么改、影响什么 |
| 读 | 中 | 为什么读、读出的关键结论（服务于后续的写/改/删） |
| 只读 | 低 | 文件用途/大致结构；需要细节时重新读 |
| 删除 | 低 | 删了什么、为什么删、最终结论 |
| 幽灵 | 一句话 | 文件不存在，读失败（错误路径测试/误读），无实质内容 |
| 越界 | 一句话 | 尝试访问越界路径被安全拦截，读/删未发生 |

多标签组合（如「创建，读，删除」）：按标签逐项写，每项按各自分辨率；
同块多标签不互相挤占，短的标签一两句即可。

## 文件块整理规则（补充，2026-09-09 用户拍板）

文件块 = 根据块标签与状态，把块内内容**综合总结成一段话**：

1. **一段话**，不拆条、不堆标签——标签和状态是给整理者的**提示**，
   不是输出内容；输出是连贯的一段叙述；
2. **以生命周期标签为骨架**：创建/重构/修改/读/删除按时间序交代
   这个文件块里文件经历了什么（从哪来、做了什么、结果如何）；
3. **辅助工具调用结果的阐述**：块内吸收的工具调用（测试/验证/命令）
   把**结果**融进叙述——"改了 X，跑 pytest 验证通过"这种因果链
   是必须的，不能只写动作不写结果；
4. **按状态决定叙述重心**：LIVE 写清当前有效内容/结构（这是现状）；
   DEAD 收在死亡原因与最终结论；HISTORICAL 保留演化关系与关键原因；
5. **交代清楚这个文件块的内容**——读完这一段，读者（后续轮次的
   模型）应该能知道：这个文件在本块发生了什么、现在处于什么状态、
   有什么可复用的事实。

例子（示意，非格式约束）：

    创建：index.html 建立 Three.js 场景容器与 HUD 骨架，三块面板
    （世界/控制台/资产）分区明确；随后 edit 调整了视口高度以适配
    移动端，headless chrome 截图验证渲染正常（DOM 检查通过）。

## 工具标签 → 整理指令

| 标签 | 含义 | 整理时写什么 |
|---|---|---|
| 工具 | 本轮单文件块，工具调用确定服务该文件 | 把块内工具调用并入描述：为什么调用 + 结果结论 |
| 工具? | 本轮多文件块，工具归属不确定 | 描述时留意块内是否混有工具调用，有则写出其意图与结论 |

## 状态后缀 → 详略底线

| 状态 | 整理时写什么 |
|---|---|
| LIVE | 保持当前有效状态——内容/结构写清楚，这是现状，后续工作基于它 |
| HISTORICAL | 保留演化关系与关键原因（被取代的旧文件） |
| DEAD | 只保留死亡原因与最终结论，不写细节 |

## 块类型 → 整理指令

| 块 | 整理时写什么 |
|---|---|
| 用户块 | 全量保存：用户被打断后补充/修正了什么、插在哪段工作之后 |
| 环境块 | 为什么做环境准备（目的）+ 结果 |
| 保底块 | 助手结论，简练一段 |

## 用户输入（轮头）——沿用之前

👤 用户：原文；🎯 意图：澄清后的意图；📌 关键约束：红线/硬性约束。
用户输入永远是最高关注，全量保存意图+梳理+约束。

## 块顺序

按块内**第一次交互**在事件流中的时间顺序排序；一轮内多次穿插交互
（A 写 → B 写 → A 改）不重排，就按第一次交互的顺序。

## 待定（等用户细化）

* 幽灵/越界是否各自再分"读幽灵/删幽灵"还是统一；
* HISTORICAL 的触发（move/重构替换时）是否本轮落地；
* 工具? 在整理指令里是否需要"逐块核对"的强约束。
