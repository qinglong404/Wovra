# Wovra 上下文管理机制 V3（实验修正版 · 机制基线）

> 定位：V3 不是一份"足够严谨的压缩方案论文"，而是**经过真实长任务与
> 真实 Runtime 问题反复打磨后的第一版机制基线**——假设 → 实现 → 真实
> 运行 → 失败 → 定位 → 修机制 → 再运行，每个关键机制都走完了这个循环。
> 核心机制自本文起**封版**：后续探索沿地图分区推进（见 §8），不再往
> V3 里塞东西。
>
> 证据链：11 轮观察性对照（`managed-vs-baseline-11rounds.md`）、R11
> 三代机制实验（`round11-context-experiment.md`）、两组受控多轮实验
> （本文 §1，会话 `8ecd11` managed / `02d81f` baseline，Gradio 项目
> "按清单实现 10 个功能"真实任务）。
> 阅读前提：`context-management-explained.md`（机制科普版）。

## 0. 一页结论

实验把我们从三个想当然里打醒，V3 是修正后的定稿：

1. **"截断省 token"是幻觉**——折叠时代 39 次重读、2KB 锁孔时代 11 次
   读取全部沉没；执行期零截断后，同量级任务 3 次读取完成。省下的
   token 会被"重读 + 返工"加倍买回来。
2. **"命中率至上"是错的**——baseline 全量回放命中率高达 99.3%，但
   臃肿基座上的高命中照样贵。正确的优化对象是**基座**：每步等效成本
   ≈ 新增 + 基座/折扣率，命中率只是折扣的深度。
3. **"每轮必整理"是过早优化**——轻轮的整理费（3,118）比轮本身的
   干活成本（2,816）还高；14 轮整理共 98K，把 managed 在等效成本上的
   全部优势吃回去了。V3 改为**水位触发的批量合并整理**。

一句话：**执行期零截断，管理看基座，整理按水位，命中率只做诊断。**

## 1. 实验证据总览

受控实验：同一 Gradio 项目、同一冻结起始文件（1003 行原版页面）、
同一任务书（按清单逐轮实现 10 个功能）、同一模型。A = managed，
B = baseline，会话级 ABBA。

| | A managed（14 轮） | B baseline（15 轮） | B/A |
|---|---:|---:|---:|
| 名义 token | 2,255,448 | 4,966,437 | **2.20×** |
| 等效输入（不含管理） | 377,668 | 475,686 | 1.26× |
| 整理/压缩开销 | 98,111 | 0 | — |
| 含管理的等效成本 | ≈475,779 | ≈475,686 | **≈1.00×** |
| 步数 | 112 | 153 | 1.37× |
| 上下文峰值 | 57,472 | 66,456 | 1.16× |
| 工具报错事件 | 10 | 16 | — |

（更早的 11 轮观察性对照同向：总量 1.49×、纯对话轮 4-5×。）

三条必须诚实说明的背景：

* **本实验是轻中度负载**：上下文峰值只到窗口的 3.0%（A）/ 6.6%（B），
  从未触发压缩线。V3 机制的重度优势（§4）在这轮里只露了头，没充分展开。
* **任务为工具密集型**：大文件反复读写使"轮内工作集"在两侧上下文中
  占主导，稀释了历史携带的差异。
* **n=1、无验收快照**：产出质量靠人工判断（两边最终功能均可用），
  B 多一轮是修 bug 轮（Gradio 6 消息格式 + 端口孤儿）。

**效度定位**：V3 不能当成"严格实验的性能结论"（n=1、无重复、轨迹
不完全一致），它是**经过真实长任务打磨的机制基线**——每个关键机制
都有实测依据，但数字本身留待受控重复实验校准。

## 2. 核心修正：从"减少 token"到"四方调度"

实验最大的收获不是省了多少 token，而是**优化目标变了**。天真的模型：

```text
上下文管理 = 压缩上下文 → token 变少 → 省钱
```

实测跑出来的是：

```text
压缩/截断上下文
  ↓
信息丢失 → Agent 重读 → Tool Call 增加
  ↓
Steps 增加 → Token 反而增加
```

所以 V3 的定义是：

> **上下文管理 = 在"信息完整性、工作集大小、组织成本、缓存成本"
> 四者之间做调度。** 这已经高于单纯的 Summary / Truncation / RAG。

**基座税公式**：每一步的等效成本 ≈ 新增 token + 基座/折扣率。
命中率决定**折扣**，基座决定**税基**。两组实测从相反方向验证：

* **B（baseline）证明折扣的威力**：R13 单轮 592,560 prompt，命中率
  99.3%，当轮等效仅 ~5K。全量回放的纯追加结构是完美的前缀缓存布局。
* **A 的高峰值轮证明税基的可怕**：R15（B）31 步、上下文 66K、命中率
  96.4%，当轮等效仍 ~118K——96% 的折扣救不了一个臃肿的税基。

**修订（2026-09-05）：折扣深度是服务商参数，且横跨整个行业——
从 1/40 到 1/5，差 8 倍。** 本文初稿按 DeepSeek 的 1/30 计算，得出
"含管理成本后打平（1.00×）"。用两组实验的命中/未命中数据，把 B/A
等效成本比值作为折扣率的函数重算：

| 缓存折扣（行业光谱） | A 等效 | B 等效 | B/A | 含整理开销 B/A |
|---|---:|---:|---:|---:|
| 1/40（Claude Fable/Mythos） | 362,257 | 437,721 | 1.21× | 0.95× |
| 1/30（DeepSeek 空闲时段） | 377,668 | 475,686 | 1.26× | 1.00× |
| 1/15（DeepSeek 高峰时段） | 439,313 | 627,545 | 1.43× | 1.17× |
| 1/10（OpenAI / Claude / Gemini / Kimi K3） | 500,957 | 779,405 | 1.56× | 1.30× |
| 1/5（GLM-5.3-Flash / Kimi K2.6） | 685,892 | 1,234,982 | **1.80×** | **1.58×** |

三个结论：

1. **行业主流是 1/10**——在这个最常见的折扣下，managed 的等效成本
   优势是 **1.56×**（含整理 1.30×），不是初稿算出的打平；
2. **折扣越浅，基座税越重**：GLM/K2.6 一档（1/5）下优势扩大到
   1.8×；最深的 1/40 下 managed 含整理开销反而略亏（0.95×）——
   **任何"打平/领先"结论都必须标注折扣深度**；
3. **折扣为零的极限是 1.025×**：即使缓存完全无优惠，managed 也只
   略输于 baseline——baseline 零管理成本，managed 的 98K 整理费是
   它的结构性代价。**managed 的盈亏平衡点在折扣 ~1/25 附近**：比这
   更深的折扣（DeepSeek 空闲、Claude 新系）里整理结构化视图是净
   支出，比这更浅（行业主流 1/10）里是净收益。

**补充（2026-09-06）：Claude 的定价暴露了第四项成本——缓存写入溢价。**
Claude Fable 5.1 的完整结构：基础输入 $10 / 命中 $0.25（1/40）/
**5 分钟缓存写入 $12.50（1.25×）** / **1 小时缓存写入 $20（2×）** /
输出 $50（5× 输入价）。成本模型因此升级为三项：

```text
每次请求 = 未变化前缀 × 命中价
         + 变化的前缀段 × 写入溢价
         + 新增 token × 原价
输出另计（本例 5× 输入价）
```

两个直接后果：

1. **写入溢价惩罚上下文搅动**——managed 每轮重写的装配尾部不只是
   "缓存失效"，在 Claude 定价下还要按 1.25× 重新写入。V3.x 的
   "追加稳定尾部"方向又多了一个独立的经济学依据；
2. **1 小时缓存写入是"隔夜冷启动"的解药**——长时运行的会话付 2×
   写入费，中断数小时后的第一轮仍可命中，避免整基座重新按原价
   付费。这是产品层可以直接利用的定价选项。

（代码已支持 `WOVRA_CACHE_RATE` 配置命中折扣；写入溢价暂未建模，
重负载场景值得纳入。）

**推论**：当基座涨到一定程度，"破坏一次缓存、把基座压低"比"维持
高命中"更省——压缩/整理本质上就是**主动的、一次性的缓存破坏**，
用它换取之后所有步骤的低税基。何时破坏（§4 触发器）、破坏后基座
压多低（整理质量），才是管理机制真正的决策点。

**现金成本对照（2026-09-06，命中模型 v2）：29 轮真实生产数据，回放口径**
（`scripts/realdata_three_mechanisms.py`，同账本按两套价目表结算）。

命中模型 v2 修正了 v1 的保守偏差：轮内追加式两种模式**同构**，轮内
首发 miss 直接取实测 3.5M 按轮内容量分摊（真实摩擦对 managed 只多
不少）；managed 的额外 miss 只有**每轮一次**的装配重组——近 2 轮
全量换位 + 尾部重写，一次性计价，不按步摊派。修正后 managed 命中率
**93.6-94.0%**（baseline 实测 98.7%，差距即重组本身）：

| | DeepSeek 空闲（0.05 / 1.5 元/M） | GLM 半价（0.115 / 0.4 元/M） |
|---|---:|---:|
| baseline 全量回放 | 18.92 元 | 32.35 元 |
| managed 现行 | 12.76 元 | 12.21 元 |
| managed V3 水位 | 12.63 元 | 12.17 元 |
| managed V3 狠压（索引压到原文 2%） | 12.31 元 | 11.45 元 |

* **两种价位下 managed 都赢**：GLM 2.65-2.83×，DeepSeek 空闲
  1.48-1.54×。深折扣下 managed 用 4.7 个百分点的命中率换 3 倍的
  基座缩小，仍是净赚——"深折扣里整理是净支出"只在轻负载（受控
  实验，基座本来就小）成立；**负载越重、基座税越大，管理越值钱**，
  两个数据集是同一公式在不同税基下的解。
* **渲染深度是下一个杠杆**：水位触发（v3 vs cur）在这条负载上几乎
  中性（整理费 145K→78K）；把合并索引压到原文 2%（ZCode 44× 锚点
  量级）再省 ~6%，且重组点之前的前缀照常命中——**压得更狠几乎没有
  额外缓存代价**，代价只落在质量维度（需要时 expand_history 取回，
  由文件地图 + 零截断 Full 存档兜底）。
* **保守边界**：结论要求 managed 命中率 ≥ ~89%——重组摩擦比模型
  估计放大 3.4 倍才会翻盘。最终以带落盘命中的长会话实测校准
  （`WOVRA_CACHE_RATE` 已可按服务商/时段切换）。

**时间维度（2026-09-06 实测补充）：基座同时是延迟乘数。**
真实体感锚点：上下文 ~80 万 tok 时首 token 延迟近 1 分钟；压缩到
1.8 万后仅 ~3 秒（~20×）。机制：prefill 时间 ≈ 未命中 token ÷ 吞吐
——缓存折扣保护**成本**，却不保护**时间**：TTL 过期、服务重启、
空闲时段切换后的冷启动要按全量基座重算 prefill（与 Claude 1h 缓存
写入的"隔夜冷启动解药"同属冷启动经济学）。基座因此有两张面孔：
每步计费的**成本乘数** + 每步等待的**延迟乘数**，agent 循环步数
越多，后者越致命。managed 的低基座于是同时是**延迟保险**：稳态
~50K 即使冷启动也只有秒级。已知的时间代价在会话开头——降档历史
可能多几次工具往返（expand_history / 补读），由文件地图与锚点
自愈压到最低（实测 39 次重读 → 3 次）。**时间与成本并列为后续
机制的优化目标**——两者共用同一个决策变量：基座压多低、何时破坏
缓存。

## 3. 机制定稿（已实现，封版）

### 机制一：执行期零信息分辨率损失（轮内赦免）

固定表述：**执行期不主动降低当前工作上下文的信息分辨率；信息管理
发生在 Round 结束后的历史整理阶段；只有接近模型上下文上限时，才做
窗口级保底处理。**

三代机制的实测证据：

| 迭代 | 机制 | 实测结果（同一"加功能"任务） |
|---|---|---|
| 第一代 | 轮内折叠（50 事件软限制） | 39 次 read_file 重读同一文件，40 步上限烧完未完成 |
| 第二代 | 无折叠 + 2KB 安全截断 | 11 次读取每次只见前 2KB，全部沉没 |
| 第三代 | **零截断 + 窗口保底** | 3 次读取（理论最小值），一轮完成 |

这条表述固定下来——它预先回答了"上下文爆了怎么办"：有窗口保底，
不靠执行期截断。

### 机制二：窗口保底（唯一的天花板）

当前轮估算超过 `context_limit × 90%` 时，最老的事件折叠为索引行
直到回线。轻中度负载永远碰不到（本实验峰值 6.6%）；它是最后手段
而非常规机制。

### 机制三：文件地图与锚点自愈

* **文件地图**：降档历史中的文件以"路径 + 写/读轮次"清单注入装配，
  模型精准定位，不再盲目重爬（实测：39 次重读 → 3 次读取）；
* **锚点自愈**：edit_file 未命中时给出最接近内容的行号，成功时回显
  行号，文件不存在时报出解析路径——模型一次修正，不再整文件重读
  （实测一轮 6 次失败的主因）；
* **过期保护**：文件被外部修改后拒绝按旧内容编辑。

### 机制四：后台任务的会话化治理

后台进程记录启动会话；跨会话查看/停止被拒；会话退出时该会话的
后台进程一并整树关闭（keep_alive 常驻除外）。实测教训：baseline
对照组因"旧服务占端口 + 无归属管理"多烧了一整轮（1.75M tok，
全场最贵单轮）。

### 机制五：成本核算的完整落盘

步数、上下文峰值、名义/等效 token、命中率、整理成本——全部逐轮
写入 task.json。**没有这套核算，§1 的所有结论都不存在。** 仪器先于
实验，实验先于优化。

## 4. 机制五：水位触发的批量合并整理（已实现，封版）

v2 规则"轮闭合即整理"的实测账目：14 轮整理 98,111 tok，约 7K/轮；
R2 干活 2,816、整理 3,118——**整理比干活贵**。V3 规则：

* 轮闭合后**不再立即整理**，未整理轮的原始内容体量进入"整理水位"；
* 水位超过阈值 → 触发整理；
* 小会话可能全程不触发——整理成本归零，早期不再有负优化。

**落地参数（2026-09-06，刻意保守，留待实践修正）**：

> **修订（2026-09-07，用户拍板，已实现）：水位口径改为当前上下文窗口
> 体量。** 触发条件 = 最近一次装配的体量估算（轮闭合时即本轮峰值）
> ≥ `WOVRA_ORG_WATERMARK` 且本轮已闭合，替代下文的"未整理积压量"
> 口径。同时整理产物（精修索引 / Normalized / 状态补丁）先写入暂存区，
> **下一轮开启时才生效**——本轮对话期间的装配纹丝不动（连贯性 +
> 缓存前缀稳定），整理过程对用户完全静默（不再播报"后台整理中"）。

* `WOVRA_ORG_WATERMARK`（默认 100,000）：未整理轮的原始内容体量
  阈值（正文 + 工具参数，与窗口保底同一估算器）；2026-09-09 用户
  拍板批次上限删除——到水位一次性收编全部未整理轮，不再分批；
* **run 模式**（一次性进程）退出前补一批整理（`organize_backlog`），
  TaskState 才能跟上下一次自主推进；**chat 模式**保持惰性——遗留的
  pending/failed 轮天然计入水位，加载时不立即补跑。

**批量合并整理**（触发后的执行方式）：把所有未整理轮一次批量处理——

* 调用次数：N 轮 N 次 → 1 次（摊薄）；
* 跨轮去重：模型每轮重复交代的决策/背景，合并 State Patch 时
  天然去重；
* Normalized 意图：本轮落地为**逐轮意图**（渲染结构与事件 ID 的
  1:1 映射不变）；相邻轮折叠成同一工作脉络放 V3.x（§5 边界）；
* **可展开性不变**：事件 ID（R{k}-E{nn}）不受合并影响；未整理轮
  由 Runtime 机械索引行渲染（程序生成、零成本），整理只升级视图
  质量，不影响降档机制运转。

**水位阈值不要追求理论最优**——不同任务的最优值不同，陷入
70%/72%/68% 的参数调优是局部陷阱。V3 只需要一个大致合理的区间；
前瞻性决策留给 V4/V5：

> 整理是否值得 ≈ （基座 − 整理后基座）× 预计未来步数 / 30
> 　　> 整理成本 + 缓存重建成本

**整理质量的经验锚点（2026-09-06）**：一个生产级编码 Agent 在 ~80%
窗口处把约 80 万 tok 的会话一次性压缩到 **1.8 万 tok（~44×）**，
压缩后任务无缝续跑（触发点也印证了 80% 窗口线）。这说明"维持继续
工作所需的最小状态"可以低到 ~2 万 tok——远低于逐轮降档视图的 10%
比率。Wovra 不追求 44×：一次性有损压缩正是三代实验里重读螺旋的
根源，逐事件索引 + Full 存档是底线；但批量合并整理（跨轮去重 +
意图合并）应把"整理后基座"从"逐轮降档视图"进一步压向"工作状态 +
合并索引"的最小集。

## 5. 合并整理的边界与后续方向（V3.x）

**原则：合并的是"上下文视图"，不是原始历史。**

R1/R3/R5/R7 可以在整理视图里折叠成同一个工作脉络（如"ICP 误差
排查"），但每轮原文与事件 ID 原样保留——"这个参数是哪次测的？"
依然能精确回到 R3。

实现上**不引入** embedding / 聚类 / 向量库：先用时间邻近 +
Normalized 意图 + 状态字段分簇就足够。这一方向放 V3.x，不为它
提前复杂化。

## 6. Runtime Governance：实验踩出的下一个区域（独立方向，不并入 V3）

这轮实验暴露的大量问题根本不在上下文管理本身：Gradio 进程占端口、
服务重启后跑旧代码、文件被外部修改、代理 Fake-IP、依赖装错环境……
它们造成同一条因果链：

```text
Runtime 不可靠
  ↓ Agent 反复排查 Runtime 问题
Steps 增加 → Context 增加 → Token 增加
```

**好的 Runtime 本身就是上下文优化。** 这条因果链值得成为 Wovra 的
一个独立机制方向（Runtime Governance）。已落地的部分：后台任务会话
归属与退出清理、敏感命令确认、文件过期保护、原子落盘、子进程编码
统一——它们既是安全问题，也是上下文质量问题。

**但不把这些塞进 V3**——什么都能管的代价是没有任何机制被真正验证。
Runtime Governance 的系统化放下一阶段，解决真实踩出来的问题。

## 7. 缓存的三层优化框架（定位修正）

不写"缓存不重要"，写**分层**：

```text
第一层  减少不必要的上下文           → 降基座（主税基）
第二层  保持上下文追加稳定           → 提命中率（折扣）
第三层  合理安排整理/展开的时机      → 避免无意义的缓存破坏
```

最终形态是**低基座 + 高命中**，不是二选一。V3 已完成第二层的口径
修正（命中率 = 诊断指标）；第一层靠机制一/三/四；第三层是 V4/V5 的
研究问题——"什么时候值得主动破坏缓存"比"怎么提高命中率"更有意思。

## 9. 封版清单

## 一段话总结

V3 的全部修正来自同一个顿悟：**缓存命中率是折扣，基座才是税基；
执行期的截断是在省折扣钱的同时放大税基。** 所以：执行期零截断、
轮内赦免，让模型看到它该看到的一切；管理的唯一职责是在水位到线时
把基座批量折叠到低位——一次破坏缓存，换取之后每一步的低税基；
命中率从此只用来诊断，不用来讨好。而折扣的深度（行业光谱 1/40 到
1/5）决定这一切的金额——折扣越浅，管理越值钱；这条光谱本身，就是
Wovra 存在的价格学依据。而这次实验还揭示了第二层：
**Runtime 的可靠性本身就是上下文优化**——那是地图上的下一站。
