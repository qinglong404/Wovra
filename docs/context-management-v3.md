# Wovra 上下文管理机制 V3（实验修正版 · 机制基线）

> 定位：V3 不是一份"足够严谨的压缩方案论文"，而是**经过真实长任务与
> 真实 Runtime 问题反复打磨后的第一版机制基线**——假设 → 实现 → 真实
> 运行 → 失败 → 定位 → 修机制 → 再运行，每个关键机制都走完了这个循环。
> 核心机制自本文起**封版**：后续探索沿地图分区推进（见 §8），不再往
> V3 里塞东西。
>
> 证据链：11 轮观察性对照（`managed-vs-baseline-11rounds.md`）、R11
> 三代机制实验（`round11-context-experiment.md`）、两组受控多轮实验
> （本文 §1，会话 `8ecd11` managed / `02d81f` baseline，Gradio 项目
> "按清单实现 10 个功能"真实任务）。
> 阅读前提：`context-management-explained.md`（机制科普版）。

## 0. 一页结论

实验把我们从三个想当然里打醒，V3 是修正后的定稿：

1. **"截断省 token"是幻觉**——折叠时代 39 次重读、2KB 锁孔时代 11 次
   读取全部沉没；执行期零截断后，同量级任务 3 次读取完成。省下的
   token 会被"重读 + 返工"加倍买回来。
2. **"命中率至上"是错的**——baseline 全量回放命中率高达 99.3%，但
   臃肿基座上的高命中照样贵。正确的优化对象是**基座**：每步等效成本
   ≈ 新增 + 基座/30，命中率只是折扣。
3. **"每轮必整理"是过早优化**——轻轮的整理费（3,118）比轮本身的
   干活成本（2,816）还高；14 轮整理共 98K，把 managed 在等效成本上的
   全部优势吃回去了。V3 改为**水位触发的批量合并整理**。

一句话：**执行期零截断，管理看基座，整理按水位，命中率只做诊断。**

## 1. 实验证据总览

受控实验：同一 Gradio 项目、同一冻结起始文件（1003 行原版页面）、
同一任务书（按清单逐轮实现 10 个功能）、同一模型。A = managed，
B = baseline，会话级 ABBA。

| | A managed（14 轮） | B baseline（15 轮） | B/A |
|---|---:|---:|---:|
| 名义 token | 2,255,448 | 4,966,437 | **2.20×** |
| 等效输入（不含管理） | 377,668 | 475,686 | 1.26× |
| 整理/压缩开销 | 98,111 | 0 | — |
| 含管理的等效成本 | ≈475,779 | ≈475,686 | **≈1.00×** |
| 步数 | 112 | 153 | 1.37× |
| 上下文峰值 | 57,472 | 66,456 | 1.16× |
| 工具报错事件 | 10 | 16 | — |

（更早的 11 轮观察性对照同向：总量 1.49×、纯对话轮 4-5×。）

三条必须诚实说明的背景：

* **本实验是轻中度负载**：上下文峰值只到窗口的 3.0%（A）/ 6.6%（B），
  从未触发压缩线。V3 机制的重度优势（§4）在这轮里只露了头，没充分展开。
* **任务为工具密集型**：大文件反复读写使"轮内工作集"在两侧上下文中
  占主导，稀释了历史携带的差异。
* **n=1、无验收快照**：产出质量靠人工判断（两边最终功能均可用），
  B 多一轮是修 bug 轮（Gradio 6 消息格式 + 端口孤儿）。

**效度定位**：V3 不能当成"严格实验的性能结论"（n=1、无重复、轨迹
不完全一致），它是**经过真实长任务打磨的机制基线**——每个关键机制
都有实测依据，但数字本身留待受控重复实验校准。

## 2. 核心修正：从"减少 token"到"四方调度"

实验最大的收获不是省了多少 token，而是**优化目标变了**。天真的模型：

```text
上下文管理 = 压缩上下文 → token 变少 → 省钱
```

实测跑出来的是：

```text
压缩/截断上下文
  ↓
信息丢失 → Agent 重读 → Tool Call 增加
  ↓
Steps 增加 → Token 反而增加
```

所以 V3 的定义是：

> **上下文管理 = 在"信息完整性、工作集大小、组织成本、缓存成本"
> 四者之间做调度。** 这已经高于单纯的 Summary / Truncation / RAG。

**基座税公式**：每一步的等效成本 ≈ 新增 token + 基座/30。
命中率决定**折扣**，基座决定**税基**。两组实测从相反方向验证：

* **B（baseline）证明折扣的威力**：R13 单轮 592,560 prompt，命中率
  99.3%，当轮等效仅 ~5K。全量回放的纯追加结构是完美的前缀缓存布局。
* **A 的高峰值轮证明税基的可怕**：R15（B）31 步、上下文 66K、命中率
  96.4%，当轮等效仍 ~118K——96% 的折扣救不了一个臃肿的税基。

**推论**：当基座涨到一定程度，"破坏一次缓存、把基座压低"比"维持
高命中"更省——压缩/整理本质上就是**主动的、一次性的缓存破坏**，
用它换取之后所有步骤的低税基。何时破坏（§4 触发器）、破坏后基座
压多低（整理质量），才是管理机制真正的决策点。

## 3. 机制定稿（已实现，封版）

### 机制一：执行期零信息分辨率损失（轮内赦免）

固定表述：**执行期不主动降低当前工作上下文的信息分辨率；信息管理
发生在 Round 结束后的历史整理阶段；只有接近模型上下文上限时，才做
窗口级保底处理。**

三代机制的实测证据：

| 迭代 | 机制 | 实测结果（同一"加功能"任务） |
|---|---|---|
| 第一代 | 轮内折叠（50 事件软限制） | 39 次 read_file 重读同一文件，40 步上限烧完未完成 |
| 第二代 | 无折叠 + 2KB 安全截断 | 11 次读取每次只见前 2KB，全部沉没 |
| 第三代 | **零截断 + 窗口保底** | 3 次读取（理论最小值），一轮完成 |

这条表述固定下来——它预先回答了"上下文爆了怎么办"：有窗口保底，
不靠执行期截断。

### 机制二：窗口保底（唯一的天花板）

当前轮估算超过 `context_limit × 90%` 时，最老的事件折叠为索引行
直到回线。轻中度负载永远碰不到（本实验峰值 6.6%）；它是最后手段
而非常规机制。

### 机制三：文件地图与锚点自愈

* **文件地图**：降档历史中的文件以"路径 + 写/读轮次"清单注入装配，
  模型精准定位，不再盲目重爬（实测：39 次重读 → 3 次读取）；
* **锚点自愈**：edit_file 未命中时给出最接近内容的行号，成功时回显
  行号，文件不存在时报出解析路径——模型一次修正，不再整文件重读
  （实测一轮 6 次失败的主因）；
* **过期保护**：文件被外部修改后拒绝按旧内容编辑。

### 机制四：后台任务的会话化治理

后台进程记录启动会话；跨会话查看/停止被拒；会话退出时该会话的
后台进程一并整树关闭（keep_alive 常驻除外）。实测教训：baseline
对照组因"旧服务占端口 + 无归属管理"多烧了一整轮（1.75M tok，
全场最贵单轮）。

### 机制五：成本核算的完整落盘

步数、上下文峰值、名义/等效 token、命中率、整理成本——全部逐轮
写入 task.json。**没有这套核算，§1 的所有结论都不存在。** 仪器先于
实验，实验先于优化。

## 4. V3 待实现：水位触发的批量合并整理

v2 规则"轮闭合即整理"的实测账目：14 轮整理 98,111 tok，约 7K/轮；
R2 干活 2,816、整理 3,118——**整理比干活贵**。V3 规则：

* 轮闭合后**不再立即整理**，未整理轮的原始内容体量进入"整理水位"；
* 水位超过阈值 → 触发整理；
* 小会话可能全程不触发——整理成本归零，早期不再有负优化。

**水位阈值不要追求理论最优**——不同任务的最优值不同，陷入
70%/72%/68% 的参数调优是局部陷阱。V3 只需要一个大致合理的区间；
前瞻性决策留给 V4/V5：

> 整理是否值得 ≈ （基座 − 整理后基座）× 预计未来步数 / 30
> 　　> 整理成本 + 缓存重建成本

**批量合并整理**（触发后的执行方式）：把所有未整理轮一次批量处理——

* 调用次数：N 轮 N 次 → 1 次（摊薄）；
* 跨轮去重：模型每轮重复交代的决策/背景，合并索引时天然去重；
* 合并意图：多条相邻输入合并成一条 Normalized 意图，索引不再碎片化；
* **可展开性不变**：事件 ID（R{k}-E{nn}）不受合并影响。

## 5. 合并整理的边界与后续方向（V3.x）

**原则：合并的是"上下文视图"，不是原始历史。**

R1/R3/R5/R7 可以在整理视图里折叠成同一个工作脉络（如"ICP 误差
排查"），但每轮原文与事件 ID 原样保留——"这个参数是哪次测的？"
依然能精确回到 R3。

实现上**不引入** embedding / 聚类 / 向量库：先用时间邻近 +
Normalized 意图 + 状态字段分簇就足够。这一方向放 V3.x，不为它
提前复杂化。

## 6. Runtime Governance：实验踩出的下一个区域（独立方向，不并入 V3）

这轮实验暴露的大量问题根本不在上下文管理本身：Gradio 进程占端口、
服务重启后跑旧代码、文件被外部修改、代理 Fake-IP、依赖装错环境……
它们造成同一条因果链：

```text
Runtime 不可靠
  ↓ Agent 反复排查 Runtime 问题
Steps 增加 → Context 增加 → Token 增加
```

**好的 Runtime 本身就是上下文优化。** 这条因果链值得成为 Wovra 的
一个独立机制方向（Runtime Governance）。已落地的部分：后台任务会话
归属与退出清理、敏感命令确认、文件过期保护、原子落盘、子进程编码
统一——它们既是安全问题，也是上下文质量问题。

**但不把这些塞进 V3**——什么都能管的代价是没有任何机制被真正验证。
Runtime Governance 的系统化放下一阶段，解决真实踩出来的问题。

## 7. 缓存的三层优化框架（定位修正）

不写"缓存不重要"，写**分层**：

```text
第一层  减少不必要的上下文           → 降基座（主税基）
第二层  保持上下文追加稳定           → 提命中率（折扣）
第三层  合理安排整理/展开的时机      → 避免无意义的缓存破坏
```

最终形态是**低基座 + 高命中**，不是二选一。V3 已完成第二层的口径
修正（命中率 = 诊断指标）；第一层靠机制一/三/四；第三层是 V4/V5 的
研究问题——"什么时候值得主动破坏缓存"比"怎么提高命中率"更有意思。

## 8. 地图与下一阶段

```text
                    Wovra
                      │
         结构化长时运行工作
                      │
    ┌─────────────────┼─────────────────┐
    ↓                 ↓                 ↓
Context         Runtime            Agent
Management      Governance         Organization
（V3 已插旗）    （已踩出问题清单）  （下一站）
```

三个区域与上下文的关系：

* **Context Management**：已发生的历史，哪些应该进入当前上下文——
  **事后控制**；
* **职责划分**：哪些事情从一开始就不该由这个 Agent 负责——**事前
  控制**；
* **Multi-Agent**：不同 Agent 的工作上下文天然隔离——**结构性控制**。

下一阶段沿地图推进：职责划分 → 最小 Multi-Agent 实验 → Runtime
Governance 系统化。等新的实测把我们打脸了，再回来写 V4。

## 9. 封版清单

**已确定（机制基线，冻结）**：

1. 执行期零信息分辨率损失（零主动截断）
2. Round 内信息完整
3. Round 结束后再进行历史整理
4. 整理采用水位触发
5. 多个未整理 Round 批量处理
6. 原始历史不可变
7. 整理结果是可重建的视图（Organization View ≠ 原始历史）
8. Full 信息始终可展开（expand_history）
9. 缓存命中率是诊断指标
10. 基座（Context Base）是主要的成本控制对象
11. Workspace / 进程等 Runtime 治理纳入整体设计（独立方向）

**暂时不要急着解决**：

最优水位值 · 最优缓存破坏时机 · 最优整理提示词 · embedding ·
向量库 · 自动语义聚类 · 复杂记忆系统 · 完整 Multi-Agent ·
动态 Agent 拆分 · 全自动 Planner

## 一段话总结

V3 的全部修正来自同一个顿悟：**缓存命中率是折扣，基座才是税基；
执行期的截断是在省折扣钱的同时放大税基。** 所以：执行期零截断、
轮内赦免，让模型看到它该看到的一切；管理的唯一职责是在水位到线时
把基座批量折叠到低位——一次破坏缓存，换取之后每一步的低税基；
命中率从此只用来诊断，不用来讨好。而这次实验还揭示了第二层：
**Runtime 的可靠性本身就是上下文优化**——那是地图上的下一站。
