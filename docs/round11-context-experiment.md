# R11 实测报告：同一任务在三代上下文机制下的表现

> 2026-09-05。会话 `20260904-211910-fbd3e6`（managed 模式）。
> 同一个任务、同一个文件、同一句用户输入，在机制两次迭代后各执行一次，
> 外加 9/4 晚 baseline 会话 `3c87e1` 对同一网页的迭代作参照。
> 这是"执行期截断"系列机制（轮内折叠 → 2KB 安全截断 → 零截断）的
> 收官实测，数据全部来自 task.json 落盘记录，无人工修饰。

## 0. 一页结论

1. **同一任务，三代机制，只有零截断完成了。** 给 1134 行的 `chat.html`
   加功能：折叠时代 40 步烧完只落地 3 个 edit；2KB 锁孔时代 11 次读取
   全部沉没、零 edit；零截断时代 **3 次 read_file（理论最小值）+ 18 次
   edit_file，一轮完成 6 组新功能**。
2. **名义 token 大、等效 token 小。** 尝试 3 名义消耗 374,732 tok，
   但追加式事件流带来 89.8% 的缓存命中，**等效输入只有 45,612 tok**——
   "不截断"并不是"贵"，在缓存定价下它恰恰是最便宜的布局。
3. **对照尝试 2：11 万 token 沉没，产出为零。** 省上下文的机制省错了
   地方：钱花了，活没干。等效输入才是唯一有意义的成本口径。
4. 设计定稿（9.1 二次修订）：**执行期零截断，压缩只属于整理侧，
   唯一的天花板是模型窗口本身。**

## 3. 逐次分析：死循环是如何形成、如何被拆掉的

### 尝试 1：折叠造的死循环

轮内折叠（50 事件软限制）把模型**同一轮里刚读到的文件内容**也折叠成
一行索引。于是：读文件 → 事件涨 → 早期读取被折叠 → 失忆 → 重读 →
事件更多 → 折叠更快。实测区间序列 `694-1003 → 700-769 → 864-1003 →
884-933 → 960-1003`，39 次 read_file 里大量重读同一区间，40 步烧完
只落地 3 个 edit。轮保持开放，98 个事件沉没。

### 尝试 2：2KB 锁孔

折叠废除后区间不再重叠（11 段互不重复）——但每段 400 行（19-21KB）
进入上下文时被 SAFE_RESULT_LIMIT 砍到前 2000 字符。模型面对的实际上是
一个 **2000 字符的锁孔**，只能一寸一寸蹭 42KB 的文件。它没有调用
expand_history（0 次）——因为 `[:4000]` 上限使"完整原文"的承诺对
19KB 的结果不可兑现，模型正确地判断这条路走不通。用户中断时 110,080
token 全部沉没、零产出。

### 尝试 3：零截断

读取区间 `(1-400)(401-800)(801-1134)` 恰为理论最小值——文件地图给了
路径，read_file 的 400 行分段引导给了读法，上下文里不再有锁孔。随后
18 次 edit_file 精准落地，`node -e` 校验结构，`start` 打开预览，
一轮闭合。**没有任何一步花在"找回本该在眼前的东西"上。**

## 4. 缓存经济学：名义 token 是假象，等效输入才是成本

| 口径 | 尝试 2（失败） | 尝试 3（成功） |
|---|---|---|
| 名义 token | 110,080 | 374,732 |
| 缓存命中 | 93,120（87.3%） | 310,400（**89.8%**） |
| 等效输入（未命中 + 命中/30） | ≈16,675 | **45,612** |
| 产出 | 0 个 edit | 6 组新功能 |

零截断让单轮名义 token 膨胀到 37 万，直觉上"很贵"——但追加式事件流
意味着每步 prompt 的前缀不变，正是前缀缓存的最优布局，89.8% 的命中
把真实成本压到 4.6 万等效输入。**"不截断"在缓存定价下反而是最便宜的
策略**；而截断省下的那点上下文，代价是重读步数和沉没的整轮成本。

| 修复项 | 证据 |

## 6. 遗留观察

1. **步数未落盘**：usage 行没有记录 LLM 调用次数（终端有显示），
   跨会话分析时缺一个维度，下次补。
2. **R11 整理尚未完成**（org_state=pending）：其成本将随下次记账
   出现（维护账本排水机制）；整理预期会把 task_state 从 R10 的
   `is_done=true / 路线讨论已收尾` 改写为新状态——状态修正路径的
   下一处实测点。
3. **单次 prompt 峰值未记录**：名义 37.5 万是多步累加，单步 prompt
   峰值（窗口占用的真实压力）值得在 usage 行补一个字段。
4. **诚实声明**：n=1，模型输出有非确定性；B 是不同对话的参照而非
   严格对照。结论的强度来自三代机制在同一任务上的方向一致性，
   而非统计显著性。

## 7. 设计定稿（随本报告生效）

> **执行期零截断。** 轮内事件全量进上下文，内容不做任何剪切；
> 唯一的天花板是模型窗口（估算 > `WOVRA_CONTEXT_LIMIT` × 90% 时
> 紧急折叠最老事件）；压缩只属于整理侧。窗口够大的时代，
> 窗口本身就是最宽裕的资源——省 token 的正确位置在整理，
> 不在执行者的眼前。
