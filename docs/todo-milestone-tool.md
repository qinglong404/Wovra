# Todo 阶段/工作项工具 · 设计稿（已实现）

> 2026-09-08。背景：早期以"计划两层论"否掉 todo 工具（计划赶不上变化，
> 工具化即僵化）。两层制以**计划深度恒等于 1** 化解——工具里永远
> 只存"当前阶段 + 它的工作项"，下一阶段在当前阶段验收通过后才允许写。
> 计划只保留一步深度，永远不与长期现实发生偏差累积。
> **状态：已实现**（同日）。开放问题已决：工具名 = `todo`；人工验收
> 分两型（阻塞型停轮等反馈 / 非阻塞型 defer_check 挂起累积、阶段收尾
> 一次性呈交、未决转 experiments 不搁置）；工作项跨轮持久（绑死阶段
> 生命周期，关阶段即清）。
> **2026-09-11 补充（用户拍板）**：明确两层是两个维度——阶段 = 可验收的
> 推进增量（最小可行 → 逐步增加功能），工作项 = 阶段内的拆解；verify 加
> **结构闸门**（未拆过工作项 / 带未完成工作项 → 拒绝），防模型跳过拆解。
> **2026-09-12 改版（用户拍板，worklog §53）**：①**改名**——原"大步/小步"
> 改为**阶段（Stage）/ 工作项（Item）**，动作名 `start_stage` / `add_item` /
> `check_item` / `drop_item` / `verify_stage` / `drop_stage`（旧名保留为
> 别名；落盘键仍是 `milestone` / `steps`，无需迁移）。理由：它们都带"步"
> 字，与执行账里的"步数"（`steps_used`）撞车、与"轮"抢语义。
> ②**验收不切轮**——阶段验收 = **轮内检查点**（带 `M{n}` 编号与
> `{round, event, block}` 锚点），轮 = 一次用户输入 → 最终回答，不再被
> 运行时事件分割（旧行为"检查点 = 轮边界"已废，见 worklog §52 取证）。

## 1. 概念

| 层 | 是什么 | 生命周期 |
|---|---|---|
| **阶段**（`todo.milestone`） | 一次**可验收的推进增量**：从最小可行起步、逐步增加功能 | 跨轮持久，验收后关闭（编号 `M{n}`） |
| **工作项**（`todo.steps`） | **阶段内的工作拆解**：阶段内直接做仍然复杂，必须拆成能逐步完成、逐步自证的工作项 | 绑死阶段：开阶段时建，关阶段即清 |

两层是两个维度（2026-09-11 用户拍板强调）：普通 todo 是"一个任务拆
几步"（平铺一条清单）；这里是"一个任务分几个阶段、每阶段内再拆解"
——删掉工作项就退化成普通 todo，故设**结构闸门**：未拆过工作项或带未完成
工作项 → verify 拒绝（先 add_item 拆解 / check_item 完成 / drop_item 留痕）。
E/F 组实测 8 个阶段 0 次拆解，不加门模型会跳过拆解直接闷头做。

粒度判据：一个阶段 = 一次可验收的增量。太大（"重写整个项目"）说明该拆；
太小（= 一个工作项）说明该并。验收口径来自用户，落在阶段的 `acceptance`
字段（`Task.acceptance_criteria` 已于 2026-09-11 遗产整治删除——实测
0/77 会话有数据、0 处消费者，本文档原文照存档纪律保留于下方引用之外）。

## 2. 状态模型（`task.todo`，随 task.json 持久化，深度恒为 1）

```json
{
  "milestone_seq": 4,
  "milestone": {
    "id": "M4",
    "goal": "多会话版：左侧列表 + 新建/切换/删除",
    "acceptance": ["刷新后会话保留", "删除当前会话回落到相邻会话"],
    "started_seq": 3,
    "planned": true,
    "deferred": []
  },
  "steps": [
    {"text": "sessions 数据结构与 localStorage 读写", "done": true},
    {"text": "切换/删除交互 + 移动端抽屉", "done": false}
  ],
  "history": [
    {"id": "M3", "goal": "单文件聊天页初版", "evidence": "node tests/run.js 全绿",
     "started_seq": 1, "closed_seq": 2,
     "anchor": {"round": 2, "event": "R2-E17", "block": "R2-B3",
                "at": "2026-09-12T20:31:04"}}
  ]
}
```

`planned` = 本阶段是否拆过工作项（结构闸门判据）。与 steps 是否为空分开
——全部完成或 drop 后 steps 为空，"拆过"这个事实仍要能查到（旧数据无
该字段视为 false，兼容：旧阶段未拆工作项的会被门拦一次，属预期纠偏）。

`milestone_seq` / `milestone.id`（`M{n}`）与 `history[].anchor`
（`{round, event, block, at}`）是 2026-09-12 新增：阶段要**编号 + 锚点**，
"这个阶段在哪一轮、哪一块完成"可查（`block` 在轮闭合、块切分完成后由
`_backfill_stage_anchors()` 机械回填）。旧数据无 `id` 时按历史长度推断。

## 3. 工具形态：单工具多动作（常驻工作工具）

模型主动调用的**工作工具**（非维护提交工具；常驻 → tools 数组恒定，
缓存纪律不变）。**动作名 v2（2026-09-12）**，旧名保留为别名：

| 动作 | 语义 | 守卫 |
|---|---|---|
| `start_stage(goal, acceptance[])`<br>（旧名 `start_milestone`） | 开新阶段，acceptance 必填，**硬上限 3 条**（F 组实测 4-6 条打包 → 上下文被拖大 → 整理批次撞等待） | 已有进行中的阶段 → 拒绝（深度=1 强制）；acceptance > 3 → 拒绝并要求拆成下一阶段 |
| `add_item(text)` / `check_item(text)` / `drop_item(text)`<br>（旧名 `add_step` / `check_step` / `drop_step`） | 工作项增删改；add 即置 `planned=true` | 无进行中的阶段 → 拒绝 |
| `verify_stage(evidence)`<br>（旧名 `verify_milestone`） | 关阶段：证据必填（测试输出/人工确认） | **结构闸门**：`planned=false`（从未拆过工作项）或有未完成工作项 → 拒绝；通过后自动追加 TaskState.completed、清空工作项、**在轮内留一个检查点**（不切轮） |
| `drop_stage(reason)`<br>（旧名 `drop_milestone`） | 诚实作废（计划可证伪，记录死亡原因） | — |
| `defer_check(text)` | 挂起非阻塞人工验收，阶段收尾一次性呈交 | — |
| `show()` | 读当前状态 | — |

## 4. 集成点（不另立第二本账）

* **TaskState 单一事实源**：`verify_stage` 自动把阶段摘要 + 验收
  证据追加进 `completed`——todo 是 TaskState 的结构化前哨。
* **阶段验收 = 轮内检查点（2026-09-12 改版，worklog §52/§53）**：
  验收只往当前轮追加一条检查点（`round["checkpoints"]`，带 `M{n}` 与
  `{round, event, block}` 锚点），**不闭合轮、不开新轮**。旧行为
  （"检查点 = 轮边界"，为让巨型轮期间水位能出力）造出没有用户意图的
  人造轮、并让步数跨轮累计，已按用户口径废除；**巨型轮不做特殊处理**
  （用户口径：服务长期多轮任务，单体巨轮不值那份维护钱）。
* **runtime-reminder 尾部**：展示"当前阶段 + 工作项进度"——跨轮/中断后
  续跑的工作记忆。
* **机制二历史线**：阶段边界 = 类内叙事的**章节标记**——干活时由模型
  声明，整理时免反推（DeepSeek"逻辑阶段归组"的正解）。
* **轮 ↔ 阶段映射（2026-09-09 落地，2026-09-12 带编号）**：
  `verify/drop_stage` 在 history 记录 `started_seq` + `closed_seq`
  （旧数据缺 started_seq 时按"上一阶段闭合轮 +1"推断，区间不重叠）；
  整理/分裂指令自动注入 `[轮↔阶段映射]` 段——同一阶段的轮通常同属一个
  功能域，辅助现状归属判断。
* **现状清单检查点**：阶段验收 = 现状可能变化的时刻，与分裂分析的
  现状清单更新天然对齐。

## 5. 纪律

1. 深度恒 1：永不维护长程计划。
2. 入口/出口都是证据：acceptance 必填、evidence 必填，禁止自述完成。
3. 诚实作废：计划可证伪，废弃要留原因。
4. **acceptance 有下游后果**：验收标准的粒度质量直接决定这一摊活被
   组织成几个块/归到哪个域（整理以轮为单位出块与归属）。阶段按"可验收
   的增量"划分，acceptance 写可检验的口径，不写"做好做完善"这类
   不可判定的空话。
5. **阶段收窄硬约束（2026-09-09 F 组数据驱动）**：acceptance 1-3 条，
   超 3 条拒绝。F 组 5 个阶段全部 4-6 条打包（如"核心玩法：物品栏
   图形化+挖掘进度+粒子+音效+存档+视角"），单轮事件 367 个、上下文
   堆到 325K、整理 6 次全 pending——阶段宽度就是轮宽度与整理批次
   大小，宁可拆细快跑。

## 6. 开放问题（已决，见头部状态）

* 工具名：`todo` / `plan` / `milestone` → 定为 `todo`（2026-09-12 复核：
  保留不改，它是账本入口，与"轮/步"不撞词）。
* `verify_stage` 是否需要用户确认——倾向：机器可验的走测试证据，
  人工验收类阶段走 experiments 通道（机制五"人当传感器"）。
