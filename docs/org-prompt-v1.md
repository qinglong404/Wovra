# 整理提示词 v1（标签体系接入 org 指令）

> 用途：替换 `agent.py::_organize_rounds` 的 instruction 主体（当前只有
> "信息量自适应"一句话）。标签体系（block-tags-v1.md）此前只存在于
> 展示文档，这是第一次把"标签 = 分辨率指令"写进整理调用本身。
>
> 目标：消除 org 的"应该怎么写"思考（15K 思考撞输出上限的病根）。
> 模型不判断"哪些内容重要"——标签已定详略与焦点，模型只执行。

## 提示词全文

```
[整理指令]
以上是本会话的完整上下文。请把其中这些轮次整理成结构化档案：
R{seq_list}。其余轮次不要输出。

[分块地图]
以下块由 Runtime 按工作对象确定性划分并打了标签。标签 = 写多细、
写什么的指令，你按标签执行，不需要判断"哪些内容重要"。

{map_lines —— 每行一个块：块ID + 标签行 + 事件范围，见下}

{ms_lines —— 轮→里程碑映射，沿用现有注入}

[标签说明]

一、块类型 → 产物

1. 文件块【路径(状态)】：标签序列
   把块内内容综合总结成一段话：
   - 按标签序列所代表的时间序交代：从哪来、做了什么、结果如何；
   - 多标签只做覆盖检查（每项都交代到），不作为分段格式；
   - 带「工具」的块 = 吸收了验证/执行类工具（test/build/run）：
     把工具调用结果融进叙述，构成因果链（如"改了 X，跑 pytest
     验证通过"）；只写动作不写结果是缺失；
   - 一段话写完，不拆条、不重复标签。

2. 环境块【环境块】：
   为什么做环境准备（目的）+ 结果，简练一段。

3. 用户块【用户块】：
   全量保存：用户补充/修正的原话要点 + 意图 + 约束；说明这段补充
   插在哪段工作之后。与文件块独立成段，不混写。

4. 保底块【保底块】：（可能带「工具」）
   助手结论，简练一段。无「工具」标签的纯聊天轮：若内容没有可
   复用价值（寒暄/闲聊/招呼），这一块写一行「无法定夺」；若含
   方案谋划、思想对齐、答疑、决策结论，正常描述。

二、文件块标签 → 写什么

   创建  文件用途、整体结构、核心设计思想（骨架级，写充实）
   重构  重写动机、与旧版的关键差异、现在的结构（差异是重点）
   修改  改了什么实现、为什么改、影响什么
   读    为什么读、读出的关键结论（它服务于后续的写/改/删）
   只读  文件用途/大致结构，细节不展开——需要时重新读
   删除  删了什么、为什么删、最终结论
   幽灵  路径：动作；幽灵（文件不存在）；结果；无实质内容
   越界  路径：动作；越界（被安全拦截）；结果；无实质内容

三、状态 → 详略底线

   - LIVE：当前有效内容/结构写清楚——这是现状，后续工作基于它；
   - DEAD：只保留死亡原因与最终结论。测试/实验类文件即使 DEAD，
     路径、操作序列、结果、失败原因必须保留（它验证了什么、怎么
     验的、结果如何，属于结论的一部分）；
   - 状态已在标签行给出，正文不要重复解释状态。

四、用户输入（轮头）

   👤 用户：原文；🎯 意图：澄清后的意图；📌 关键约束：红线/硬性
   约束。全量保存，最高分辨率。

五、篇幅

   - 标签定了分辨率基线，块内实际信息量只做微调：大改动/长推理/
     关键决策写满该标签允许的篇幅；低信息量块（寒暄/一句话问答）
     两三行甚至一句即可；
   - 关键数字（行数/字节数/条数/次数）与关键命令的目的必须保留；
     禁止空洞词（"调整""修改""处理"）单独成描述；
   - 含最终回答的块，对用户的承诺/交付口径完整写入。

完成后调用 submit_organization 工具提交结果（唯一出口，不要在
正文中输出 JSON）。字段语义以工具定义为准；块 ID 逐字取自
[分块地图]，每个块一条、一个不落、与地图同序。
```

## 分块地图升级

现格式（只有范围）：

```
R9（3 块）：R9-B1=E01~E02 · R9-B2=E03~E04 · R9-B3=E05~E07
```

升级为逐行带标签（复用 file_block_structure.py 的 block_label 格式，
一个块一行，标签即指令）：

```
R9（3 块）
  R9-B1 【testlab/target.txt(LIVE)】：创建，工具（E01~E02）
  R9-B2 【保底块】：工具（E03~E04）
  R9-B3 【testlab/editme.txt(LIVE)】：创建，修改（E05~E07）
```

标签行来源（全部确定性，零 LLM）：

| 字段 | 来源 |
|---|---|
| 块ID / 事件范围 | blocks.py 的块结构（已有） |
| 块类型（文件/环境/保底/用户） | blocks.py 的 `kind`（已有） |
| 生命周期标签（创建/重构/修改/读/只读/删除） | 从 `ops` 推导 + FileLedger 的版本数判断创建 vs 重构（需在 _organize_rounds 内按轮序跑一遍 ledger，与 file_block_structure.build 同流程） |
| 幽灵/越界 | 块 `fail_tags`（已有） |
| 工具 | 块 `has_tools`（已有，v3 块级精确归属） |
| 状态 LIVE/DEAD | FileLedger 状态（已有；READ_ONLY 显示为 LIVE"存在即可用"） |

## 接入要点

1. **静态常量**：`[标签说明]` 全文做成模块级常量 `_ORG_TAG_INSTRUCTIONS`，
   不随批次变化——追加式指令，前缀缓存稳定，命中后成本≈0。
2. **动态部分**：只有 seq_list、map_lines、ms_lines 三处拼接。
3. **「无法定夺」的视图合并**：LLM 产物里是每轮 `block_summaries[0].summary
   = "无法定夺"`；视图层渲染时把连续且 summary=="无法定夺" 的轮合并成
   一行 `R1-2：无法定夺`（file_block_structure.build 已有同款逻辑，
   渲染端补齐）。这是接入时顺带实现的部分。
4. **schema 不动**：submit_organization 的字段语义不变，变的只是
   block_summaries 里 summary 的写法规则。
5. **HISTORICAL**：暂不落地（触发条件未定义），提示词不写，状态只出现
   LIVE/DEAD。

## 未决点（等你定）

1. 提示词长度：标签说明约 700 字，每次整理调用追加。缓存命中后
   几乎免费，但不命中的维护调用会多花这 700 字输入——可接受？
2. 「无法定夺」要不要限定在**连续纯聊天轮**才合并（合并行格式
   `R1-2`），还是任何纯聊天轮都单行「无法定夺」？（当前文档按
   连续合并写，和 build 一致）
3. 生命周期标签进地图后，地图行数变多（35 轮会话约 130 行）——
   是否可接受，还是只对**待整理轮**生成地图（现有实现已只对待
   整理轮生成，无增量）。
