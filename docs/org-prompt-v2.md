## 整理指令的完整拼装

运行时按以下顺序拼装（`_organize_rounds`）：

1. `[整理指令]` 头（动态：轮次列表）
2. `[压缩元信息]`（静态模板，轮次范围动态注入）
3. `[分块地图]`（确定性生成：块 ID + 标签行 + 👤 锚点 + 事件范围）
4. `[轮↔大步映射]`（来自 todo 里程碑历史）
5. `[标签说明]`（静态常量）
6. 尾部提交约束

### [压缩元信息]

```
[压缩元信息]
- 本次整理范围：R{seq_list}。连续纯聊天轮已合并为组（如 R1-2），组内共用一个块描述、一个综合意图。
- 状态定义：LIVE=文件当前有效（内容以磁盘为准，需要细节时重新读）；DEAD=已删除/已闭环/测试已清理（不是失败）；B1=该轮第一个块。
- 原文都在会话历史里，本视图只降分辨率不删事实；后续需要细节时按块/事件取回原文。

```

### [标签说明]（静态常量全文）

```
[标签说明]
一、块类型 → 产物
1. 文件块【路径(状态)】：标签序列 —— 把块内内容综合总结成一段话：
   按标签序列所代表的时间序交代：从哪来、做了什么、结果如何；多标签
   只做覆盖检查（每项都交代到），不作为分段格式；带「工具」的块 =
   吸收了验证/执行类工具（test/build/run）：把工具调用结果融进叙述，
   构成因果链（如"改了 X，跑 pytest 验证通过"）；只写动作不写结果是
   缺失。一段话写完，不拆条、不重复标签。
2. 环境块【环境块】：为什么做环境准备（目的）+ 结果，简练一段。
3. 用户块【用户块】：轮头**之后**的用户补充/修正输入。先保留
   补充原话（引号），再附要点（插在哪段工作之后）。原话取补充
   输入本身，不是轮头原文。与文件块独立成段，不混写。
4. 保底块【保底块】：（可能带「工具」）助手结论，简练一段。纯聊天
   轮（无「工具」）自由发挥：如实描述这轮实际内容（寒暄/问答/
   决策讨论/方案谋划），不要用占位词敷衍。
二、文件块标签 → 写什么
   创建：文件用途、整体结构、核心设计思想（骨架级，写充实）
   重构：重写动机、与旧版的关键差异、现在的结构（差异是重点）
   修改：改了什么实现、为什么改、影响什么
   读：为什么读、读出的关键结论（它服务于后续的写/改/删）
   只读：文件用途/大致结构，细节不展开——需要时重新读
   删除：删了什么、为什么删、最终结论
   幽灵：路径：动作；幽灵（文件不存在）；结果；无实质内容
   越界：路径：动作；越界（被安全拦截）；结果；无实质内容
   测试/实验文件块（创建-读-删除的测试矩阵成员）：统一一行模板
     "文件：测[特性]；结果[正常/异常]：[结论]"（如
     "t2_empty.txt：测空文件读取；read_file 返回'是空文件'，正常"）。
     信息量小，一行即可，禁止跳过。
三、状态 → 详略底线
   LIVE：当前有效内容/结构写清楚——这是现状，后续工作基于它；
   DEAD：只保留死亡原因与最终结论。测试/实验类文件即使 DEAD，路径、
     操作序列、结果、失败原因必须保留（它验证了什么、怎么验的、结果
     如何，属于结论的一部分）；状态已在标签行给出，正文不要重复解释
     状态。
四、用户输入（轮头）：👤 用户原文 / 🎯 意图（澄清后）/ 📌 关键约束——
   全量保存，最高分辨率。
   🎯 意图只提炼该轮轮头用户输入原话的内容：短批准句（如"可以"）
     的意图 = 批准/同意上文的提议，不扩展不脑补；轮内事件（ask_user
     的回复、工具结果）不是意图来源；合并组综合组内所有轮的原话。
     意图必须与该轮 👤 用户原文直接对应——原文里没有的内容（如其他
     轮的"可以测试A""23M/458M"等）一律不得写进意图。
   📌 约束标注来源轮次与时效：格式 [R7] 只读限定 agent-test；被后续
     轮覆盖的约束注明覆盖关系（如"R8 用户新指令开放写入，覆盖 R7
     只读"）；同一约束多次出现只保留最新状态并带最新来源轮次。
     轮内用户拍板的关键决策（ask_user 的回复、明确的选型如"选 C"）
     也写入该轮 📌 约束。
五、轮头与块描述分工：轮头已承载"用户说了什么、要什么、约束什么"，
   块描述不得复述用户输入，只写助手/工具对它的响应——做了什么、
   结论是什么。
六、合并与覆盖（2026-09-10 用户拍板）
   1. 连续纯聊天轮（保底块且无「工具」）在[分块地图]中合并为一组
      （如 R1-2）：组内只输出一个块描述（写到组内第一轮的块上，
      其余轮不写），同时 🎯 意图/📌 约束综合组内所有轮的用户输入
      提炼一次（写在组内第一轮）——禁止只取其中某一轮的内容；
      合并组块描述内部按子轮分段标注（R19：…/R20：…/…），便于
      后续按轮拉开原文；
   2. 每个块都必须给出描述，一个不落：信息量少的块一句带过即可，
      禁止跳过不写；
   3. 块 ID 与内容必须严格一一对应：从[分块地图]第一个块开始按
      顺序写，不跳号、不错位——某块的内容必须写在该块的 ID 下，
      禁止把 A 块的内容挂到 B 块的 ID（实测易犯：测试矩阵轮整体
      错位一位）。
七、篇幅
   标签定了分辨率基线，块内实际信息量只做微调：大改动/长推理/关键决策
   写满该标签允许的篇幅；低信息量块（寒暄/一句话问答）两三行甚至一句
   即可；关键数字（行数/字节数/条数/次数）与关键命令的目的必须保留；
   禁止空洞词（"调整""修改""处理"）单独成描述；含最终回答的块，对
   用户的承诺/交付口径完整写入。

```

## 运行参数（2026-09-10 实测定稿）

| 项 | 值 | 原因 |
|---|---|---|
| max_tokens | 393216（384K） | 不传时端点默认锁 4,096——org 全覆盖产物、write_file 大参数都在此截断（全部历史截断问题的根因） |
| 思考 | 开 | 思考不是截断原因；关闭后模型把规划写进正文、工具调用质量下降 |
| org 工具集 | 只留 submit_organization | 模型会把整理指令当普通工作对话乱调工具（实测去调 write_file） |
| 重试 | 无 | 重试只是再付一遍生成，不能确定解决失败（实测两次同因失败） |
| 分批 | 不分批（全批） | 分批伤缓存命中；全批靠 👤 锚点解决意图偏移 |

## 产物契约（submit_organization）

- 每轮一个元素：normalized_user_input（🎯）+ key_constraints（📌）+ block_summaries（逐块）
- 合并组（连续纯聊天轮）：只输出一个块描述 + 综合意图（挂在组首轮），块内按子轮 R19：/R20：分段
- 约束标注来源轮次与时效：[R7] 只读限定；被覆盖注明（R8 开放写入覆盖 R7 只读）
- 用户块保留补充原话（引号）+ 要点
- state_patch 挂在批次首轮；视图/文档渲染为顶部[当前状态卡]

## 视图分代折叠（2026-09-10 用户拍板，方案 b）

会话可上千轮，视图（每轮 ~200-400 token）会累积爆掉。机制：

- **最近 3 次水位触发（3 代）的整理视图全量保留**；更早的轮折叠。
- **折叠判定用装配时的实时 FileLedger**（零 LLM，现场重算）——整理时的
  文件状态会过期（新会话文件可能重建/删除），不用整理时的状态。
- 折叠轮 = `[R5]（折叠）👤 原文 + 🎯 意图 + 当前仍 LIVE 的文件的块摘要`，
  其余块折叠成一行注明（防模型误以为该轮只有这些块）。
- **两级展开**：expand_history 轮号 → summary 档（块视图）→ full 档（原文）。
- 代次：每次成功整理 `org_generation += 1`，批次轮落盘标记；旧轮视为第 1 代。
