# 缓存前缀布局：不变量与决策规则

> 本文是**前缀布局的决策存档**（2026-09-11 建立）。它存在的理由：这类问题
> 反复出现在讨论里（"整理吃的是哪段缓存""分裂后能不能吃到"），每次重推一遍
> 机理既费上下文又容易推错。故把**不变量**与**实测数字**固化在这里，后续
> 讨论直接引用。
>
> 实测证据见 `worklog-20260911.md` §16（维护调用命中率）与 §19（断裂定价与
> 视图前缀测算）。

## 0. 一页结论

* **命中 = 从第 0 token 对齐的连续公共前缀**，不是"能吃到某一块"。第一次
  分叉在哪，命中就到哪。
* **要复用前缀就得保留旧字节，要压缩就得改字节——两者不可兼得**。每批一次
  断裂是压缩的定价，不是缺陷。
* **实测定价：0.0075 元/批**（净 18,830 tok @ 未命中 0.4 元/M），换每步体量
  从 ~250K 降到 ~40K。**这笔交易压倒性划算。**
* **现行布局（system 最前）是能吃到 96% 的那个**；把整理产物放最前是从第 0
  字节分叉（实测公共前缀 **0**）。
* **分裂的真实收益是每轮体量（降 82–84%），不是跨视图共享缓存**——各视图
  之间只共享 system 头（实测 1,256 tok ≈ 1%）。分裂后各视图靠**各自积累
  长链**命中（96–97%）。
* **分裂后最大的剩余成本是信封重复**：TaskState + 文件地图 + todo 约 21K，
  每个视图各带一份，已占子视图 95% 以上。

## 1. 不变量（物理约束，不是设计选择）

1. **命中是连续公共前缀**。服务端从第 0 token 逐字节比对，断在哪就丢到哪。
   故"上下文由哪几段组成"不重要，"第一处不同的字节在哪"才重要。
2. **前缀顺序必须是"少变在前、多变在后"**。基于 1，把高频变化的状态放在
   前部，等于每次变化都作废其后全部前缀。
3. **维护调用是冷启动插入**：一次付掉整个尾部信封 + 指令段，这些 token
   对本进程必然是新 token，压不掉（实测 org 残余 ~9% 即此）。
4. **纯追加继承有效**：split 的 `cached` ≈ org 的 `prompt`（实测 98,944 ≈
   98,954），只付自己新增的指令与地图。

## 2. 现行布局（无分裂）

```
[1] system 人设（静态，冻结）
[2] 历史轮次视图（少变：闭合时成形，之后不可变——未整理全量、
                   已整理紧凑视图、更早折叠）
[3] 当前轮事件（追加式，轮内赦免）
[4] 运行时信封（绝对尾部：todo / TaskState / 文件地图）
```

规则：

* **只有整理生效（promotion）才破坏前缀**（2026-09-07 用户拍板）。除此之外
  装配严格追加。
* 信封放**绝对尾部**（2026-09-08 用户拍板，D 组实测）：放中部时 26 次 todo
  变化把命中率砸到 77.5%（段 2/3 零变化时 99.2–99.5%）。
* **V2 三档滑窗已废**：它每轮在装配中部改写历史，实测把命中率从 83.7% 砸到
  49.9%。任何"每轮中部改写"的机制都是同一个错误。
* 权衡：折叠判定 `keep_min = 最新代次 − 2`，新批次 promote 时最老一代从紧凑
  降为折叠——断裂点比"只改本批"更靠前一点。属可取舍项（省体量与断裂点前移
  可折算比较），当前保留。

## 3. 分裂重组布局（Level 1 派生视图）

三段排法（R24 讨论认可，**尚未实现**）：

```
[1] 共享 system 人设        ← 公共部分待在能被所有 agent 共享的头部
[2] 重组上下文（本域块描述 + 域卡 + 外域指针）
[3] 子 agent 身份与约束      ← 分叉点尽量往后，身份作为稳定尾
```

规则与理由：

* **公共部分在前、域相关内容在中、身份在后**：基于不变量 1，分叉点越靠后，
  能共享的前缀越长。身份作为稳定尾，只在子 agent 间不同。
* **身份放尾部有被历史淹没的风险**：缓解办法是让已固定在绝对尾部的运行时
  信封每轮重申一行子 agent 身份与边界（前提：这行不能每轮变，否则违反
  不变量 2）。
* **域视图内部有两种彼此冲突的排法**（`context-differentiation-runtime.md`
  原话倾向时间序，但值得实测）：
  * *时间序 + 外域块留一行指针*：能与主链共享更长前缀，指针行确定性渲染；
  * *域分组*：语义干净，但从头分叉。
* **不要指望跨视图共享**：实测各视图之间只共享 system 头。收益在"每个视图
  各自的长链"，不在"分裂后大家吃同一段缓存"。
* **粘滞路由不只是体验问题，是钱的问题**：多前缀树之间交替，若间隔超 TTL
  就是全价冷算（`context-differentiation-runtime.md` §3.2）。

## 4. 已实测否定的两个直觉

| 直觉 | 实测 | 结论 |
|---|---|---|
| 把整理产物放最前，可以吃到整理的前缀 | 公共前缀 **0** | 产物是整理调用的**输出**，不在任何已缓存前缀的头部；放最前从第 0 字节分叉，**比现状更差** |
| 分裂后大家共享缓存 / 整理产物放前面更省 | 各视图互享仅 **1,265 tok**（system 头） | 共享的是 system 头，不是内容；真收益是各自长链 + 每轮体量降 82–84% |

另一处需澄清的表述：**"只吃到系统提示词且不一定吃得到"不准确**。promotion
后仍能命中 system + 未被本批替换的更早紧凑视图；system 恰是冻结纪律下最
确定的一段。真正全丢的只有分叉点之后。

## 5. 待办（分裂第二步的设计输入）

1. **信封分片**（优先级最高）：文件地图只列本域 `file_domains` 的文件 + 一行
   指针；TaskState 按域裁剪或保持全局单份。**不做这一步，分裂只降了内容、
   没降固定开销**（实测：子视图 21–24K 里 95%+ 是信封）。
2. **域视图内部排法实测**：时间序 + 外域指针 vs 域分组，量各自与主链的公共
   前缀。
3. **折叠窗口与断裂点的折算**：`keep_min = 最新代次 − 2` 让断裂点前移，
   是否值得收紧/放宽，用同一单位（token）比较。

## 6. 决策速查

* 要问"某改法能不能省缓存" → 先问"第一次分叉在哪"，再算公共前缀 token。
* 要问"某改法值不值" → 断裂定价 ~0.0075 元/次；体量降幅按每步计。
* 要问"分裂收益" → 算**每轮体量**（主 agent 路由视图 vs 单体全链），
  不要算跨视图共享。
* 引用命中率数字前 → 先看 `worklog-20260911.md` §16 与 §19，确认数字
  属于哪个时代（收窄 tools 时代 / 恒定数组时代），过期读数不得作为
  决策依据。
